## 0. 摘要（一分钟版）

- **一句话**：挑战与复习的**判分规则不动**（客户端仍是唯一真源）；服务端补三样东西——**挑战结算**（把逐题对错折算成带权重的分数与榜单）、**大白饭镜像账**（跨设备汇合 + 防滥用闸）、**进度派生表**（streak/汇总查询）。全部是加法：**新增 7 张表、6 个端点、3 个错误码、0 个新依赖、0 个新容器**。
- **每日挑战**：客户端做完整批题 → 把「逐题事实」（题号/语言/阶段/题型/难度/对错）一次提交 → 服务端**自己算分**（不信客户端的加权分）→ 落结算表 + 进排行榜。同一天同账号只结算一次（先到先得，多设备规则见 §8.4）。
- **每日复习**：**零新端点**——复习的加权抽样真源是 practice.json，而它已在 v1 同步四份之内（docs/21 §0.3-2）。合并后的练习史在本地重算权重，复习奖励（图库并集 / 碗数流水）各有既有落点。
- **计分算法**：`分 = Σ ok × 难度权重`，整数化存储（无浮点）。难度权重 easy/medium/hard/challenge = 100/150/200/250%；**2026-10-10 v3 起语言权重统一 100**（C/C++/Java/Python 同权——多语言不代表高分、专精一门也能霸榜），语言只进统计/筛选（`score_by_lang`）。**算例：5 题对 4 题 = 550 分（本批满分 700）**，见 §5.5。
- **大白饭**：本地账继续是「离线可用的第一真源」；服务端只做**镜像账 + 闸**（幂等键去重、每条 delta 白名单、按 kind 日上限、重放与时钟异常检测）。服务端**不发饭、不重判**——它证明不了对错，只保证「批量刷分/重放/重复入账」不成立。
- **难度分级**：逐题元数据（difficulty/lang/stage/type）进提交体与落库；排行榜支持按语言/难度筛选；服务端对「difficulty=challenge」做合法性降级（防全报挑战题刷分）。
- **离线**：一切照旧——做挑战、复习、赚饭、花饭全离线可用；结算与流水进待结算队列，恢复后幂等重放；**不允许**把未入云条目当丢失。
- **诚实边界（先说清）**：纯客户端判分的世界，服务端**无法证明**一局的真伪；本设计的防作弊目标是「防批量、防重放、防抬权重」，不是「防单机改内存」——后者需要内容上云 + 服务端重跑判分，明确列入不做（§8.5）。
- **需要拍板**：7 项在 §10（权重数值、榜单隐私、大白饭是否现在做、多设备同日口径、AI 题计分、分榜口径、阶段编号与先后）。

### 1.3 客户端红线约束（不可违反）

- **离线优先**：核心功能断网完整可用；同步失败**静默降级**（不报错、不阻塞、不弹失败窗）——挑战/复习/大白饭全部照此（docs/25 §1.5-②）。
- **判分唯一真源在客户端**：`shared/quiz-grading.ts`（同步判分）+ `shared/run-grading.ts`（真跑判分）；本文不允许出现"第二套判分"。
- **难度唯一真源**：`shared/difficulty.ts` 规则表；服务端需要的副本进 protocol.ts 并由单测断言两表等价（§7.4）。
- **零 API 底线**：桌宠全本地（含大白饭发放规则）；云同步是**可选增强**，失败不影响任何本地行为。
- **数据安全**：凭据不进日志/聊天；测试一律 `--user-data-dir` 隔离；改 JSON schema 必 bump version + 写迁移（铁律 6）。

## 2. 客户端现状底账（设计必须兼容的事实，全部 2026-10-07 实读源码；挑战相关行已按 2026-10-10 v3 主人令写回）

### 2.1 判分与题型（设计的地基）

| 项 | 现状 | 出处 |
|---|---|---|
| 同步判分 | choice 下标相等 / fill 归一化（trim+折叠+小写）/ code 走真跑输出契约 / codefill 每空全对 | `src/shared/quiz-grading.ts` |
| 真跑判分 | codefix / codewrite 真编译真运行，结论在会话的 `runResults` 上（不在同步函数里） | `src/shared/run-grading.ts` |
| 判分入口 | 全项目唯一入口 `quiz.verdictAt()` → `gradeQuestion()` / 真跑读取；挑战记账也借这个入口 | `stores/quiz.ts`、`stores/challenge.ts` |
| 难度 | 运行时解析：choice/fill→easy；code/codefill→medium；codefix→stage≥3 hard 否则 medium；codewrite→hard；**显式 difficulty 覆盖一切**（挑战题靠它） | `src/shared/difficulty.ts` |
| 挑战题 | 24 道精选模板（全为 codefix/codewrite），只在阶段/整门/每日挑战三处出现 | docs/20 §3.3 |

### 2.2 每日挑战现状

| 项 | 现状 | 对服务端设计的含义 |
|---|---|---|
| 题量 | **抽整个已学题库**（开始前可勾选今天想考的语言；common/基础题恒含）；**答对继续、答错立即结束**，无固定题数——`CHALLENGE_RUN_MAX = 5000` 只是健全性上界（2026-10-10 v3 主人令） | 结算接受 total ∈ [1,5000]（无产品题数上限） |
| 出题 | 只用 learned 课（本地池）+ AI 兜底（source: 'local'\|'ai'）；AI 失败静默退回本地 | 服务端不需要（也没有）内容包；`source` 进结算 |
| 本地分数 | `score: { correct, total }`（原始对数，无权重）；逐题 `answers[{your, ok}]` 按存 | **本地语义不动**；加权分是新增的"云端分"（§5.4） |
| 留存 | 30 天滚动窗口，裁剪在主进程（`CHALLENGE_KEEP_DAYS=30`）；文件 `challenge.json` | 服务端结算表**永久保留**（用于榜单/streak），两者不同生命周期 |
| 日期 | `dateKey = todayKey()`（**本地时区**，`shared/dates.ts`） | 上报的 dayKey 可被改时钟伪造 → **结算窗口 = 过去 ≤30 天 / 未来 ≤+1 天**（超窗 400 `VALIDATION_FAILED` + log.warn，§4.3；30 天对应本地 `CHALLENGE_KEEP_DAYS` 滚动窗，未来宽容吸收 UTC 日差与时钟偏差） |

### 3.3 ② 进度表（user_days / user_stats，均为派生）

> 权威数据仍是 `user_docs` 里的四份 JSON（服务端只存不解释）。这两张表是**查询用的派生**：由每日任务从 user_docs（practice/profile）+ challenge_days + rice_ledger 计算，**可随时全量重算**（对齐 docs/22 §4.8 台阶 2「派生表可弃可重算」）。

```sql
CREATE TABLE user_days (
  account_id  uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  day_key     date NOT NULL,                -- 客户端本地日（结算/流水带来的口径）
  learned     smallint NOT NULL DEFAULT 0,  -- 当日 profile.learned 净增课数
  practiced   smallint NOT NULL DEFAULT 0,  -- 当日 practice 会话数
  correct     smallint NOT NULL DEFAULT 0,  -- 当日答对题数（practice items 汇总）
  total       smallint NOT NULL DEFAULT 0,  -- 当日作答题数
  score       int      NOT NULL DEFAULT 0,  -- 当日挑战分（服务端算的加权分，§5）
  updated_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (account_id, day_key),
  CHECK (correct <= total)
);

CREATE TABLE user_stats (
  account_id      uuid PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  learned_count   int NOT NULL DEFAULT 0,   -- 累计已学课数
  practiced_count int NOT NULL DEFAULT 0,   -- 累计练习会话数
  streak_days     int NOT NULL DEFAULT 0,   -- 连续学习天数（含挑战/练习任一）
  last_active_day date,
  total_score     int NOT NULL DEFAULT 0,   -- 累计挑战分（总榜真源）
  updated_at      timestamptz NOT NULL DEFAULT now()
);
```

| 字段说明 | 口径 |
|---|---|
| day_key | 沿用客户端 `localDateKey`（本地时区）——与挑战 dateKey 同源；服务端不试图换算时区 |
| streak_days | 有任一学习动作的自然日连续计数；断一天归零；由每日任务重算 |
| total_score | = `SUM(challenge_days.score)`，冗余为快路径；重算时校验一致（不一致即重算覆盖） |

> 【修正注 · 2026-10-10 核定】本节描述与实现存在三处刻意的口径差，以实现为准：
> （1）`learned` 统计当日新增（取消已学后重学不扣减；净增口径在 v2 数据后无法还原）；
> （2）`practice` 归日与（3）`streak` 锚点均采用 UTC 服务端日（单一时间源；与客户端本地日的 ±1 天错位已由结算 dateKey 窗口容差覆盖，见 §4.3）。

### 3.4 ③ 挑战表（challenge_days / challenge_questions）

```sql
CREATE TABLE challenge_days (
  account_id        uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  date_key          date NOT NULL,
  install_id        uuid NOT NULL,             -- 结算设备（P10.1 的 device.json installId）
  source            text NOT NULL CHECK (source IN ('local','ai')),
  started_at        timestamptz,
  finished_at       timestamptz NOT NULL,
  correct           smallint NOT NULL CHECK (correct >= 0),
  total             smallint NOT NULL CHECK (total BETWEEN 1 AND 5000), -- 挑战 v3：无产品题数上限；沿革 0003(1..5)→0007(1..20)→0009(1..5000)，5000=健全性上界（CHALLENGE_RUN_MAX）
  score             int NOT NULL CHECK (score >= 0),      -- 服务端加权分（§5）
  score_max         int NOT NULL CHECK (score_max >= score),
  score_by_lang     jsonb NOT NULL DEFAULT '{}'::jsonb,   -- {"common":100,"cpp":150,"java":200,…} 服务端铸（实得口径：答错计 0，见 §5.5；v3 起只作统计/筛选）
  score_by_difficulty jsonb NOT NULL DEFAULT '{}'::jsonb, -- {"easy":200,"medium":150,"hard":200,…} 服务端铸（实得口径，同 §5.5）
  picked_langs      text[] NOT NULL DEFAULT '{}',          -- 开赛前勾选的语言（四门子集，声明序归一；0010）。旧行/缺省 = legacy：写侧派生落库、读侧返回库值（无迁移前存量行，§3.1）
  flags             text[] NOT NULL DEFAULT '{}',          -- 异常标记（§6.4），只标记不拦截
  submission_id     uuid NOT NULL,
  payload_sha256    text NOT NULL,             -- 提交体规范化后的 sha256（幂等冲突判定；2026-10-10 夜起含 pickedLangs——同 submissionId 换勾选值重放 → 409）
  settled_at        timestamptz NOT NULL DEFAULT now(),
  CHECK (correct <= total),
  CHECK (jsonb_typeof(score_by_lang) = 'object'),
  CHECK (jsonb_typeof(score_by_difficulty) = 'object'),
  CHECK (cardinality(picked_langs) <= 4 AND picked_langs <@ ARRAY['c','cpp','java','python']::text[]), -- 0010：四门子集；'common' 与未知语言落库即 23514 → 400
  PRIMARY KEY (account_id, date_key)           -- 一天一批：多设备同日先到先得（§8.4）
);

CREATE TABLE challenge_questions (
  account_id   uuid NOT NULL,
  date_key     date   NOT NULL,
  idx          smallint NOT NULL CHECK (idx >= 0),
  question_key text NOT NULL CHECK (question_key ~ '^[A-Za-z0-9_.-]+:[A-Za-z0-9_.-]+$'),
  lesson_id    text NOT NULL,
  qid          text NOT NULL,
  lang         text NOT NULL CHECK (lang IN ('common','c','cpp','java','python')),
  stage        smallint NOT NULL CHECK (stage BETWEEN 0 AND 3),
  qtype        text NOT NULL CHECK (qtype IN ('choice','fill','code','codefill','codefix','codewrite')),
  difficulty   text NOT NULL CHECK (difficulty IN ('easy','medium','hard','challenge')),
  source       text NOT NULL CHECK (source IN ('local','ai')),
  ok           boolean NOT NULL,
  points       int NOT NULL CHECK (points >= 0),
  PRIMARY KEY (account_id, date_key, idx),
  FOREIGN KEY (account_id, date_key)
    REFERENCES challenge_days(account_id, date_key) ON DELETE CASCADE
);

CREATE INDEX challenge_days_day_idx ON challenge_days (date_key);
CREATE INDEX challenge_questions_key_idx ON challenge_questions (date_key, question_key);
```

| 设计点 | 说明 |
|---|---|
| 为什么不存题干/答案 | 服务端**零内容**（docs/22 总原则）；题目本体在客户端内容包（内置题）或用户自己的 AI 题里。历史 key 随内容演进可能失效——服务端只做统计，不负责还原 |
| `score_by_lang` / `score_by_difficulty` | 排行榜筛选（§7.3）与将来「各语言战力」统计的快路径；**由服务端自己铸**（不信客户端算的分数），落这两个 jsonb 的是**实得**口径（答错计 0——与 §5.5 算例一致）；DB 侧只 CHECK 对象类型（`jsonb_typeof(...) = 'object'`），求和/对账靠服务端结算逻辑，不靠值域 CHECK |
| `picked_langs`（0010） | 开赛勾选语言的落库形态，排行榜「所选语言」列**唯一数据源**（§4.5）。服务端归一为**协议声明序**（c→cpp→java→python）后落库；上报缺省（legacy 客户端 / 全点掉只剩 common 题的合法开赛）→ 服务端**从题批派生**（questions 的 lang ∩ 四门、声明序）；上报了但为空数组/含 common/含未知语言/有重复 → 400（显式空数组与缺省在语义上等价、在协议上不等价——空数组是坏编码，400 抓它） |
| 两表用途分工 | `challenge_days` = 榜单/streak 的数据源；`challenge_questions` = 难度分析（"哪类题最常错"——docs/22 §4.8 台阶 3 的先行版），未来与 review 无关 |
| 挑战文档同步（v1.5） | `challenge.json` 走 user_docs 新 docType（0002 的 CHECK 已备）；**前置**：补 origin/uid 字段治 AI 题 key 撞主键（docs/20 §8 隐患），客户端新版必须在服务端迁移之后发布（docs/21 §3.4 流程） |

### 3.5 ④ 排行榜表（leaderboard_snapshots）

```sql
CREATE TABLE leaderboard_snapshots (
  period      text NOT NULL CHECK (period IN ('daily','weekly','monthly','yearly')),  -- 0008：monthly/yearly 为 2026-10-10 扩档
  period_key  text NOT NULL,          -- daily: '2026-10-07'；weekly: ISO 周 '2026-W41'；monthly: '2026-10'；yearly: '2026'
  account_id  uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,

  PRIMARY KEY (period, period_key, account_id)

CREATE INDEX leaderboard_board_idx ON leaderboard_snapshots (period, period_key, rank);
```

| 设计点 | 说明 |
|---|---|
| 为什么快照而不是实时算 | 2C2G 的账单：一次日任务（cron 03:05，早于 03:17 备份）跑两条 `INSERT … SELECT … rank() OVER`；查询路径只剩一次索引扫描——代价 O(行数)，几十用户=几十行 |

| monthly / yearly（0008 新增） | 与 weekly 同款模式重铸（自然月 `YYYY-MM` / 自然年 `YYYY`），与前端五页签（日/周/月/年/总）对齐；alltime 仍不进快照 |
| 榜单入选条件 | `leaderboard_opt_in = true` 且 `disabled_at IS NULL`；本人名次不论是否 opt-in 都返回（只给本人看） |
| 并列裁决 | `rank()` 并列同名次；展示排序 `(score DESC, finished_at ASC)` 保证确定性 |

| 设计点 | 说明 |
|---|---|
| 为什么是流水表而不是"余额字段" | 双向同步、双设备汇合、幂等去重都需要**逐条身份**（`entry_key`）；余额永远可 SUM 重算 |
| 为什么不用 user_docs 纯文档同步 | 纯文档 CAS 给不出"幂等键去重 / 逐条日上限 / 重放防护"的落点；而跨设备共享钱包必须有中心闸。这不违反"服务端只做存储"——闸只是形状与配额校验，**零内容解释** |
| `uuidv7()` | PG18 内建，时间有序：ledger 行天然按插入顺序聚簇（官方 Release 18 新增项，已核实） |
| 容量 | 日活 10 人 × 100 条/日 ≈ 1000 条/日 ≈ 36 万条/年 ≈ 30~60MB/年（含索引）——2C2G/40G 盘余量充足；上限逼近时的归档策略列入未来的运维项，不在 v1 |

### 3.7 索引清单（够用即止）

| 索引 | 用途 |
|---|---|
| `user_days` PK (account_id, day_key) | 单账号趋势/streak |
| `user_stats` PK (account_id) | 总榜、面板 |
| `challenge_days` PK (account_id, date_key) | 结算幂等判定、单账号历史 |
| `challenge_days` (date_key) | 日榜聚合、每日任务 |
| `challenge_questions` PK + (date_key, question_key) | 台阶 3 预留：跨用户最常错题 |
| `leaderboard_snapshots` PK + (period, period_key, rank) | 榜面查询 + 本人名次 |
| `rice_ledger` PK (account_id, entry_key) | 幂等去重（唯一热路径） |
| `rice_ledger` (account_id, seq) | 下行增量拉取 |
| `rice_ledger` (account_id, day_key, kind) | 日上限校验 |

### 3.8 与 PG18 的适配说明

- 全部字段用 `timestamptz` / `date` / `smallint` / `jsonb` / `text[]`——PG18 全部内建，无扩展。
- `uuidv7()` 是 PG18 新增（时间有序 UUID）；主键仍用 `gen_random_uuid()` 风格的 uuid 的地方继承 docs/22。若镜像因任何原因退回 PG17，`uuidv7()` 需改应用层生成——**镜像锁 18 的前提下无此问题**（docs/22 §4.1 已锁）。
- 迁移与本地开发：本机免安装 PG18（docs/22 拍板 #16）跑同一份 DDL + 种坏值自检（`delta` 非法、`jsonb` 非对象、`correct > total`、`doc_type='challenge'` 未迁移时写入，逐条必须见红）。

### 4.1 注册 / 登录（沿用，摘要）

`POST /v1/auth/register` `{username, password}` → 201 `{token, expiresAt, absoluteExpiresAt, account}`；`POST /v1/auth/login` 同形（200）。失败统一 `BAD_CREDENTIALS`；限流见 docs/22 §5.4。**本文不改这两个端点的任何语义。**

### 4.2 同步拉 / 推（沿用，摘要）

`GET /v1/docs/:docType` → 200 `{docVer, revision, updatedAt, payload}` 或 404；`PUT /v1/docs/:docType` `{docVer, baseRevision, payload}` → 200 `{revision, docVer, updatedAt}`；409 `CONFLICT_STALE` / `DOC_VER_BLOCKED` 语义照 docs/22 §3.4/§4.3。**复习的跨设备能力完全建立在这两个端点上**（practice 文档），本文不新增复习专用端点。

### 4.3 POST `/v1/challenge/days` —— 提交挑战判分（核心新端点）

**请求体**（逐题事实；**不含客户端算的分数**。下面的 `questions` 只截 5 道演示形状——v3 起实际一批 = 整个已学题库，1..5000 道）：

```json
  "source": "local",
  "pickedLangs": ["c", "java"],
  "startedAt": "2026-10-07T12:01:03.000Z",
  "finishedAt": "2026-10-07T12:06:44.000Z",
  "questions": [
    { "key": "common-03:q2",        "lessonId": "common-03",       "qid": "q2",
      "lang": "common", "stage": 0, "type": "choice",   "difficulty": "easy",   "source": "local", "ok": true },

      "lang": "python", "stage": 1, "type": "fill",     "difficulty": "easy",   "source": "local", "ok": true },
    { "key": "c-stage1-02:q3",      "lessonId": "c-stage1-02",     "qid": "q3",
      "lang": "c",      "stage": 1, "type": "code",     "difficulty": "medium", "source": "local", "ok": false },
    { "key": "cpp-stage2-07:q5",    "lessonId": "cpp-stage2-07",   "qid": "q5",
      "lang": "cpp",    "stage": 2, "type": "codefill", "difficulty": "medium", "source": "local", "ok": true },

      "lang": "java",   "stage": 3, "type": "codefix",  "difficulty": "hard",   "source": "local", "ok": true }
  ]
}
```

**响应 200**：

```json
{
  "settled": true,
  "idempotent": false,
  "dateKey": "2026-10-07",
  "correct": 4,
  "total": 5,
  "score": 550,
  "scoreMax": 700,
  "flags": []
}
```

**`pickedLangs` 字段语义（2026-10-10 夜新增，可选）**：客户端在**开赛抽题那刻**记下勾选的语言（四门、去重、协议声明序），结算时随上行带出。规则：①**present** ⇒ 必须非空、⊆ 四门（'common' 拒）、无重复，否则 400 `VALIDATION_FAILED`；②**缺省** ⇒ legacy 语义，服务端**从题批派生**（questions 的 lang ∩ 四门、声明序；全 common 题批派生出空数组）——v2 老客户端与「全点掉只剩通用题」的合法开赛都走这条；③落库前统一归一为声明序（`['java','c']` → `['c','java']`），保证榜单并集与排序与上行顺序无关。**重放保护自动覆盖新字段**：幂等 200 的条件是「同 `submissionId` **且**同 payload hash」，hash 对原始请求体取（canonicalJson）——同 submissionId 下 pickedLangs 有任何不同（换集合、换顺序都算）即 hash 不同 → 409 `CHALLENGE_DUPLICATE`，库里保留首写值。

| 错误 | 码 | 场景 |
|---|---|---|
| 400 | `VALIDATION_FAILED` | 形状/值域错（submissionId/installId 非 UUID、dateKey 非真实日期、lang/type/difficulty/source 白名单、`pickedLangs` 值域〔非空/⊆四门/无重复〕、questions 1..CHALLENGE_RUN_MAX 与逐字段形状；另含服务端自查断言 scoreMax 越每日理论上限——§5.6/§7.2）。**结算窗口**：dateKey 与服务器日差**过去 >30 天或未来 >+1 天** → 400（message 含 `settle window`）+ log.warn（§8.3 恢复重放的服务端侧复核；30 天 = 客户端 `CHALLENGE_KEEP_DAYS` 滚动窗）。注：请求体**没有 total 字段**（服务端从 questions 数出 correct/total），旧列「total 与 questions 数不符」已于 2026-10-10 删除 |
| 401 | `UNAUTHENTICATED` / `TOKEN_EXPIRED` | 令牌问题（沿用） |
| 403 | `FORBIDDEN` | 已封禁 |
| 409 | **`CHALLENGE_DUPLICATE`**（新增码） | 该 `date_key` 已有**不同**结算（`details: {settledAt, score}`）；同 `submissionId` + 同 payload hash 重放 → 200 `idempotent:true` |
| 429 | `RATE_LIMITED` | 提交限流（§4.7）；带 `Retry-After` |
| 503 | `DB_UNAVAILABLE` | 沿用（附 `Retry-After`） |

**服务端处理链**：鉴权 → 形状校验（zod，含 `pickedLangs` 值域与结算窗口）→ 难度合法性复核（§7.2）→ `pickedLangs` 归一（present）/题批派生（缺省）→ 逐题计分（§5.2，服务端唯一算分者）→ 事务内 `INSERT challenge_days + 批量 INSERT challenge_questions`（逐题行**分批 1000 行/次**——2026-10-10 夜改，原一次性 5000 行 65,000 个绑定参数贴着 65,535 上限；PK 冲突 → 走幂等/重复判定）→ 更新 `user_days` → 返回。`correct` 由服务端从 `ok` 数出，杜绝"correct 与 ok 打架"。

### 4.4 GET `/v1/challenge/days`

`GET /v1/challenge/days?from=2026-09-08&to=2026-10-07&limit=30`（≤90）→

```json
{ "days": [
  { "dateKey": "2026-10-07", "source": "local", "correct": 4, "total": 5,
    "score": 550, "scoreMax": 700, "pickedLangs": ["c", "java"],
    "settledAt": "2026-10-07T12:06:45Z" }

```

用途：新设备登录后榜面/统计的快速对账、（可选）挑战页显示"云端分"。**不含逐题明细**（明细只在服务端统计里，客户端回顾读自己的 challenge.json）。

**默认窗口（2026-10-10 夜收口、当晚二次修订）**：两者都省略时 `to = 服务器日 + 1`、`from = 服务器日 − (limit−1)`——即默认窗 = `[服务器日−(limit−1), 服务器日+1]`。`from` 缺省的锚 = **`min(服务器日, to)`**：① `to` 缺省或 ≥ 服务器日时锚**服务器日**（若从 to 倒推，limit=1 时窗口会整体漂到「明天」，今天的档反而拉不到——测试抓到的原修法漏洞）；② 显式给了更早的 `to`（历史翻页：下一页 `to` = 上一页最老日 − 1）时锚 **`to`**，窗口 `[to−(limit−1), to]` 以 `to` 收尾（只锚服务器日曾把过去 to 顶成 `from > to` → 400，首页 200、第二页骤断——同晚对抗核验抓到的组合，契约本批裁定）。+1 天用于吸收客户端本地日与服务器 UTC 日的日差（客户端 dateKey 是**本地日**）。响应 `days[].pickedLangs` = 归一/派生后的**落库值**（§4.3）：派生只发生在结算写入口（缺省字段的 legacy 上行由写侧从题批派生），读侧一律返回库值——0010 前服务从未部署、无存量行，`'{}'` 读出去即空数组（「读侧派生」无实现、也不需要有）。

## 5. 挑战计分算法

### 5.1 三条原则

1. **判分唯一真源在客户端**：服务端收到的只有逐题 `ok` 布尔（`quiz.verdictAt()` 的产物，真跑题型读 `runResults`）与题目元数据；服务端**不重判、不知道题干**。
2. **算分唯一在服务端**：客户端**不上报分数**（本地 `score:{correct,total}` 保持原样、原语义）；服务端用自持权重表算加权分——权重表进 `protocol.ts`，客户端可离线预览同一份公式，但以服务端为准。
3. **整数算术**：全部用整数百分点（×100 存储），`Math.round` 四舍五入到整数分——无浮点、两端无 0.1 差。

### 5.2 公式（唯一版）

```
单题得分 points_i = ok_i ? round(100 × D_i × L_i ÷ 10000) : 0
日得分   score    = Σ points_i
本批满分 scoreMax = Σ (100 × D_i × L_i ÷ 10000 四舍五入)      （与 ok 无关）
```

- 基准 100 分/题（easy × 语言权重 100% = 100）；
- `D_i` = 难度权重（整数百分数）：`easy 100 / medium 150 / hard 200 / challenge 250`；
- `L_i` = 语言权重（整数百分数）：**2026-10-10 v3 起全部 100**（C/C++/Java/Python 同权）——公式与函数签名保留不动，但 L 退化为恒等，**单题得分只由难度决定**（easy 100 / medium 150 / hard 200 / challenge 250）。

### 5.3 权重取值表与理由（**2026-10-10 v3 主人令定稿**；原为待拍板 #1）

| 维度 | 取值 | 理由（口径对齐） |
|---|---|---|
| 难度 | easy 1.0 / medium 1.5 / hard 2.0 / challenge 2.5 | **直接对齐客户端难度规则**（`shared/difficulty.ts`）：choice/fill→easy、code/codefill→medium、codefix→stage≥3 hard、codewrite→hard；挑战靠显式字段。难度越高，答对的信息量越大 |
| 语言 | **common / python / java / c / cpp 全部 1.00**（v3 统一；v2 曾为 100/100/105/110/115%） | 主人令口径：**多语言不代表高分、专精一门也能霸榜**，核心是连对高难度题；语言只进统计与榜单筛选（`score_by_lang`），不参与计分。改一处 = protocol.ts 一处 + 服务端逐字节同步 |

不做时间加成、不做连续天数倍率——每一项都会引入新的可伪造输入（客户端改时钟即可），列进"不做"（§8.5）。

### 5.4 与客户端判分规则的四个对齐点（防漂移）

| # | 对齐点 | 落地 |
|---|---|---|
| 1 | 对错来源 | 挑战记账沿用 `quiz.verdictAt()`（未作答 = false；真跑题型读 `runResults`）——服务端拿到的 ok 与结果页显示的一致 |
| 2 | 难度来源 | 客户端上报 `resolveDifficulty()` 的结果；服务端按 §7.2 复核（不是重算） |
| 3 | 不重判 | 服务端无内容包，**永不重判**；未来若要重判（台阶 3 的防作弊终极形态）必须先"内容上云"——明确列不做（§8.5） |
| 4 | 本地语义不动 | `challenge.json` 的 `score:{correct,total}`、30 天窗口、回顾页全部零改动；加权分只活在云端与本设计的新字段里 |

### 5.5 带数字算例

下表以 5 道题演示加权算术（含跨语言、跨难度、一道答错；v3 起实际一批 = 整个已学题库，题量 1..5000——本表只演示算术，不模拟「答错即停」的停局时序）：

| # | 语言 | 阶段 | 题型 | 难度（客户端解析） | ok | D | L | 计算 | points |
|---|---|---|---|---|---|---|---|---|---|
| 1 | common | 0 | choice | easy | ✔ | 100 | 100 | 100×100×100÷10000 | **100** |
| 2 | python | 1 | fill | easy | ✔ | 100 | 100 | 同左 | **100** |
| 3 | c | 1 | code | medium | ✘ | 150 | 100 | ok=false | **0** |
| 4 | cpp | 2 | codefill | medium | ✔ | 150 | 100 | 100×150×100÷10000=150 | **150** |
| 5 | java | 3 | codefix | hard | ✔ | 200 | 100 | 100×200×100÷10000=200 | **200** |

- **日得分 = 100+100+0+150+200 = 550 分**
- **本批满分 = 100+100+150+150+200 = 700 分**（第 3 题若答对是 150）
- 结算响应即 `{"score":550, "scoreMax":700, "correct":4, "total":5}`；本地挑战页仍显示 4/5（本地语义零改动）。

### 5.6 上限、多设备与截断

- **单日理论上限（纯护栏，不是产品规则）**：v3 起 `CHALLENGE_RUN_MAX = 5000` 是**健全性上界**（全库 4169 题 + AI 段 20 道 = 最坏 4189，之上留余量），不是"每天最多 5000 题"；分数护栏 `DAILY_SCORE_MAX = 5000 × 250 = **1,250,000 分**`（只活在应用层——DB 对 `score` 只 CHECK >= 0）。沿革：1440（0003，5 题×288）→ 5760（0007，20 题×288）→ 1,250,000（0009/v3，难度分制 250/题）。服务端校验 `score ≤ scoreMax`（批内自洽）+ `scoreMax ≤ DAILY_SCORE_MAX`（越界 → 400 拒结算 + 审计）。榜单不存在"分数窗口"问题——上限天然可判定。
- **多设备同日**：`PK (account_id, date_key)`，**先到先得**；第二台设备提交 → 409 `CHALLENGE_DUPLICATE`（响应带已结算分数），客户端保留本地展示、榜面归第一台。这是拍板项 #4 的建议值。
- **总榜口径**：`total_score = Σ 日结算分`（不是正确率、不是最高单日）——单调、可审计、无归一化空间。

## 6. 大白饭奖励同步与防作弊

> 【修订标注】本文修订 docs/25 §3.6 指定的流程（原要求走「加一个新同步对象」）：改独立账本表 + 专用端点，理由见本节；回填 docs/25 §3.6 时须显式改写。

### 6.1 设计原则与账本模型

- **本地第一真源不变**：断网照赚照花；云同步失败静默降级（只影响跨设备对齐与榜面）。
- **服务端角色 = 镜像账 + 闸**：`rice_ledger` 是"被接受的条目集合"，余额是它的 SUM；服务端**不发饭**（不知道对错）、**不消费**（消费在客户端发生）、**不惩罚**（v1 不清零）。
- **账本模型（v5，客户端侧）**——【回填 · 2026-10-11】**已全部落地**（P10.5 内核 + P10.6 接线）：
  - `pet.json` 继续是**设备显示状态**（satiety/位置/体型/情绪；`rice` 字段改为"当前盒账本余额的镜像"）；
  - 新增**账本文件**（跟随盒：客人盒在根目录、账号盒进 `accounts/<id>/`）：`{version, entries:[…], localSeq, appliedServerSeq}`——每条 = `{entryKey, kind, delta, dayKey, at, ref}`；【回填】文件实名 **`rice-ledger.json`**（与 pet.json / profile.json 同级——`.sync/` 只放同步元数据，账本是真数据），纯函数核心 = `src/shared/cloud/rice-ledger.ts`（零 I/O、三端可载，条目 `cloud` 三态见 §6.5）；
  - 发放/消费的**唯一写口仍为主进程**（沿用 pet store 的漏斗纪律）；余额 = `clamp(Σentries, 0, 999)`。【回填】写口 = `src/main/cloud/rice-journal.ts` 的 `record()`——任何改饭的行为（喂饭/学习奖/跑步奖/签到）经它记一条账，并拿返回值（新余额镜像）覆盖 `pet.json.rice`；brain 自算的数一律被覆盖。
  - 【补 · 2026-10-11，实现期定稿、草案未写的两条本地规则】：
    - **genesis 条目（升级首启的存量饭）**：首次建账时 `pet.json` 已有 N 碗（N>0）→ 记一条 `{entryKey:'<installId>:0', kind:'adopt', delta:N, cloud:'rejected', ref:{installId, carried:N}}`。`cloud:'rejected'` 即「**永不上行**」（存量饭是设备本地事实，不属账号流水；不发明第四态）；收编查重必须按 `!ref.carried` 过滤（收编的 adopt 标记没有 carried）。已知代价（接受）：同账号第二台设备的镜像缺第一台存量；999 饱和时有一次「免费喂饭」空间（第一次真实消费后对齐）。
    - **账本坏档处置**：主档 + `.bak` 都判坏 → 坏档副本留 `rice-ledger.bad-<ms>.json`（取证）、出声、**按 genesis 路径重建**（carriedRice = 此刻 `pet.json.rice`）——优先保住用户看得见的余额。已知代价（接受）：若此刻已登录且服务端有流水，水位归零后的全量重拉会把服务端部分再记一遍（余额虚高、被 999 钳住，直到消费磨回）——错误路径的错误路径，优先保余额、优先出声。
- **收编**：登录时把客人盒账本复制合并进账号账本（**不移动**，与 docs/21 §8.4 的档案收编同款）；另生成一条 `kind='adopt'` 条目——**`delta` 恒 0**，仅作「来自客人档案」的来源标记（`ref={installId}`，仍须为最早条目，每 installId 只允许一次）；余额由复制后的 `clamp(Σentries, 0, 999)` 自然重算，让"我攒的饭没有消失"成为事实而不是口头承诺。

### 6.2 流水条目形状与 delta 白名单

| kind | delta | 客户端依据（常量真源） | 服务端校验 |
|---|---|---|---|
| adopt | **恒 0**（来源标记，不携带余额） | 首登收编 | 每 (account, installId) 仅一条；必须是最早条目；delta 必须 == 0 |
| lesson | **+2** | `PET_REWARD_RICE.lesson` | delta 必须 == 2，且 ref.lessonId 形状合法 |
| review | **+2** | `PET_REWARD_RICE.review` | delta 必须 == 2 |
| answer | **+1** | `PET_REWARD_RICE.answer`（一局一题一次） | delta 必须 == 1 |
| run | **+1** | `PET_RUN_REWARD_RICE`（own+指纹+日上限 10） | delta 必须 == 1；ref.fingerprint 必须匹配 `shared/code-hash` 形状（`长度36:FNV16`） |
| feed | **-1** | 喂饭固定 -1（`feedPet` 里的字面量；【修正 · 2026-10-10 夜】原写 `PET_FEED_GAIN`——那是**饱食度**增益 +20，不是饭依据） | delta 必须 == -1 |
| chase | **-1**（冻结值） | 【修正 · 2026-10-10 夜】**v1 客户端不上行**：「跑腿」的真实实现是 `exertPet(PET_CHASE_COST)`——扣**饱食度**，与饭流水无关；原写「依据 = `PET_CHASE_COST`」是把饱食度常量错当饭依据 | delta 必须 == -1（白名单保留、服务端宽容收；客户端没有合法来源） |
| chat | **-2**（冻结值） | 【修正 · 2026-10-10 夜】同上：聊天（思考）扣**饱食度** `exertPet(PET_CHAT_COST)`，不进饭账本；v1 从不上行 | delta 必须 == -2（同上） |
| checkin | **+2** | `PET_REWARD_RICE.checkin`（= `PET_CHECKIN_RICE`；每日签到，连签不递增）——【补 · 2026-10-10 夜】原表漏了它；账本模型下 pet.json.rice 是 `clamp(Σentries)` 的镜像，**漏登记的加饭会被下一次镜像重算抹掉**，故协议与 DB CHECK 同批补（迁移 `0011_rice_checkin_kind.sql`） | delta 必须 == 2；无 ref 要求 |

**delta 白名单是本设计的防伪造地基**：条目形状固定，伪造者能"多报几条"，但不能"一条报 999"——把作弊面从"任意数值"压缩到"条目数量"，再由 §6.4 的日上限兜住。白名单进 `protocol.ts`（两端逐字节一致；客户端常量表任何改动都将触发协议版本 bump）。

### 6.3 服务端结算设计

1. **入账**：`POST /rice/entries` 逐条校验 → `INSERT … ON CONFLICT (account_id, entry_key) DO NOTHING` → 插成功的记 `accepted`；冲突且内容一致记 `duplicated`；日上限拦截记 `rejected[]`（**不是整批失败**，HTTP 仍 200）。
2. **余额**：事务内 `UPDATE rice_balances SET balance = clamp(balance + Σdeltas, 0, 999)`；`balance` 有 CHECK 上界 999（与客户端 `PET_RICE_MAX` 同值——上限对齐在 protocol.ts）。
3. **下行**：`GET /rice/entries?since=<seq>` 增量拉取；客户端 apply 时同样按 `entryKey` 去重，`appliedServerSeq` 落盘做断点。
4. **一致性**：`rice_balances` 任何时刻可用 `SELECT SUM(delta) FROM rice_ledger` 全量重算；每日任务校验一次（不一致 → 重算覆盖 + 审计行）。
5. **不做**：服务端不产生任何新消费（没有"服务端扣饭"的场景）；v1 不做负余额惩罚（clamp 到 0 即止，双花损失由平台承担——诚实且便宜）。

### 6.4 防刷分机制（四层）

| 层 | 机制 | 具体规则 | 触发动作 |
|---|---|---|---|
| ① 幂等 | `entry_key` 唯一 | `PK (account_id, entry_key)`；键格式 `${installId}:${localSeq}`（installId 来自 P10.1 `device.json`） | 重放同内容 → 200 计 `duplicated`；同键不同内容 → 409 `ENTRY_CONFLICT` |
| ② 限速 | 批量频率 + 日条数 | 6 次/时/账号；≤200 条/次；≤1000 条/日 | 429 `RATE_LIMITED`（带 Retry-After，客户端只退避不惊扰） |
| ③ 重放防护 | 记账窗口 + 单调序 | `dayKey` 与服务器日差 >1 天 → 拒（时区容差）；同 installId 的 `at` 显著倒退或超前 >10 分钟 → 记 flag 照收（不罚诚实用户）。**同款窗口的另一半在挑战侧（§4.3）**：结算 dateKey 过去 ≤30 天 / 未来 ≤+1 天，超窗 400——两窗口同属重放防护，未来宽容方向一致（都只宽放 1 天吸收 UTC 日差）；过去方向不同宽（流水是即时动作、挑战有离线补结算队列 ≤30 天，§8.3） | 拒 / flag |
| ④ 异常检测（按 kind 日上限 + 交叉核对） | 见下表 | 超限条目进 `rejected[]`，**客户端标"未入云"（不静默丢弃）** | 拒 / flag |

**kind 日上限（建议值，env 可调；超限条目的拒绝码 = `OVER_DAILY_CAP`，见 §4.7）**：

| kind | 上限/日 | 对齐依据 |
|---|---|---|
| lesson | 20 | 10 课/日（狂学档）×2 碗；终身另有硬顶：learned ≤ 244 课 → ≤488 碗（【计数修正 · 2026-10-10 夜】原写 229/458——那是 3.0 时代课数，现 content/ = 244 课，见 §8.5） |
| review | 20 | 复习不限次数但全对才有；20 次/日已远超真实 |
| answer | 300 | 一局一题发一次；v3 全池口径下局长不固定（可达数千题）——300 是防批量闸的保守日值（env 可调） |
| run | **10** | 直接抄客户端 `PET_RUN_REWARD_DAILY_MAX` |
| feed | 30 | 有效喂饭受饱食度上限约束（5 次/日左右），30 是防抖余量 |
| chase | 300 | 冻结值（【修正 · 2026-10-10 夜】v1 客户端不上行，无客户端依据；原「30s 冷却理论值」按饱食度口径写就） |

### 6.5 与客户端本地账的合并策略

| 场景 | 规则 | 说明 |
|---|---|---|
| 常态 | **并集 + `entry_key` 去重**；余额 = `clamp(Σ, 0, 999)` | 两端同式；任一侧重放/重复推送都收敛 |
| 上行 | 【回填 · 2026-10-11】批次 = 账本里 `cloud === 'pending'` 的条目（`pendingEntries`，按插入序取前 N）——**`cloud` 字段缺席 = 已入云、永不重推**（含全部下行条目与 genesis）；被 `rejected[]` 的条目**保留在本地账**（标"未入云"徽标，账户面板可见，**不重试**——与草案"`localSeq` 之后的条目批量推"等价，但对"被拒条目"不再反复上推） | 绝不因云端拒收而回滚本地行为（离线优先红线） |
| 下行 | 云端 `seq > appliedServerSeq` 的条目 apply 进本地账（去重后计数） | 另一台设备赚的饭/花的饭在下一轮合并后到达本机并显示 |
| 双设备离线双花（已知无解） | 合并方向：服务端 `clamp(balance + Σ, 0, 999)` 先落地；本地下一轮 pull 后跟随服务端账（余额可能减少——**如实显示**，差额只在账户面板出现，主界面静默） | 无中心锁的分布式账本固有代价；v1 接受（几十用户、非经济系统） |
| 上限 | 两端同为 999（客户端 `PET_RICE_MAX`）；服务端 CHECK 同值 | 数值对齐进 protocol.ts |

**算例（合并收敛演示）**：

| 时刻 | 设备 A（本地账） | 设备 B（本地账） | 服务端 |
|---|---|---|---|
| T1 | 余额 40 | 余额 40（同一账号旧状态） | 余额 40 |
| T2 A 赚 6（离线） | 46 | 40 | 40 |
| T3 B 花 2（离线） | 46 | 38 | 40 |
| T4 A 先上行 | 46（6 条 accepted） | 38 | 46 |
| T5 B 上行 + 下行 | 46 | 38-2+6=**减记**：B 上行 1 条 → 服务端 44，B pull 到 A 的 6 条 → B = 38 + 6 = 44 | 44 |

两端在 T6 全部收敛到 44（= 40 + 6 − 2）。**余额不是 max 也不是覆盖，是流水并集的算术结果**。

### 6.6 明确不做

- 服务端不重跑代码/不判题（无内容包）；不做行为风控模型（v1 只有规则表）；不做惩罚性清零；不做"饭市"（兑换/交易）；不做实时推送余额（拉取模式，同 docs/21 §11）。

## 7. 题目难度分级在 API 中的体现

### 7.1 提交字段（逐题元数据与难度值域）

| 字段 | 值域 | 来源（客户端） | 服务端处置 |
|---|---|---|---|
| `lang` | common / c / cpp / java / python | 宿主课的 lang | 白名单校验；v3 起不参与计分（语言权重统一 100），只进统计与榜单筛选（`score_by_lang`） |
| `stage` | 0~3 | 宿主课的阶段 | 白名单校验；参与默认难度推导（§7.4） |
| `type` | 六题型 | 题目对象 | 白名单校验；参与默认难度推导 |
| `difficulty` | easy / medium / hard / challenge | `resolveDifficulty(q, stage)`（显式字段覆盖一切） | 复核（§7.2）；计分难度权重 |
| `ok` | boolean | `quiz.verdictAt()` | 计分唯一输入 |
| `source` | local / ai | 批次来源 | challenge 难度合法性检查（§7.2）、统计区分 |

### 7.2 服务端对 difficulty 的复核（防"全报挑战题"）

| 上报值 | 服务端规则 | 计分 |
|---|---|---|
| `challenge` | 仅当 `type ∈ {codefix, codewrite}` 且 `source='local'` 时合法（对齐客户端现状：24 道挑战题全是精选模板 codefix/codewrite） | 合法 → D=250；否则**与下行同式取低**——按默认规则表推导后取较低者计分（challenge 恒为最高档，实际即按诚实推导档计：choice 谎报按 easy 计）并落 `flags:['difficulty_downgraded']` |
| easy/medium/hard | 服务端按 protocol.ts 的**默认规则表**（type+stage → 默认难度，与 `shared/difficulty.ts` 同一张）独立推导，取两者中**较低**者计分 | 高报被推导值压回（防刷），低报不吃亏（保守方向） |
| 无上报 | 整条提交拒（`VALIDATION_FAILED`） | — |

**诚实边界**：客户端如果绕过 UI 直接构造请求，仍可上报"合法的 hard codefix"抬高分数——复核只能挡"形态不合法的抬分"。真正的证明需要服务端重判，列不做（§8.5）。

### 7.3 查询参数与存储（筛选在哪生效）

- **排行榜**：`?lang=` 与 `?difficulty=` 只改变**分数口径**（对 `score_by_lang` / `score_by_difficulty` 两个 jsonb 列求和），不产生第二张榜、不加表。
- **挑战历史**：`GET /v1/challenge/days` 返回每日汇总；逐题明细不出 API（只进统计），避免服务端暴露"全站答题明细"这一无谓面。
- **落库**：`challenge_questions.difficulty` 建普通列 + `(date_key, question_key)` 索引——"全站最常错题（按难度/语言切）"这类查询（docs/22 §4.8 台阶 3 的方向）从此有数据可用，且不需要现在建六表。

### 7.4 服务端不"重算"而是"复核"的理由

- 客户端存在**显式 difficulty 覆盖字段**（挑战题靠它），服务端无法区分"显式覆盖"与"谎报"——所以只做白名单 + challenge 合法性 + 取低计分，不假装能算准。
- 默认规则表在 `protocol.ts` 里放一份**副本**（服务端独立包，不能 import 客户端 `difficulty.ts`）；正确性由客户端单测保证：`difficulty.ts` 的规则表与 protocol.ts 副本**逐项等价断言**（种坏值：改一处必须见红），对齐 docs/22 §3.3 的"协议真源 + 闸门"纪律。
- 同理，`protocol.ts` 里的 **rice 常量副本**（`PET_RICE_MAX` / `PET_REWARD_RICE`（含 checkin）/ `PET_RUN_REWARD_RICE`——见 §6.2 的 delta 白名单）须与 `src/shared/pet.ts` **逐项等价单测**（同款：种坏值，改一处必须见红）。【修正 · 2026-10-10 夜】原列 `PET_FEED_GAIN`/`PET_CHASE_COST`/`PET_CHAT_COST`——三者全是**饱食度**常量、不是饭依据（协议侧对应 delta 为字面量或冻结值），不得再拿它们对拍。

## 8. 离线/断网降级

### 8.1 总口径（逐字继承）

**本地第一真源、云是副本**（docs/21 §2.1）；同步失败**永远静默降级**——不报错、不阻塞、不弹失败窗（docs/25 §1.5-②）；429/503 在客户端只是退避信号、不算错误、不惊扰用户（docs/22 §5.4）。

### 8.2 离线时逐功能行为

| 功能 | 离线行为 |
|---|---|
| 每日挑战（抽题/答题/判分/回顾） | **完整可用**（本地池 + AI 失败静默退回本地）；结算入待结算队列 |
| 每日复习（组卷/作答/全对发图发饭） | **完整可用**（权重真源 = 本地 practice.json） |
| 大白饭（赚/花） | **完整可用**（本地账本照记照花） |
| 排行榜 | 显示上次拉取的快照 + "截至 X 时间"标注；无快照则显示空态（不摆假数据） |
| 题面/内容/IDE/桌宠 | 与今天完全一致（本设计零触碰） |

### 8.3 恢复后的合并与退避

- 待结算队列（【回填 · 2026-10-11，P10.6 ① 定死】落点 = **独立文件 `<盒>/.sync/pending-ops.json`**（不并入 `state.json`：队列有自己的独立原子读写口，混进状态档等于「落盘一条结算」也要重写整个同步状态）；【回填】实现上限 **60 条**（`SETTLE_QUEUE_MAX`，按 `dateKey` 去重——同一天只排一条；队满丢**最老的**并出声；草案 90 条改定 60 的依据 = 注释口径"约两个月的离线积压"，服务端结算窗只有 30 天，更老的本来也发不出去））承载两类：待结算挑战（客户端 30 天滚动窗口内的批次；**服务端同宽复核**——过去 ≤30 天 / 未来 ≤+1 天，超窗 400 `VALIDATION_FAILED`〔§4.3〕，客户端收到即标记该条「已过期、不再重试」并如实展示）与待上行流水（≤1000 条，超限丢最老的**并如实报数**——待拍板项并入 #3）。
- 【补 · 2026-10-11，P10.6 ⑤】「收工 → 入队落盘」之间的崩溃窗口由**「已提交」标记**闭环：`ChallengeDay.submittedAt` **只在主进程确认入队之后**写（写早 = 这一天被误判已交、永久不再补交——主进程回话 `queued: true/false` 都算交付，形状不对不写）；每次读档用 `challengeToday.unsent`（`finishedAt != null && submittedAt == null`，dateKey 升序）自动补交，`format < 2` 的老档不补（结算负载形状对不上）。在飞的补交按 dateKey 去重（两个并发读档只发一包）。
- 重放顺序：先流水（幂等、只增）→ 再挑战结算（可能撞 `CHALLENGE_DUPLICATE`，按 §8.4 处理）→ 最后拉榜单/汇总。
- 退避节奏：1 → 5 → 15 → 60 分钟（docs/21 §8.2 同款），徽章状态 `offline/error` 两档区分。
- **幂等 = 重放的充分依据**：挑战靠 `submissionId`，流水靠 `entry_key`——断点续传不需要 outbox 事务语义（与 docs/21 §8.2"无 outbox"同一论证）。

### 8.4 冲突处理表

| 冲突 | 裁决 | 用户可见性 |
|---|---|---|
| 同 `submissionId` 重放（同 hash） | 200 `idempotent` | 无 |
| 同 `date_key` 第二台设备提交 | 409 `CHALLENGE_DUPLICATE`；本机批次标"已在他机结算"，本地挑战页保留 | 挑战页一行提示（copy.ts），不弹窗 |
| 同 `entry_key` 不同内容 | 409 `ENTRY_CONFLICT`；该条标"未入云" | 账户面板明细可见 |
| 流水双花（离线） | 服务端 clamp 先落地，本地 pull 后跟随 | 账户面板可见差额；主界面静默 |
| 榜单 stale | 拉取失败保留旧快照 + 时间标注 | 徽章 |

### 8.5 明确不做（边界清单）

- **服务端重放判分 / 内容上云**（防作弊的终极形态，需把 244 课/4169 题上云 + 服务端跑判分——与"服务端零内容"总原则冲突，且 2C2G 扛不起代码真跑）；【计数修正 · 2026-10-10 夜】原写 229 课/4047 题：题数以 v3 全库口径 **4169 题**为准（§5.6 同值），课数以 content/ 现况 **244 课**为准（bundle 与 syllabus 三路同值；2026-10-10 报告第七节「§8.5 与实现的口径差」登记项的写回收口）；
- **实时推送 / 长连接**（docs/21 §11 原判）；
- **跨设备复习组卷一致性**（抽样天然随机，两端题目不同是特性不是 bug）；
- **离线期间的"补签"**（断几天就是断几天，streak 不追溯——反作弊与诚实）；
- **把未被服务端接受的条目当丢失**（不许静默；必须本地保留 + 可见徽标）；
- **AI 题服务端复核**（不可能——题目由用户自带 Key 现场生成，服务端没有也不该有）。

## 11. 诚实边界与风险（写在最后，防止被当成承诺）

1. **不可证明性**：客户端判分的世界，服务端无法证明"这局是真的"；本设计挡批量/重放/抬权重，不挡单机改内存。谁对此不满意，唯一的路是"内容上云 + 服务端重判"——那是另一个量级的工程（与分享版/离线优先也冲突）。
2. **时钟**：dateKey 是客户端本地日；结算窗口 ±1 天 + flag 是"接受不完美但可审计"的方案，不做 NTP 对齐（不值得）。
3. **双花**：大白饭在无中心锁时允许多设备离线双花，平台吃亏（clamp 到 0），不追责不惩罚。
4. **2C2G 的余量**：所有估算都在"几十用户"量级；用户数上一个量级（>几百）时，排行榜快照与流水归档要重新算账（触发条件写在这里，别当没看见）。
5. **本文与 S6 的关系**：TLS 已完成（S6 于 2026-10-07 配通）不影响本文任何设计；M1 之后的实测同样走 https 客户端校验——与 docs/22 拍板 #4 的停止项对应（停止项 1 签发、3 三客户端校验已达标；停止项 2 续期观察进行中，预计 3–5 天）。
6. **回填责任**：本草案定稿后需回填的位置——docs/22 §3.4（端点 15→21）/§3.5（错误码 16→19）/§5.4（限流三行）、docs/21 §11（排行榜从"不做"改为"见 docs/26"）、docs/21 §8.4（回填时写入「challenge 不入收编」的归属句——docs/22 §8.2⑤ 要求写死）、docs/25 §3.5/§3.6（现状改为"设计见 docs/26"）。**本文不动它们**（先拍板，后回填）。
