## 7. ⚠️ 硬性注意事项（都是试错换来的结论）

### 7.1 必须 512 × 512
用 768 出图**头身比会崩成「大头娃娃」** —— LoRA 是在 512 上训练的，**训练尺寸必须等于出图尺寸**。

> **批量的秘诀是多抽**：要 30 张就生成 90 张（合格率约 1/3 ~ 1/2）。出图很快（90 张约 3 分钟），**瓶颈在审图不在生成**。

### 7.2 禁用高清修复（hires fix）
放大后重画会把平涂画风变成**油画感、画面崩坏**。直接出 512 最还原。

### 7.3 不要加 `chibi`
历史实测：`chibi` 与 `animal_ears` 同现时会出现**复耳**（鲸鱼耳 + 普通耳朵并存）。

### 7.4 `animal_ears` 现在必须写
早年曾因「写了必复耳」被列为禁词，**后查明那是极短提示词下的结论**（当时没有发色 / 服装 / `full_body` 等语境），属过度推广。
用**完整配方**实测 80 张（v1 / v2 各 40 张），**复耳 0 张，禁令已撤销**。若 v1 复耳率仍是老估的 1/8，40 张全干净的概率仅约 0.5%，故「必复耳」不成立。

> ⚠️ **但注意**：0/40 的 95% 统计上界仍有约 **7%**，**不等于零**，产图时仍需留意耳部。

### 7.5 `smug` 必须在正面
放进负面会把这个表情**彻底压掉**，是方向性错误；负面只留「凶」的部分。

### 7.6 围裙上的鲸鱼 logo 在 512 全身图里只有约 30 px
SD1.5 画不干净，**已接受，不必再优化**。

### 7.7 不要混用 QteaMix 版配方
QteaMix 底模版本与 Counterfeit 版本**互为反面**（QteaMix 不写 `animal_ears` 就会变兔耳），**两套配方各自专用**。

### 7.8 8 GB 显存提示
训练时峰值 7.0 / 8.1 GB，**训练期间不要同时出图**。

### 7.9 各姿态的命中率天生不一样，别用同一个及格线去要求

2026-09-14 实测（每姿态 30 张候选、人工挑选）：

| 姿态 | 30 张里挑得出 | 命中率 |
|---|---|---|
| busy / yay / soothe | 10 ~ 11 张 | ≈ 35% |
| milestone | 4 张 | ≈ 13% |

**milestone 明显更难出，原因是它的要求自相矛盾**：表情要「炸」（`:d` + `open mouth` + `sparkling eyes`），
构图又要「不散」（`full_body`），SD1.5 一接到高能量表情就容易把人物画跑偏。

⚠️ **不要因此把「动作幅度」当成判据**。第二批 30 张按动作分 10 组（每组 3 张）的实测结果是：

- 中奖的 4 张全部落在**新写的**动作上，每组恰好中 1 张（即「每 3 张中 1 张」的常态手气）
- **大幅度的组 0 中，但小幅度的组也 0 中** —— 成败与幅度看不出相关性

真正稳的做法只有两条：
1. **多抽**（这是唯一被反复验证有效的手段）
2. 让动作**在身体附近有个锚点**（抱鲸鱼 / 捧鱼 / 举手比心 / 双手捧脸），比纯姿态描述（`jumping` / `waving`）稳得多

### 8.5 透明底图生产决策（2026-09-12：**暂缓批量抠图**）

**决策**：**暂停**把 42 张白底成品图批量转透明底这件事。

**原因**：**UI 需求尚未确定** —— 还不知道每张图要贴在哪个位置、要多大、要什么姿态。此时批量抠图，很可能抠完发现「要的那张没抠、抠好的用不上」，白白浪费生产精力（抠图不是难点，**选图才是**）。

```
LoRA 按指定姿态/表情出图（512×512，白底）
     ↓
ComfyUI 的 RemoveBackground_SET 节点 + BiRefNet 模型
     ↓

```

**为什么这样更好**：
- 只生产真正要用的图，**绝不浪费一张图的生产精力**
- BiRefNet 直出比「先出白底再抠」少一道工序，边缘质量更可控
- 需求明确后可以精确指定表情 / 动作 / 构图，而不是从 42 张现成的里凑

- ComfyUI 已装 `ComfyUI-RemoveBackground_SET` 自定义节点 ✅（已确认在 `<ComfyUI>\custom_nodes\`）
- **BiRefNet 模型文件 ✅ 已就位（2026-09-13）** —— 见下方「§8.5.1 落地时踩的坑」
- 图片需求清单 ✅ **已完成** → [13-图片资产需求清单.md](./13-图片资产需求清单.md)（2026-09-13）

### 8.5.1 落地时踩的坑（2026-09-13 实测，**照抄别改**）

**① 节点不叫 `RemoveBackground_SET`。** 本文档早先写的名字是错的，实际节点是：

| 节点 | 作用 |
|---|---|
| `LoadRembgByBiRefNetModel_SET` | 加载模型（先加载，再抠图） |
| `RembgByBiRefNet_SET` | 真正抠图 |

**② 模型只能从节点自带的清单里选，文件名是算出来的。** 节点源码里
`fname = m.file_name + os.path.splitext(m.url)[1]` —— 也就是说文件**必须叫**
`General-reso_512.safetensors`。放错名字节点会当它不存在。

选的是 **BiRefNet General (LR=512)** = `ZhengPeng7/BiRefNet_512x512`（424 MiB）——
**它训练时用的就是 512×512，和我们出图规格一模一样**，这是选它而不是选别的分辨率的唯一理由。
模型放 `<ComfyUI>\models\BiRefNet\`。下载走 hf-mirror（HF 直连在本网络下不可靠）。

**③ `device` 参数大小写敏感。** 写 `'auto'` 会被拒（合法值只有 `AUTO` / `cpu` / `cuda` / `cuda:0`），
报错长这样：`value_not_in_list ... device: 'auto' not in [...]`。

**④ `dtype` 参数必须显式传，不能省。** 这是**节点自己的 bug**：

```python
def execute(cls, model, device, dtype="auto", ...):
    target_dtype = arch.dtype if dtype == "AUTO" else TORCH_DTYPE[dtype]
```

默认值是小写 `"auto"`，比较时用的是大写 `"AUTO"` —— **小写永远匹配不上，于是走到
`TORCH_DTYPE["auto"]` 直接 KeyError。** 所以必须显式传 `dtype='float32'`
（合法值只有 `float16` / `float32` / `bfloat16`）。

**⑤ 抠图不必单独跑一遍。** VAEDecode 的输出接两个分支就行：一个 SaveImage 存白底原图，
一个接 `RembgByBiRefNet_SET` → SaveImage 存透明底。**一次生成同时拿到两张**，省一半时间。

**⑥ 量出来的边缘质量**（3 秒/张，512×512）：39.7% 全透明、25.7% 全不透明，
**90,729 个半透明像素** —— 是真的抗锯齿过渡，不是硬切的二值蒙版。

> 📐 **这套参数已经写死在** `scripts/图片工具/gen_mascot.py` 的 `REMBG_*` 常量里，
> 上面这几条是给「将来要重新搭节点」时看的，不是每次出图都要手动填一遍。

> 🔓 **阻塞已解除（2026-09-13）**：上述「UI 需求未确定」这一条已经补齐（见 docs/13），
> 位置、尺寸、姿态、构图全部定死。**§8.5 的「暂缓」结论仍然有效，但暂缓的对象变了** ——
> 不是「不知道要什么」（现在知道），而是**按 docs/13 的规格生产新图，而不是把现有 42 张白底图拿去抠**。
> 落位点全在卡片底/彩色底上，白底图贴上去就是一个白方块，所以那 42 张直接抠出来也不能用。

> 附带结论：当前 42 张白底图**保持白底状态不动**，不预先抠图。它们仍可用于需要白底方图的场景（头像、贴纸、占位图）。

> ⚠️ **两个写 .bat 的坑（都实测踩过）**
> 1. **`rem` 注释行里也不能出现中文。** cmd.exe 按 OEM 代码页（中文 Windows 是 GBK）读 `.bat` 的**内容**，
>    UTF-8 中文会变成乱码并**把那一行拆成好几条命令**。中文提示一律交给 Python 打印（Python 自己管 stdout 编码）。
>    —— 文件名可以是中文，那存在目录项里，不受影响。
> 2. **行尾必须是 CRLF。** 只写 LF 的话 cmd.exe 会**吃掉每一行的第一个字符**：
>    `rem Double-click...` 变成 `em ouble-click...`，双击后先糊一屏「不是内部或外部命令」才轮到正经输出。

## 10. 标准生产流程（SOP）

### 10.1 ⭐ 现在用这条（按 docs/13 工单出图）

```
1. 确认 ComfyUI 已启动（http://127.0.0.1:8188）
2. 双击桌面「一键出图」
   —— 它自己会：读工单 → 按 3 倍过采样出图 → 直出透明底 → 拼好对比图并弹出来
3. 在对比图上挑图（每张左上角有编号，报编号就行）
4. 把挑中的编号填进 --apply，定稿搬进 assets/mascot/（见 §10.2）
```

**「3 倍过采样」是什么意思**：docs/13 要 47 张，脚本会出 **141 张**候选（每个动作抽 3 个种子）。
对比图里同一动作的 3 张是**挨着的**，所以你是「每个动作三选一」，不是从 141 张里大海捞针。

**中途关了不要紧**：再跑一次会跳过已经出了的，接着往下跑（判定键见 §9.1）。

### 10.2 定稿：把挑中的编号搬成正式图

```bash
python scripts/图片工具/gen_mascot.py --apply busy=1,4,7 --apply yay=2,5,9
# 不带 = 编号的写法 = 整个姿态所有候选都搬（单张的姿态用这个）
python scripts/图片工具/gen_mascot.py --apply expect --apply proud
```

**编号重排是自动的**：你挑 `busy=1,4,7`，到了 `assets/mascot/` 里会自动叫
`busy_01.png` / `busy_02.png` / `busy_03.png` —— **你不需要手动改名**。

### 10.3 补图：同一个姿态要**追加**，一律用 `--add`

```bash
python scripts/图片工具/gen_mascot.py --add milestone=13,16,21,24
```

⚠️ **别用 `--apply` 补图** —— `--apply` 的编号是**从 `_01` 重排**的，它做的是「整组替换」。
已经定稿 4 张 milestone 之后再报 4 个新编号，会把那 4 张**原样顶掉**，
而且报错都不报，你只会看到「4 张定稿成功」。

| | `--apply` | `--add` |
|---|---|---|
| 语义 | 整组替换 | 往后追加 |
| 起始编号 | 永远从 `_01` | 已有最大编号 + 1 |
| 已定稿的图 | **会被覆盖** | 一张不动 |
| 什么时候用 | 这个姿态第一次定稿、或要整组换掉 | 任何「再补几张」的场合 |

两者不能同时给（脚本会直接拒绝，不猜你想干嘛）。
起始编号取自 `assets/mascot/` 而不是 `raw/`，所以**补图前重新抽一批候选也不会算错编号**。

### 10.4 早期流程（已不用，留作对照）

```
1. 跑 gen_prod_v2.py 批量出图（多抽，目标量的 3 倍）
2. 跑 make_montage.py 拼图，快速过一遍
3. 人工逐张筛选（合格率约 1/3 ~ 1/2）
4. 跑 finalize_prod_v2.py 整理成正式成品夹并重编号（保留来源清单）
```

> 🔑 **审图是人工环节，且是真正的瓶颈** —— 生成上百张只要十几分钟，审图要花的时间远大于此。
> 出图脚本能做的只是**多抽**和**把候选摆整齐**，它不替你判断哪张好。
