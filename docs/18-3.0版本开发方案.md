## 2. 任务一 · 环境检测（Dev-C++ 那台机器检测不到）

**病因不是版本解析，是候选路径没覆盖到。** 三条实测依据：

1. `expandGlob()`（`detect.ts:290-329`）对不带 `*` 的路径**会查存在性**（`:296`）—— §1.6 那个假阳性的根因已经修掉了。
2. `chooseCompiler()`（`:559-573`）**没有**「降级兜底」分支，只有真跑出像样版本号才算找到。
3. `looksLikeVersion()`（`:354-357`）只要求「含 `x.y` 且不含 `not found|not recognized|no such file|cannot find|error`」—— 老 GCC 的 `gcc.exe (tdm-1) 4.9.2`、`gcc (GCC) 4.9.2` 这类形状**本来就过**。

**缺的候选**（兜底表现状：每盘符 44 条 × 盘数 + 用户级 13 条 + `shared/install-plan.ts` 15 条；已有的 IDE 路径只有 4 条）：

| 已有 | 缺（怀疑就是朋友那台） |
|---|---|
| `Program Files\CodeBlocks\MinGW`、`Program Files (x86)\CodeBlocks\MinGW`、`Program Files\Dev-Cpp\MinGW64`（**仅非 x86 那一份**）、`TDM-GCC-64`（盘根） | **`Program Files (x86)\Dev-Cpp\MinGW32\bin`**（Dev-C++ 5.x 自带的就是它，TDM-GCC 4.9.2 **32 位** —— 与「自带的 GCC 较老」严丝合缝）、`Program Files (x86)\Dev-Cpp\MinGW64\bin`（6.3 默认落点）、盘根 `\Dev-Cpp\*`、`TDM-GCC-32`、`Program Files\TDM-GCC*`、`msys64\mingw32\bin`、盘根 `\CodeBlocks\MinGW`、`%APPDATA%\CodeBlocks`；且全表**没有** `%ProgramFiles(x86)%` 这种环境变量写法，**没有**按注册表发现 IDE |

> 这是**推断**：我没有那台机器。下面的方案第一步就是把它变成可证的事实。

**方案（四步）**

1. **改正向枚举（主力）**：新增「注册表卸载项 → `InstallLocation` → 在其下找 `MinGW*\bin\gcc.exe` / `mingw*\bin\gcc.exe`」。数据驱动，覆盖任意代际 / 版本 / 盘符，不用我猜目录名。仍然**只当候选**，真值照样靠真跑取版本（红线 17）。
2. **补静态候选**：上表「缺」的那批全补进 `perDrivePaths` / `userLevelPaths`（含 32 位与 x86 形式）。
3. **有界扫描（兜底，可选）**：在 `Program Files*` 与盘根下按名字前缀列一层目录（`Dev-Cpp*` / `CodeBlocks*` / `TDM-GCC*` / `MinGW*`），**不递归、不扫全盘**。默认只做 1+2，不够再加。
4. **顺手订正 4 处自相矛盾的注释断言**（都在检测器里，属本次范围）：Store 空壳退出码写 `49` 又写 `9009`；`python 在 stderr` 与实测的 stdout 矛盾；`老版本 JDK 的 -version 往 stderr 写` 无实测标记；`三段顺序…降级兜底` 已经过期。**先量再改**（红线：注释里的断言也要量）。

**验收判据**：① `foreign-pc.test.ts` 新增场景（Dev-C++ 各代目录 / `Program Files (x86)` / 非 C 盘 / 32 位 / 老版本输出形状），每条**先有阴性对照**；② 反向验证：种一个坏值，亲眼见它红（红线 19）；③ `npm run check:foreign` 全绿；④ **在真窗口里看「没找到」那一行**（0 字节 `reg.exe` + 重定向用户目录变量那招）；⑤ 真机：见 §0-1。

**红线对照**：开发机上四门齐活、注册表还会把 PATH 捞回来 → **开发机的绿是假的**（§5.6 / 红线 16），所以必须有真机或等价环境那一步。

### 2.2 真窗口 A/B（验收判据 ④）

单测全绿不等于界面里对 —— 而**开发机上根本摆不出「没找到」**：这台机器 gcc / g++ / javac / python 四个全在 PATH 里，检测永远是「一次就找到」，兜底表与注册表两条路**一次都不走**（红线 16）。所以另搭一套假环境，用**真窗口**跑三臂对照。

**假环境**（`<workspace>\_noToolchain\`，纯 ASCII —— 要经 `reg.exe` 的 GBK 输出，中文路径会解成乱码）：

| 项 | 造法 | 为什么 |
|---|---|---|
| PATH | 只留 `shim\` + `System32` | 让 `where gcc` 走真的「查不到」那条路；System32 必须留（`where.exe` 在里面，砍掉就不是「PATH 里没编译器」而是「`where` 都不存在」，那是另一种故障） |
| 注册表 | `shim\reg.exe` 0 字节 | 注册表路由哑火，隔离出静态表这一条 |
| 用户目录 | `%LOCALAPPDATA%` / `%APPDATA%` / `%ProgramFiles%` / `%ProgramFiles(x86)%` 全指到空目录 | 否则「应用自己下的 winlibs 工具链」会从用户目录被翻出来，A 臂演不成「没找到」 |

**前提断言（先证前提，再看结论）**：改动前的盘符候选 **44 条，本机存在的 0 条** —— 所以 old 臂只可能演成「没找到」，不可能靠运气命中。

**reg 臂（同一个 new 产物，但 `reg.exe` 换成会说话的夹具）**：夹具只回答一件事 —— 卸载项里有一条叫 `Dev-C++`、`UninstallString` 指向 `<workspace>\_noToolchain\fake-ide\uninstall.exe`（**故意不给 `InstallLocation`**，走从 UninstallString 推安装根那条更险的路）：

**`fake-ide` 这个路径在静态表里一个字都没有**，它只可能来自注册表那条路由；而候选排位是「注册表认出的排在兜底表前面」，所以赢家就是它。这条链整条都在真窗口里跑通了：`reg query` → 按**名字**认出 IDE → 从 UninstallString 推根 → 根下 `MinGW64\bin\gcc.exe` → **真跑出** `gcc.exe (tdm64-1) 4.9.2`。

三张截图的 sha256 各不相同（`new` 与 `reg` 字节数恰好一样，因为界面上**只显示版本号、不显示路径**，两条路径在屏幕上长得一模一样 —— 归属只能从落盘的 `envCache.report[lang].path` 取，这次就是靠它判的）。三臂跑完全部 `主人数据目录 一个字节没动 ✓`，没有残留进程。

**这一轮自己踩的三个坑（都写进脚本注释了）**：

2 道是**同一个模板**：`bank-c-s2-malloc-missing-include-000` / `-023`。同一段代码在三个环境下的真实读数（都是刚才现编的，不是推的）：

| 编译器 | 退出码 | 学员看到什么 |
|---|---|---|
| 新 gcc 16.1.0（开发机） | **1** | `error: implicit declaration of function 'malloc'`，还附一条 `note`，**直接把 `+++ #include <stdlib.h>` 那一行画出来** |

**病因**：这道题要教的是「忘了 `#include <stdlib.h>`」，而这条在 **GCC 14 之前只是警告**（新编译器才把它升成错误）。所以它在朋友那台机器上**本来就没教到点子上**（改动前是靠一个不相干的 for 循环错误，勉强算「编不过」）。`-std` 不是元凶，只是把那层遮羞布拿掉了 —— 但结果一样：**那台机器上这道题现在无事可做**。

**建议（先量后定，不许先改再看）**：给 C 的编译参数加一条 `-Werror=implicit-function-declaration`（GCC 4.9 就支持），让老 gcc 与新 gcc **口径一致**。它是全局参数，会把**所有**依赖隐式声明的代码从「编得过」变成「编不过」——**包括某些题目的正解**。所以：用现成的探针加第三个臂（老编译器 + `-std` + 这条 flag）量一遍 1222 道，判据两条：① 正解的编译成功率**不许掉**；② 这 2 道必须变回编不过。量出来再决定加不加。

|---|---|---|---|

| `cpp-stage3-06` | `'…' was not declared in this scope` | **（没命中）** | `use of deleted function 'std::unique_ptr…'` |

★ **但有一臂还没量，必须在决定前补上**：上面这 70 处**只跑了老编译器**。新编译器的默认方言是 `gnu23` / `gnu++23`，改成 `gnu11` / `gnu++14` **同样可能改掉报错文本** —— 而**用新编译器的人才是多数**。同一条探针加一臂（新编译器 ± `-std`）就能量出来；那一臂的结果才决定「要不要补规则、补多少」。

## 3. 任务二 · 原生编译环境（本次唯一底层改动）

### 3.1 一个必须先讲清的事实

**应用今天本来就在调本机编译器** —— 它没有内置编译器：`resources/` 只有 7 张立绘 PNG，全仓（`node_modules` 外）`.exe/.dll/.jar` **0 个**，`package.json` 里连 electron-builder 都没有。所以「关闭时用内置的 / 开启时用本机的」这个二分，在代码里**不成立**。

真正能"不一样"的只有三件事，建议做前两件：

| 候选差异 | 做不做 | 理由 |
|---|---|---|
| ① 命令名由**用户合并 PATH**（进程 PATH + 注册表 HKLM/HKCU PATH）解析 | **做** | `mergedPath()` 今天只喂给检测（`detect.ts:466/604`），**从不喂给运行器**（`runner.ts:290` 只 spread `process.env`）。应用启动早于用户装工具链是真实场景，注册表才是当下事实 |
| ② 走**真 shell**（`cmd.exe /c`） | **做** | `.bat/.cmd` 垫片（scoop shims、`git.cmd`、venv 的 `activate.bat`）在 `shell:false` 下够不着。这正是将来终端 / Git / 虚拟环境课必经的那条路 |

### 3.2 弹窗与失败语义（两条硬规矩）

- **弹窗放渲染层单例**（练习场与答题遮罩会同时挂载，各挂一个必然两个弹窗叠着）；**答题里也弹** —— 不弹就等于在判分场景下静默用机主环境。位置在 `stores/runner.ts:107-109` 两道 guard **之后**、`lastResult` 清空前；**取消时上一次的输出必须原封不动**（清掉会看起来像跑过了）。
- ★ **原生失败绝不静默回退**到应用自己的链路（红线 17；结构上让两个函数不共享 catch，没有可"顺手加一行"的 fallback 位）。四种失败全部 `ok:false` 且带真实原因：命令在你 PATH 里不存在（预检 `where`）/ shell 起不来 / 编译阶段非 0 退出 / 运行阶段非 0 退出或超时。`tool-missing` 的 message 要说清四件事：找的是什么、**在你的 PATH 里**找的、应用自己找到了哪个绝对路径但原生模式不会去用、两条出路（关掉开关 / 把它加进 PATH）。→ 什么都没跑，所以这不是 fallback。
  - ⚠️ **本方案原写的「编译阶段 `exitCode === 9009`」是错的，已按实测订正**（2026-09-28，本机 Windows 11 / cmd.exe 10.0.26200）：`cmd /c` 跑一条不存在的命令，退出码是 **1**，不是 9009（9009 是批处理里那条路的产物）。所以「命令不存在」**只认预检 `where`**（找不到时 where 的退出码是 1），**不靠退出码猜**；预检没拦住时（PATH 在两次调用之间被改），原样把 cmd 的原话交给用户看，而不是编一个理由。实测记录写在 `src/main/runner/native.ts` 文件头。
- 一处**必须偏离现状**：`run-result-view.ts:232` 现在对 `envIssue` 会**隐藏 stderr**（怕 `spawn ENOENT` 吓到新手），但原生失败时 cmd.exe 的中文原话**就是**真实原因，必须显示。

### 3.4 风险与测试（都是会真跑的）

- 不用 `spawn({shell:true})`；用 `spawn(comspec, ['/d','/v:off','/s','/c', line])`，命令行由**纯函数**生成 + 元字符单测。**`/d` 不可省**：`Command Processor\AutoRun` 注册表键会在每次 cmd.exe 启动时执行任意命令。
  - 元字符的实测订正（原方案写的是「`& | ^ % " ! 空格`」，两处不准）：**要加引号的是空白与 `& | < > ^ ( ) "`**（引号外它们会改变整行结构，`a&b` 会被拆成两条命令）；**`!` 不算** —— 延迟展开（`/v:on`）才让它特殊，而我们固定用 `/v:off`，它是普通字符；**`%` 是引号救不了的**（引号里照样展开），换行同理 —— 这两个只能靠「保证它们不出现」，由「今天生成的行就是裸拼」那组不变式用例钉着。
  - `windowsVerbatimArguments: true` **不可省**：不加的话 Node 会按 MSVCRT 规则替我们给带空格的参数补引号（还带 `\"`），cmd 收到的是被改过的行 —— 实测报「文件名、目录名或卷标语法不正确」，而错误信息完全指不到这里。行首是引号时还必须**再套一层**（`/s` 会剥掉行首行尾那一对）。三条都有对照臂用例。
- **`.bat` 的直接子进程是 cmd.exe** → 绝不能按 pid 识别程序；`timedOut` 永远以我们自己的 flag 为准，**不看退出码**（cmd.exe 不转发信号）；`killTree` 的 `taskkill /T` 仍覆盖整棵树。
- 必测：**stdin 穿透**（`cmd /c` 下是否仍能从管道读到输入，最易漏）；**两种模式 stdout 逐字节相等**（否则 `codewrite` 会出现"写对了却判错"）。
- ★ `runCodeNative(req, report, deps: {env, shell?, whereExe?})` **必须可注入 env** —— 这是**设计约束不是测试便利**：不能注入，缺编译器那条分支在开发机上永远跑不到，绿就是假的（红线 16）。`whereExe` 同理可注入（`where` 自己起不来的那条分支要能测）。
- 测试计划：`foreign-pc.test.ts` 追加（先断言前提成立 → 阴性对照 → **对照臂**：同一条假 PATH 下托管管线仍成功）→ 反向验证（开关 OFF 时 `native:true` 必须 throw + 一条读源码的静态闸门：原生模块里出现对托管 `runCode` 的调用即红）→ 配置链迁移测试（含"显式 false 能真的关掉"）。

### 4.3 每节课的动画是什么形式（逐节画出来）

#### ① `common-14` 冒泡排序：大鱼干沉到底

```
[ 5 ][ 2 ][ 9 ][ 1 ][ 8 ]
 ^^^^^^^^                       <- 第 0、1 格点着（正在比大小）
```
**步序**：摆出这排 → 比 0/1 → **交换**（看得见的位移，不是文字说「换好了」）→ 比 1/2 → …… → 一轮走完，**最肥的那条沉到最后**（尾巴变灰 = 它站好队了）→ 第二轮（范围少一格）→ 收尾全灰。
**气泡示例**：「喵！5 比 2 大，换位子～」/「大鱼干沉到底啦！」/「这一条已经站好队，不用再管它了」
**立绘节奏**：比较 `think` → 交换 `yay` → 沉底 `proud`（**10 种姿态够用，不出新图**）
**成本控制**：只把**第一轮**拆到每一步，后面几轮各用 1~2 步带过；格子只开 **5~6 格**。

#### ② `common-15` 选择排序：每轮捞最小的一条

```
[ 5 ][ 2 ][ 9 ][ 1 ][ 8 ]
  ^i   ^j                       <- i 守着队首，j 一路扫过去
```
**步序**：队首立个「目前最小」→ 指针一路扫过去比 → 遇到更小的就换标记 → 一圈扫完 → **最小的那条跟队首交换**（跨格位移）→ 前缀变灰。
**气泡示例**：「这条比手里的还小，先记下它喵」/「一圈扫完，最小的跑到队首啦！」
**为什么要有这一节**：和冒泡**对照** —— 都是「每轮定一个」，一个靠相邻换、一个靠挑最小，学员能看见「同一个问题有不同解法」。

#### ③ `common-16` 二分查找：一半一半地丢

```
[ 1 ][ 3 ][ 5 ][ 7 ][ 9 ]
  ^         ^         ^
  lo       mid       hi
```
**步序**：先立前提「这排**必须是有序的**」（正好接第 ①② 节的排序）→ 看 `mid` → 比大小 → **一半变灰收拢**（这一步是主角：动画要慢、要让灰的那半边「收」起来）→ 看新区间的 `mid` → 命中 / 说「没有这只」。
**气泡示例**：「这一半的鱼干都没用了，丢掉喵！」/「中间这只比目标小，左边全都不用理了」/「找到啦！就是第 4 格那条～」
**计数**：每丢一半就把「还剩 N 只」写一步（8 → 4 → 2 → 1）—— 学员**亲眼看见**为什么是 O(log n)。

#### ④⑤ `common-17` / `common-18` 递归：一路收网进去 / 回来

```
+--------------+
| 收网(3)      |  <- 刚压进来，还没有结果
+--------------+
| 收网(2)      |
+--------------+
| 收网(1)      |
+--------------+
| main         |
+--------------+
```
**上节（下潜）**：每叫一层就**压一格**，格子里写「收网(3) = 还没算出来」。**必须停在「到底」的那一帧**（`收网(0)` 拿到答案、还没回头），下节从这里接上。
**下节（返回）**：**弹一格**、把结果**回填**到上一层的格子里（`收网(1) = 1` → `收网(2) = 3` → `收网(3) = 6`）。
**气泡示例**：「层数不一样，但每个人干的活一模一样喵」/「先别急着算，我再叫一个人下来」/「有人接住啦，可以回头了喵」/「一层交一层，最后交回 main 手上」
**为什么拆两节**：下潜和返回是**两个方向**的同一件事，塞一节里学员只会记住「有个栈」。

#### ⑥ `common-19` 复杂度：n 变大了会怎样

```
O(n^2)   ########################  4096
O(n)     ##############             64
O(log n) ###                         6
O(1)     #                           1
```
**步序**：先把 n 调大（8 → 64 → 1024），看四根柱子各长多少 → 再让 n **翻一倍**，看谁翻得最凶。
**气泡示例**：「n 才翻一倍，这柱子咋长了四倍喵？！」/「二分只要再往下走一格就够了～」
★ **纵轴必须是对数刻度**，否则 n=64 时 n²=4096 会把别的柱子全压成一条线（O(log n) 和 O(1) 直接看不见，学员会得出「二分和不查差不多」的**错**印象）。刻度会**明写在图上**（「纵轴：对数刻度」），不糊弄。

复用 ①③ 的视图，换成 C++ / Java 的写法，并按语言课形制带 `codefix` + `codewrite`。
