## 0. 摘要（一分钟版）

- **结论**：自建后端的选型定为 **TypeScript + Node 24 LTS + Fastify 5 + PostgreSQL 18 + 单枚随机令牌（Argon2id）**，部署形态为 **腾讯云 Lighthouse 2C2G + Docker compose 三件套（Caddy / api / db）**，代码放现有仓库的 `server/` 子目录。全部服务端依赖里**没有任何原生编译依赖**（密码哈希用 Node 24 内置 argon2，今晚已用 RFC 9106 官方向量实测通过）。
- **成本**：服务器约 400~470 元/年（先买 1 个月实测，再考虑年付 85 折）；域名 10~80 元/年（仅当走备案路线）。合计约 **35~45 元/月**。对比：BaaS 企业档 ≈300 元/月，已弃。
- **与 BaaS 版的关系**：客户端五层解耦（L1 界面→L2 store→L3 IPC 契约→L4 主进程服务→L5 云提供方）**只换 L5**；同步五步、墓碑、三态版本门、干涸协议、本地分区等机制**逐字保留**。原 8 项拍板中 7 项仍有效（BaaS 主备选 2 项作废）。
- **对抗复核的价值**：复核在五份设计里挖出 **6 条 critical 级硬伤**（认证契约四稿并存、用户/会话表三套 DDL、256KB 体积门会静默废掉练习记录同步、反代真实 IP 信任链断裂、首登收编缺「已激活重登」回边导致静默删数据、注销失败路径不可达），全部已在本文给出处置（§8）。
- **技术上的两个「今晚实测」**：① Node 24 内置 argon2id 与 RFC 9106 官方测试向量**逐位一致**（本机 19MiB/t=2 参数下约 18ms/次）→ 服务端依赖纪律升级为「零原生依赖」；② scrypt 的旧参数（N=32768,r=8,p=1）在 Node 24 上**直接抛错**（`ERR_CRYPTO_INVALID_SCRYPT_PARAMS`）——旧方案照抄必然启动即崩，已废弃。

### A 组 · 地基（P10.1 开工前必须定）

| # | 事项 | 我的建议 | 一句话理由 |
|---|---|---|---|
| 1 | **登录凭证统一**：四份设计写了四套互不兼容的令牌方案（30 分钟~180 天、一枚/两枚）。统一为：**单枚随机令牌 + 闲置 30 天滑动续期 + 绝对 180 天上限 + 即时吊销** | 照准 | 一枚不透明令牌由服务端查库验证，吊销即时生效（比 JWT 强）；另一套「访问+刷新两枚令牌」只服务于短命访问令牌——我们不需要短命，徒增弱网卡死路径 |

## 2. 技术选型总览与理由

### 2.1 选型表

| 层 | 选择 | 版本/形态 | 一句话理由 |
|---|---|---|---|
| 语言/运行时 | TypeScript + Node.js LTS | TS 5.9 strict（ESM/NodeNext）；Node 24（Docker `node:24-bookworm-slim`） | 与客户端同语言同工程习惯；ESM 与客户端一致 |
| Web 框架 | Fastify | 5.x | schema 校验+序列化内建、安全默认、`fastify.inject` 原生测试 |
| 校验 | Zod 4（经 fastify-type-provider-zod） | 4.x | schema 即类型，一处定义两处用 |
| 数据库 | PostgreSQL | 18（Docker 官方镜像，锁小版本） | JSONB + 并发 CAS + 支持到 2030；本地/生产同镜像 |
| 数据访问 | `pg`（node-postgres）+ **手写参数化 SQL** | 8.x | 6 张表都不到；安全关键路径（CAS/授权）本来就是手写 SQL；不引入 ORM 版本面 |
| 迁移 | 编号 SQL 文件 + 自研小 runner（~80 行） | — | 显式、可审计、与 ORM 解绑；校验和+advisory lock 防并发 |
| 身份认证 | 不透明随机令牌（32 字节 → base64url），服务端只存 SHA-256 | — | 查库验证、即时吊销、无签名密钥要管 |
| 密码 KDF | **Argon2id（Node `crypto.argon2`）** | m=19456 KiB, t=2, p=1，显式参数 | 零原生依赖；RFC 9106 向量实测通过（§5.2） |
| 反向代理/证书 | Caddy | 2.x（锁版本） | 自动 HTTPS/续期、配置即代码 |
| 容器 | Docker compose（caddy/api/db 三件套） | — | 与「一台小机器、一个负责人」的运维现实匹配 |
| 日志 | pino（Fastify 内置）+ 脱敏规则 | — | 结构化、默认不落敏感字段 |

### 2.2 为什么不是 MySQL + Express（你点名要的对比）

| 维度 | Fastify + PostgreSQL 18（推荐） | Express + MySQL 8 |
|---|---|---|
| 框架维护状态 | 活跃（OpenJS 基金会） | Express 长期低维护（5.x 迟到多年） |
| 请求校验 | 路由级 schema 校验+序列化内建（性能与安全一体） | 无内建，需另配中间件，漏配即无校验 |
| 类型体验 | TS 一等公民 | `@types/express` 补丁式 |
| 测试 | `fastify.inject()` 官方支持（无需起端口） | 需 supertest 等外挂 |
| 文档同步存储 | **JSONB**：整篇文档一棵树，天然匹配「客户端合并、服务端只存不解释」 | JSON 列功能弱：无 GIN 索引、jsonb 三兄弟（`->`/`->>`/路径）在 MySQL 里对应物少且坑多 |
| 并发条件写（CAS） | `UPDATE … WHERE revision=$n RETURNING` 一行语义清晰 | 等价能力有，但 RETURNING 缺失要用两步；心智负担大 |
| 单行 5MB 文档 | TOAST 压缩存储，天然支持 | `max_allowed_packet` 等一堆参数要调 |
| 迁移工具 | 编号 SQL 文件（与任何框架解耦） | 同理可行，但常见做法绑定 ORM 生态 |
| 未来排行榜/多维查询 | 窗口函数 + 部分索引 + GIN，演进台阶已规划（§4.8） | 也能做，但 JSON 内容的索引与聚合是弱项 |
| 生态坑 | 我们已用最大众的 node-postgres | MySQL 的 utf8mb4 排序规则、时区、严格模式都需要额外纪律 |
| 结论 | ✔ | ✘（无一项强于上面，常见理由只是「我熟」） |

### 2.3 为什么不是 SQLite

SQLite 单写者模型：同步服务的核心操作（CAS 并发写 + 限流/审计写 + 备份是文件拷贝期读锁）会在十几个用户同时练习记录时互相排队；且它省掉的正是我们唯一没省的地方——一台服务器和 Docker。`jsonb` 这条路（GIN 索引、TOAST、窗口函数）也全部作废。**结论：服务端用 PostgreSQL，客户端本地继续保持 JSON 文件**（本地单写者场景 SQLite 的优势本就为零，既有架构不动）。

### 2.4 为什么服务端也用 TypeScript

同一门语言、同一套 lint/测试习惯、协议类型可以客户端定义→服务端逐字节复用；主人与 AI 协作时的心智负担最低。性能对几十用户的同步 API 完全不是约束（Node 24 起 argon2 都有原生实现）。

## 3. 系统形态与 API 契约

### 3.1 拓扑

```
Electron 客户端（渲染层零网络）
   │  100% 网络调用在主进程（L5 提供方接口）
   ▼
https://api（或 https://IP）──► Caddy（80/443、TLS、安全头、覆写 X-Forwarded-For）
                                   │  Docker 内网（api 不发布端口）
                                   ▼
                                api（Fastify，15 个端点）
                                   │  同 compose 内网（db 不发布端口）
                                   ▼
                                db（PostgreSQL 18，命名卷）
```

- **五层解耦 L5 唯一出口**：本次转向只换 L5（原 `CloudProvider` → 现 `ApiProvider`），L1~L4 一行不改。
- 渲染层无出网面、无 CORS 面；无公开直链；头像也走鉴权路由（§5.8）。

### 3.2 代码放哪：同仓 `server/`

```
miai-biancheng/
  src/                        ← 客户端（现状不动）
  src/shared/cloud/protocol.ts ← 协议唯一真源（客户端侧，见 3.3）
  server/                     ← 新增，独立 npm 包（自己的 package.json）
    src/
      index.ts                ← 启动入口（读 env → 起 app）
      app.ts                  ← Fastify 实例组装（插件/路由/错误处理器）
      env.ts                  ← 环境变量校验（缺必填项启动即失败）
      errors.ts               ← 19 个错误码与应用级异常类
      protocol.ts             ← protocol.ts 的逐字节副本（闸门保证）
      http/                   ← 请求上下文（auth 中间件：令牌→会话→账号）
      plugins/                ← rate-limit / 审计 / 日志脱敏 等封装
      db/
        client.ts             ← pg Pool（连接串来自 env）
        migrate.ts            ← 迁移 runner（校验和 + advisory lock）
        migrations/0001_init.sql …
        repo/                 ← 每表一个仓库模块（users/sessions/docs/audit）
      domain/                 ← 纯函数：username / password-policy / png / size-gate / tokens
      services/               ← 用例编排：auth-service / docs-service / avatar-service
      routes/                 ← health.ts / meta.ts / auth.ts / docs.ts / avatar.ts
    test/
      unit/  contract/  integration/  fixtures/
```

**API 模块划分**（= 路由文件 = 服务 = 仓库三层）：`auth`（注册/登录/会话/登出/全撤/改密/注销）、`docs`（摘要列表/读/条件写）、`avatar`（读/写）、`meta+health`（公开）。共 **22 个端点**（本表 15 冻结 + docs/26 扩展 7，口径见 §3.4 注）。

### 3.3 协议真源机制（唯一机制，已消除原稿矛盾）

- 真源：`src/shared/cloud/protocol.ts`（客户端 repo），内容 = 协议版本号、文档类型与上限、错误码枚举、状态码映射。
- 服务端 `server/src/protocol.ts` 是**纯拷贝（无任何文件头差异）**，由 P10.2 落 `scripts/protocol-sync.mjs`：`copy` 同步 + `check` 在 CI/测试里做**逐字节相等**闸门（不等即红）。
- 「生成物勿手改」的提示放在 server 侧 README 与文件所在目录说明里，**不进文件本身**（文件头会破坏逐字节相等——这是原两份设计稿互相打架的点，此处裁定为纯拷贝）。

### 3.4 端点总表（22 个 = 本表 15 冻结 + 7 扩展，唯一权威）

| # | 方法 | 路径 | 鉴权 | 用途 | 要点 |

| 9 | POST | `/v1/auth/change-password` | 令牌 | 改密 | `{currentPassword, newPassword}` → 204；保留当前会话、吊销其他（5 次/天） |
| 10 | POST | `/v1/auth/delete-account` | 令牌 | 注销 | `{password}` → 204；幂等（§5.7 注销语义） |
| 11 | GET | `/v1/docs` | 令牌 | 四文档摘要 | 200 `{profile: 摘要\|null, wrongbook: …, favorites: …, practice: …}`（不含 payload；收编对话与预检用） |
| 12 | GET | `/v1/docs/:docType` | 令牌 | 拉取文档 | 200 `{docVer, revision, updatedAt, payload}` 或 404 `{null}` 语义；支持 ETag 条件读 |
| 13 | PUT | `/v1/docs/:docType` | 令牌 | 条件写（CAS） | `{docVer, baseRevision, payload}` → 200 `{revision, docVer, updatedAt}`；409 见 §3.5 |
| 14 | GET | `/v1/avatar/:hash` | 令牌 | 取自己头像 | 200 PNG（`image/png`+`nosniff`）或 404（hash 过期） |
| 15 | PUT | `/v1/avatar` | 令牌 | 上传头像 | `image/png` ≤512KB → 200 `{hash}`；PNG magic 校验 |

**口径注（2026-10-12 回填）**：本表 15 个为冻结端点；另有 7 个扩展端点（docs/26 追加，已实装）：`GET /v1/me/summary`、`PUT /v1/me/leaderboard-opt-in`、`POST·GET /v1/challenge/days`、`POST·GET /v1/rice/entries`、`GET /v1/leaderboard`。连同自述端点 `GET /v1/openapi.json`，`server/openapi.json` 实测 23 操作 / 20 path 项。**以磁盘为准**。

**冻结的语义规则**：
- `doc_ver`（服务端列）≙ `payload.version`（文档内的版本号）——**同一个数**，写入时服务端校验一致，不一致即 `VALIDATION_FAILED`。原三份稿对「payload 存信封内层还是全文」的分歧就此消除：**存全文（含 version 字段）**，doc_ver 是它的冗余列（用于三态门快速比较）。
- `revision`（CAS 修订号）由服务端独占管理，客户端只回传它拿到过的值。
- 请求带 `X-Sync-Protocol: 1`；`floor > 客户端` → 426。

### 3.5 错误码（19 个）与 HTTP 状态

| 状态 | 错误码 | 场景 |
|---|---|---|
| 400 | `BAD_REQUEST` | 请求形状错误 |
| 400 | `VALIDATION_FAILED` | zod 校验失败（含 doc_ver≠payload.version） |
| 401 | `UNAUTHENTICATED` | 令牌伪造/吊销/不存在 |
| 401 | `TOKEN_EXPIRED` | 闲置或绝对过期 |
| 401 | `BAD_CREDENTIALS` | 登录/注销密码错（统一出口，防账号枚举） |
| 403 | `FORBIDDEN` | 账号被禁用 |
| 404 | `NOT_FOUND` | 资源不存在（文档/头像 hash） |
| 409 | `USERNAME_TAKEN` | 注册撞名 |
| 409 | `CONFLICT_STALE` | CAS 修订号不符 —— 响应带 `details{currentRevision, currentDocVer}` 供重拉重合并 |
| 409 | `DOC_VER_BLOCKED` | doc_ver 回退 —— 该文档停同步（客户端持久化 blocked） |
| 409 | `CHALLENGE_DUPLICATE` | 同日已结算且 payload 不同（附已结算摘要；同 submissionId + 同 payload hash 重放 → 200 `idempotent:true`） |
| 409 | `ENTRY_CONFLICT` | `entry_key` 重放但内容不一致 |
| 409 | `OVER_DAILY_CAP` | 某 `kind` 当日条目数超上限——逐条进 `rejected[]`（HTTP 仍 200，见 docs/26 §4.6/§6.4） |
| 413 | `PAYLOAD_TOO_LARGE` | 超文档上限（含 DB 约束 23514 的映射出口） |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 非 image/png 头像等 |
| 426 | `PROTOCOL_TOO_OLD` | 客户端协议低于 floor |
| 429 | `RATE_LIMITED` | 附 `Retry-After` 头 |
| 500 | `INTERNAL` | 兜底（日志含 requestId，响应不含细节） |
| 503 | `DB_UNAVAILABLE` / 哈希队列满 | 附 `Retry-After` |

错误体统一 `{"error":{"code","message","retryAfterMs?","details?","requestId"}}`。**23514 分流（docs/26 §3.1【修订标注】）**：体积硬顶约束（`user_docs_payload_size`）→ 413 `PAYLOAD_TOO_LARGE`；其余 CHECK 违约（challenge_days 的 total/picked_langs 约束等）→ 400 `VALIDATION_FAILED`（附 `details.constraint`）；**绝不允许落到 500**（否则客户端会按 5xx 无限重试文案反复重试一个永不成功的请求——复核发现的静默坏法）。

### 3.6 版本协商（唯一机制）

1. 客户端启动/定时拉 `/v1/meta` → 若 `protocol.floor > 本机常量` → 全局停同步 + 升级提示；`current > 本机` 属正常（服务端兼容 N-1）。
2. 运行中任何响应收到 426 → 同样全局停同步（floor 被抬高时的活路）。
3. 每文档：拉到的 `docVer > 本机 CURRENT_*` → 该文档 blocked；本地版本 > 云端 → 先本地 migrate 再合并。
4. 推送被 `DOC_VER_BLOCKED` → 该文档 blocked，落 `accounts/<id>/.sync/state.json`，显示角标、下次同步先重试。
5. 客户端把 blocked 状态展示为「本机版本过旧/过新，请升级」——不允许静默。

### 3.7 幂等与重试语义（冻结）

| 操作 | 客户端自动重试 | 依据 |
|---|---|---|
| GET * | 网络错误重试 2 次（0.5s/2s） | 安全幂等 |
| PUT /docs | 网络错误重试 2 次；重试撞 409 → 重拉重合并 → 收敛 | CAS 使重试安全 |
| POST login | 连接错误重试 1 次；超时不重试 | 无副作用 |
| POST register | **不自动重试**；撞 `USERNAME_TAKEN` → 提示改登录 | 防「实际成功但响应丢包」的重复注册困惑 |
| POST logout | 不重试（本地登出即为准，服务端尽力而为） | 本地状态机是权威 |
| DELETE account | 不重试；不明结果 → 重试（幂等，见 §5.7）或 login 探测 | 注销幂等设计 |
| PUT /avatar | 网络错误重试 1 次 | 内容寻址幂等 |

不引入 Idempotency-Key 头：以上语义已覆盖全部真实重试场景，几十用户规模下该机制复杂度大于收益。

### 3.8 本地开发 ↔ 生产切换（三层隔离）

| 层 | 本地开发 | 生产 | 切换机制 |
|---|---|---|---|
| 客户端地址 | `http://127.0.0.1:8787`（构建期默认） | `https://IP 或域名`（构建期常量） | `config.serverBaseUrl`（v10 新增）空串=用构建期默认；**明文 http 只放行回环地址**；打包版忽略环境变量（防凭据重定向） |
| 服务端环境 | `.env`（gitignore）；`npm run dev`（tsx watch）+ 本机 PG18 | `.env`（服务器本地文件，不进镜像/不进 git，chmod 600） | 同一份 `env.ts` 校验；缺必填启动即失败 |
| 数据库 | 本机 PostgreSQL 18（免安装 zip，测试脚本起停，监听 127.0.0.1） | Docker `postgres:18`（不映射端口） | 同一版本；差异只在 `DATABASE_URL` |
| 令牌/配置 | 无签名密钥（不透明令牌无需签名密钥——`.env` 里没有，设计上就没有） | 同左 | — |

`.env` 键全集：`DATABASE_URL`、`MIGRATION_DATABASE_URL`、`PORT`、`NODE_ENV`、`TRUST_PROXY_CIDR`、`LOG_LEVEL`、`RATE_LIMIT_*`（覆盖默认）。**没有** JWT/签名/pepper 类密钥。

## 4. 数据库与建表规划

### 4.1 引擎

**PostgreSQL 18**（Docker 官方 `postgres:18` 系列，锁小版本 tag）。理由：本地/生产同版本；官方镜像即是部署事实；支持窗口到 2030（避免 2028 前被迫大版本升级）；`gen_random_uuid()`、`jsonb`、`RETURNING`、部分索引、advisory lock 全部内建。原稿的 PG16 主选基于「Ubuntu 自带」——但我们用 Docker 跑，该优势不存在。

### 4.2 五张表（三套 DDL 合并后的唯一版）

> 完整 `0001_init.sql`（含注释、约束、索引、GRANT）在 P10.2 落库前定稿；以下为规划级清单。先跑真库 + 种坏值自检（超限/非法 doc_type/非对象 payload 逐条见红）后才算冻结。

**① `users`**（账号）

| 列 | 类型 | 约束 |
|---|---|---|
| id | uuid | PK，`DEFAULT gen_random_uuid()` |
| username | text | NOT NULL，`CHECK (username ~ '^[A-Za-z0-9_]{3,20}$')` |
| username_lower | text | NOT NULL，**UNIQUE**（大小写不敏感唯一，服务端双写） |
| password_hash | text | NOT NULL（自描述格式：`$argon2id$v=19$m=19456,t=2,p=1$<salt>$<hash>`） |
| avatar_hash | text | NULL（sha256 hex；与 avatar_png 同生共死） |
| avatar_png | bytea | NULL（≤512KB；行内存储——几十用户每张 30~100KB，让备份天然覆盖） |
| created_at / password_changed_at | timestamptz | NOT NULL DEFAULT now() |
| disabled_at | timestamptz | NULL（封禁；鉴权每请求检查） |

v1 不设昵称（用户名即展示名；将来加列=一条只增迁移）。

**② `sessions`**（会话 = 一枚令牌一行）

| 列 | 类型 | 约束 |
|---|---|---|
| session_id | uuid | PK |
| account_id | uuid | REFERENCES users ON DELETE **SET NULL**（注销后墓碑行保留 24h） |
| token_hash | text | NOT NULL，**UNIQUE**（sha256(令牌) hex64；原文不落库） |
| created_at / last_seen_at | timestamptz | NOT NULL |
| idle_expires_at | timestamptz | NOT NULL（滑动：活跃时延展，写节流 1h/次） |
| absolute_expires_at | timestamptz | NOT NULL（= 签发 + 180 天，永不延展） |
| client_label | text | NULL（「Windows 桌面版」等展示用） |
| revoked_at | timestamptz | NULL |
| revoked_reason | text | NULL；白名单 `'logout','logout_all','password_change','disabled','account_deleted','purge'` |

**③ `user_docs`**（四份文档；服务端只做存储+CAS，不解释内容）

| 列 | 类型 | 约束 |
|---|---|---|
| account_id | uuid | REFERENCES users ON DELETE CASCADE；PK 一部分 |
| doc_type | text | `IN ('profile','wrongbook','favorites','practice')`；PK 一部分 |
| revision | bigint | NOT NULL `CHECK (revision >= 1)`（CAS 修订号，服务端独占自增） |
| doc_ver | int | NOT NULL `CHECK (doc_ver >= 1)`（≙ payload.version） |
| payload | jsonb | NOT NULL `CHECK (jsonb_typeof(payload) = 'object')` + 硬顶 `CHECK (octet_length(payload::text) <= 10*1024*1024)`（防呆；业务门在应用层，见 §4.4） |
| updated_at | timestamptz | NOT NULL |

主键 `(account_id, doc_type)`。

**④ `auth_audit`**（认证审计，11 类事件）

| 列 | 类型 | 说明 |
|---|---|---|
| id | bigint IDENTITY | PK |

`version int PK / name text / checksum text / applied_at timestamptz`。`/v1/health` 的 `schemaVer` = `max(version)`（启动时读一次+迁移后刷新）——原 `app_meta` 表**取消**（它只剩这一个用途）。

### 4.3 文档同步的 CAS（两条 SQL，冻结）

```sql
-- 首次推送（baseRevision = null）：建行为准；已有行则 0 行返回 → 重拉
INSERT INTO user_docs (account_id, doc_type, revision, doc_ver, payload)
VALUES ($1, $2, 1, $3, $4)
ON CONFLICT DO NOTHING
RETURNING revision;

-- 条件更新（baseRevision = n）：revision 必须相符，且 doc_ver 不回退
UPDATE user_docs
SET payload = $3, doc_ver = $4, revision = revision + 1, updated_at = now()
WHERE account_id = $1 AND doc_type = $2 AND revision = $5 AND doc_ver <= $4
RETURNING revision;
```

0 行返回时**补读分类**（同事务）：`SELECT revision, doc_ver` → `doc_ver > 入参 doc_ver` ⇒ 409 `DOC_VER_BLOCKED`；否则 409 `CONFLICT_STALE`（附当前值供重合并）。

### 4.4 体积门（复核最重的一条 critical，重新定稿）

- **量纲统一**：客户端「序列化字节」= 服务端 `octet_length(payload::text)`（写入前服务端按此校验；响应读入上限也按实际字节强制，不信 Content-Length）。
- **按类型分档上限（protocol.ts 唯一真源）**：

| 文档 | 上限（首版值） | 现状/推导 |
|---|---|---|
| profile | 2 MiB | 实测本机档案 4.2KB；三年也到不了 |
| wrongbook | 4 MiB | 逐题累积，留足余量 |
| favorites | 2 MiB | 实测 50B（新建）~ 重度用户几百 KB |
| practice | 8 MiB | `PRACTICE_KEEP_SESSIONS=5000` × 会话字节；**P10.2 用真实+合成数据核准后允许上调** |

- **三层结构**：① 客户端推送前检查（超限则该文档进 `PAUSED` 状态 + **用户可见提示**「练习记录已超出同步上限」——绝不静默）；② 路由级 `bodyLimit`（文档 9.5MiB / 头像 600KB / 认证 JSON 16KB）；③ DB CHECK 硬顶 10MiB（防呆，23514 → 413）。
- 设计上明确：**超限只影响该文档的云同步，本地功能一切照常**——「可选增强、失败降级」总口径。
- 备选预案（若 P10.2 实测 practice 会超）：合并侧按 `(at, uid)` 全序裁剪最旧会话直到落下限内（有日志、有角标），与本地上限同一把尺子。

### 4.5 索引清单（够用即止）

| 索引 | 用途 |
|---|---|
| `users.username_lower` UNIQUE | 注册唯一性 + 登录查找 |
| `sessions.token_hash` UNIQUE | 每请求鉴权（唯一热路径） |
| `sessions (account_id) WHERE revoked_at IS NULL` 部分索引 | 会话列表 / 全撤 / 封禁踢下线 |
| `sessions (idle_expires_at)` | 过期清理任务 |
| `user_docs` PK `(account_id, doc_type)` | 一切文档读写 |
| `auth_audit (created_at)`、`auth_audit (account_id, created_at)` | 90 天清理 / 账号审计 |

原稿为「进程内限流」在 DB 里造的部分索引与 count 查询**全部删除**（限流不查库，见 §5.4——白造复杂度）。

### 4.6 权限模型（不用 RLS）

- 双角色：`miai_owner`（建表/迁移用，无 SUPERUSER）+ `miai_app`（应用连接用：仅四表 DML + 序列 USAGE，**无 DDL**）。
- 迁移用 owner 连接串、运行用 app 连接串（两个 DATABASE_URL，`env.ts` 分别校验；混用即启动失败）。
- 越权防线不靠 RLS，靠三层：① HTTP 层无任何身份入参（结构性，§5 验收）；② 仓库层每条 SQL 必带 `account_id = $token.sub`；③ 真库集成测试：伪造挂 B 的行 + A 令牌 → 读不到（含阳性对照）。
- `pg_hba`：只允许 compose 内网与本地地址；`scram-sha-256`。

### 4.7 迁移纪律

编号 SQL（`0001_init.sql`、`0002_xxx.sql`…）+ 自研 runner：读 `schema_migrations` 已应用集 → 逐文件校验 checksum（不符即终止）→ advisory lock（防并发）→ 事务内执行 → 记账。规则：**只增不改**（新列/新表/新索引；改列必走可逆评审+先手动备份）；迁移命令显式执行（`node dist/migrate.js`），**绝不放在应用启动路径上**（启动失败时「代码问题还是迁移问题」必须一眼可分）。

### 4.8 演进留路：排行榜 + 错题多维度查询（你点名要的）

| 台阶 | 内容 | 触发条件 |
|---|---|---|
| 1（v1，现状设计） | 四份文档整树存 jsonb；一切查询在客户端内存完成 | 现在 |
| 2 | 服务端**派生表**：`user_stats`（练习次数/正确率/连续天数）+ `leaderboard_snapshots`（每日榜单快照）。由每日任务从 practice 文档 jsonb **计算派生**（jsonb 仍是唯一权威，派生表可随时重算） | 排行榜功能被提出，或用户 > 100 |
| 3 | 逐题级规范化表（`question_results`：account_id, lesson_id, qid, ok, at…）+ 复合索引，支撑跨用户错题统计 | 出现「全站最常错题」类需求 |

**为什么不现在就规范化**：v1 没有服务端查询需求（下载到本地算）；提前拆表会让「合并留客户端」的协议复杂化，违反「服务端只做存储+CAS」总原则。台阶 2 的表结构在 P10.0 已预留设计方向（派生可弃可重算），不被今天的选择锁死。

## 5. 认证与安全定稿

### 5.1 登录凭证（拍板 #1）

- **单枚不透明令牌**：32 字节 CSPRNG → base64url 字符串（前缀 `ms1_` 便于识别与日志脱敏匹配）。服务端只存 `sha256(token)`；令牌原文只在客户端 `session.bin`（safeStorage/DPAPI 加密）与传输中。
- **生命周期**：闲置 30 天（每次鉴权命中若距上次 >1h 则延展，**写节流 1h** 防止每请求 UPDATE）；绝对 180 天（`min(now+30d, absolute)`）；登出/全撤/改密/封禁/注销 → **立即失效**（查库模型天然即时）。
- **为什么不 JWT**：撤销是黑名单、多设备踢出要自建、密钥要轮管——不透明令牌+一次索引进查库，在单机小库上复杂度更低且吊销即时，安全性反而强。
- **为什么砍轮换**（拍板 #10）：轮换的唯一收益是「令牌被盗的检测信号」，但没有告警通道去消费它（拍板 #12 是另一个通道）；而弱网下「刷新响应丢包→重试被当重放→全链吊销」是确定的误杀路径，且无找回通道的用户会被锁在云端数据外。滑动+绝对+即时吊销覆盖威胁模型的其余部分。
- **多设备**：每设备一枚令牌一行会话；`GET /auth/sessions` 可看设备列表；`logout-all`/改密/封禁一条 SQL 全撤。
- **客户端存储** `accounts/<id>/session.bin`：`{v:1, sub, token, issuedAt, expiresAt}`（safeStorage 不可用时只进内存、退出即失，**绝不落明文**；P10.1 落接口与单测、P10.5 接线）。

### 5.2 密码哈希（拍板 #5）

- **Argon2id，显式参数 `m=19456 KiB（19 MiB）, t=2, p=1`**（OWASP 推荐档），salt=16 字节随机，tag=32 字节，存自描述字符串 `$argon2id$v=19$m=19456,t=2,p=1$<b64salt>$<b64tag>`（将来升参数时按前缀识别、登录成功顺带重哈希）。
- **实现 = Node 24 内置 `crypto.argon2`（零原生依赖）**，实测记录（2026-10-02 本机 Node v24.20.0）：
  - RFC 9106 §5.3 官方 argon2id 测试向量（m=32KiB,t=3,p=4,含 secret/AD）→ **逐位一致**（`0d640df5…e659`）；
  - 与 Node 官方测试向量（同组）一致；`memory` 单位 = 1KiB 块（文档原文）；
  - OWASP 参数本机约 **18ms/次**；v24.7.0 加入、文档无 experimental 标记、运行时无警告。
  - （旧稿的 scrypt 参数照抄会在 Node 24 抛 `ERR_CRYPTO_INVALID_SCRYPT_PARAMS` 且低于 OWASP 下限——已废。）
- **依赖纪律**：服务端**零原生编译依赖**（比复核建议的「允许恰好一个原生库」更强）。唯一切换点：若内置实现将来被证明不可用，`domain/password.ts` 一处文件换 `@node-rs/argon2`，存储格式不变。P10.2 的 M0 里程碑把「RFC 向量自检」写进集成测试（种坏值：篡改一次参数必须复算不一致）。
- **哈希并发闸**：信号量 2 并发（2 核）+ 队列 16，超限快速 503（附 Retry-After）——防「注册风暴把 CPU/内存打满」变成对全站的 DoS。
- **不启用 pepper**（secret 参数支持但 v1 不用）：pepper 会上移为「.env 丢失 = 全员永久锁死」的灾难因子，而它防的场景（仅备份文件泄露）威胁面小。列为 v1.5 可选加固。

### 5.3 密码策略（拍板 #5）

最短 **12 位**、最长 128；不做大小写/符号组合规则（对齐 NIST）；服务端维护离线弱密码黑名单（Top 常见密码 + 用户名子串包含检查），注册与改密时校验；错误文案不区分「不满足策略」的细节到能被枚举的程度。

### 5.4 限流与防爆破（拍板 #6；以本表为唯一真源）

| 场景 | 限制 | 备注 |
|---|---|---|
| 注册 | 每 IP 5 次/时 + 全局 50 次/日 | env 可调；被扫号再加邀请码 |
| 登录尝试 | 每 IP 30 次/15 分钟（成败均计） | 校园共享出口 NAT 下的容量核算 |
| 每用户名连续失败 | 5 次 → 60s 指数退避 ×2^n，上限 15 分钟，**永不硬锁死** | 防把主人自己锁在外面 |
| 全 API（每账号/每 IP） | 120 次/分钟 | 健康检查例外 |
| 头像上传 | 10 次/时/账号 | |
| 改密 / 注销 | 5 次/日、3 次/日/账号 | |
| 哈希计算 | 2 并发 + 16 排队 | 超限 503（§5.2） |
| 挑战提交 | 10 次/日/账号 | 正常一天 1 次；重试同 submissionId 不计 |
| 流水上行 | 6 次/时/账号；≤200 条/次；≤1000 条/日 | 批量端点 |
| 榜单/汇总/历史读 | 走全 API 120 次/分钟 | 不单列 |

**以上三行为 docs/26 §4.7 扩展（2026-10-12 回填）；本表仍为唯一真源。**

- **IPv6 按 /64 聚合**分桶（只按全地址分桶会被轮换地址绕穿）。
- **审计放大抑制**：未认证失败事件的审计按 `(ip段, 用户名)` 每分钟合并计数写一行（否则单 IP 可把审计表写到 17 万行/天）。
- 实现：进程内令牌桶（单进程部署，无外部依赖）；所有 429/503 响应带 `Retry-After`；**429 在客户端只是退避信号、不算错误、不惊扰用户**。

### 5.5 反代信任链（拍板 #6；三份旧稿全错的口径统一）

- 客户端伪造 `X-Forwarded-For` 是攻击面：`trustProxy: true` = 信任最左值 = 伪造即绕过限流。
- **三层契约**：① Caddyfile 显式 `header_up X-Forwarded-For {remote_host}`（**覆写**，客户端注入的值直接丢弃）；② Fastify `trustProxy: '<compose 固定网段>'`（如 `172.20.0.0/16`，网段在 compose.yml 里钉死，**不是 true**）；③ api 容器**不发布端口**（外网根本够不着）。
- **种坏值验收**：从客户端塞伪造 XFF 发起登录失败 → 断言限速桶以真实 IP 计（伪造值无效）；去掉 Caddy 覆写行，此测试必红。此验收进部署手册第 14 步与 P10.2 集成测试。

### 5.6 封禁（拍板 #6）

`users.disabled_at` 从「半成品」补全：鉴权查询 JOIN 检查（禁用即 403 FORBIDDEN）；封禁动作 = 置 `disabled_at` + 一条 SQL 吊销该账号**全部会话**（reason='disabled'）。验收：封禁后旧令牌立即 401/403、无法再登录。这是 v1 唯一可用的滥用处置手段，必须当前有效。

### 5.7 注销与审计

- **注销（幂等）**：`DELETE /v1/account {password}` → 校验密码 → 删 users 行（user_docs 级联删除、头像随行删除）→ sessions 置 `revoked_reason='account_deleted'` 保留 24h 作**墓碑**。重试带同一令牌 → 命中墓碑 → 仍回 204（客户端即可确认删除完成）。24h 后随过期清理删除。审计行匿名化（account_id/username 置 NULL）。客户端本地目录删除条件与 204 解耦：**服务端不可达也允许用户确认后删除本地目录**（先本地备份到回收目录再删）。
- **审计（11 类事件）**：字段见 §4.2；保留 90 天（每日清理）；登录日志含尝试用户名与 IP → 进隐私政策（拍板 #14）。
- **改密**：验当前密码 → 更新 `password_hash` + `password_changed_at` → 吊销除当前外全部会话；审计 `change_password`。

### 5.8 其他加固（已定稿，无需拍板）

- 超时显式化：`connectionTimeout 30s`、`requestTimeout 90s`（容慢网大文档上传）、`keepAliveTimeout` 默认；**Fastify 的超时默认是 0（不限）——旧稿「都有默认」是错的**，必须显式设。
- 安全头：Caddy 加 HSTS（先不含 preload）、`X-Content-Type-Options: nosniff`、`Referrer-Policy: no-referrer`；头像响应带 nosniff；不开 CORS（无浏览器调用方）。
- 头像：只收 `image/png`（415 否则）、≤512KB、校验 PNG magic；客户端已缩 256px；服务端不重编码（原样存取、原样回给本人）。
- 日志脱敏：token/密码/`Authorization` 全字段红act（redact）不进日志；requestId 贯穿。
- 账号目录路径白名单：客户端把服务端返回的 accountId 拼进本地路径前必须过 UUID 正则（P10.1，防路径穿越）。

### 5.9 v1 明确不做（清单）

pepper、2FA、邮箱/手机找回（账号=用户名+密码，无找回——已在产品口径中）、令牌轮换、证书 pinning、公开头像直链、跨用户可见性、CORS、Idempotency-Key。

## 6. 部署与运维（Lighthouse）

### 6.1 TLS 路线（拍板 #4）

| 维度 | 甲：域名 + LE 证书（需备案） | 乙：纯 IP + LE IP 证书（6 天档） | 丙：私有 CA + pin |
|---|---|---|---|
| 备案 | 必须（境内） | 不需要（**灰区**） | 不需要 |
| 年成本 | 服务器 + 域名 10~80 元 | 服务器 | 服务器 |
| 上线等待 | +1~3 周 | 当天 | 当天 |
| 客户端改动 | 无 | 无（公共信任链） | 需注入信任（差） |
| 运维负担 | 低（90 天自动续） | 低但续期频率 ×20（6 天） | 高（CA 生命周期） |
| 风险 | 备案被打回/等待 | 三个环节待实测（见下） | 信任锁死，可迁移性最差 |

- **核实过的事实**：LE IP 证书 2026-01-15 已 GA（shortlived 档，6 天）；Caddy 2.11 原生支持（需显式 `profile shortlived`，官方标 EXPERIMENTAL）；客户端走系统信任链，不需要任何自定义 CA。
- **我的建议（拍板 #4）**：**先买 1 个月**（~40 元，当天可测）→ 按顺序实测**三个停止项**：① 证书首次签发成功；② 自动续期成功一次（6 天档下观察 2~4 天内的续期日志）；③ 主人电脑上 Electron/Node 直连 `https://IP` 校验通过（IP SAN）。全绿 → 你确认接受灰区则走乙起步（省钱零等待），后续想要官网/分享页时按触发条件升级甲（改一行 Caddyfile + 一个配置项）；任一红 → 走甲（买域名+备案，1~3 周）。**无论哪条路，年付都要在月付实测/价格核对之后**。
- 急救退路（乙路失败时）：acme.sh 手工签发喂给 Caddy 静态加载（社区有实例）；结构性退路=迁香港或备案。HTTP 明文**永不**允许。

### 6.4 分步手册（19 步摘要；每步有验收，手册全文随 `server/README.md` 落地）

本地准备（SSH 密钥/ACME 邮箱）→ 购买（记 IP/到期日）→ 首连 → 系统基线（更新/时区/swap）→ SSH 加固（**先验密钥再关密码**）→ 云防火墙放行 22/80/443（验收含负例：5432 从外网**必须连不上**）→ 装 Docker → 部署目录与 .env（chmod 600）→ **打包含路径契约**（见 6.5）→ 构建镜像 → 起库+迁移（`docker compose run --rm api node dist/migrate.js`）→ 起 api+caddy → 冒烟（本机+主人电脑各跑一遍 `curl https://IP/v1/health`；证书 issuer/有效期核对）→ **负例三连**（邻居 IP 应超时；停 api 后 health 应报错；恢复）→ 备份+**真恢复演练**（种坏值：先插一条测试数据，恢复后它必须消失、真实数据回来）→ 健康检查 cron → 云监控告警 → `reboot` 自愈验证 → 拍快照收尾。
**上线判据**：主人电脑连续 24h 通过 `https://IP/v1/health` 得 200，且期间**首次自动续期成功**（6 天档证书；原稿「24h 内必须续期」判据在 6 天证书下必然假红，已修正）。

### 6.5 更新与回滚

- **发布链路径契约（复核抓出的「第一次发布必失败」）**：仓库无 git remote → 本机打包。统一用 **`git archive --format=tar.gz -o miai-server-<sha>.tgz HEAD server`**（**带 `server/` 前缀**，与 `releases/<sha>/server` 的构建上下文一致）；P10.2 用真实子树做对照实验固化。将来若推私有远端，服务器可改 sparse `git pull`（Gitee 优先）。
- **发布流程**：预更新备份 → 解包 releases/<sha> + current 软链 → `docker build` → 记旧 tag → 显式迁移（失败即中止，线上不动）→ 切 api → health 连测 10 次(≥5 成功) → 失败自动写回旧 tag 回滚。**代码回滚不动数据库**（迁移只增不改 + 服务端兼容 N-1 客户端）。
- 回滚时长：健康检查失败 <1 分钟自动；业务 bug 手改 tag 再 up <1 分钟；数据事故=从预更新备份恢复（几分钟，有真演练记录才算数）。

### 6.6 备份与恢复（拍板 #12）

- 每日 `pg_dump -Fc` + gzip，保留 14 份，**目录 umask 077**（备份含用户数据，不许 644）；cron 03:17。
- **异地硬性动作**：每周把最新一份下载到主人电脑固定目录（scp）。同机备份不算备份。
- 真恢复演练：上线后一周内一次、之后每月一次；恢复比对用「dump 时刻的计数快照」而不是「与实时库比」（后者必假红）。
- `.env`、`Caddyfile` 副本放密码管理器/离线文件（对应「服务器整个没了」的场景）。
- 手动快照：上线稳定后拍一个；任何险操作前拍一个。

### 6.7 监控与告警（拍板 #12）

- 服务器侧 cron 健康检查：`/v1/health` + **证书剩余天数** + **备份新鲜度（最新 dump <26h）** + 磁盘 >80%。
- 通道（你来挑）：healthchecks.io（免费，心跳缺席即邮件/推送）或 腾讯云监控告警到微信（CPU/内存/磁盘模板 + 上面三条自定义）。
- `/v1/health` 回读 `schemaVer` 并与发布记录比对（防「部署了旧版本」）。

### 6.8 运行时安全底线

SSH 只允许密钥（`PasswordAuthentication no` 先验后关）；云防火墙只开 22/80/443；DB/api 均不发布端口；容器不以 root 跑 api（node 用户）；镜像锁 tag 不用 `latest`；`docker image prune` 保留近一周以便回滚。

## 7. P10.1 本地重构注意事项（客户端）

> 总原则：**一次纯本地重构**——结束时应用在完全没有服务器的情况下，行为与今天完全一致（账号功能不可见）；但所有「未来接网所需的本地基础设施」就位并被测试覆盖。**零网络代码。**

### 7.1 做什么（13 项，`src/main/` 为主战场）

1. **StoreBox 账号分区**：`config/ai-cache/device.json` 留设备级根目录；盒内 5 个账号级 store（profile/wrongbook/favorites/practice/challenge）；**客人盒=今天的根目录原位不动**（收编=复制合并，客人档案永不移动/删除）；`switchBox()` + 干涸协议。
2. **`device.json` + installId**（UUID，practice 会话 uid 的命名空间）。
3. **`assertSafeAccountId`**：任何拼路径前过 UUID 白名单（防服务端返回 `../` 类 id 的路径穿越；种坏值测试必红）。
4. **profile v2→v3**：`learnedAt/favoriteAt` 时间戳 + 可撤销 `tombstones`；迁移纯函数、`learned` 绝不能丢、回填 epoch0 不伪造 now（伪造 now 会在墓碑比较里错误胜出）。
5. **favorites v1→v2**：`updatedAt` + 条目/文件夹墓碑；保留区 sanitize 改四键重建。
6. **practice v1→v2**：会话加 `uid（installId:id）`；去重键改 uid、裁剪按 `(at,uid)` 全序（两台设备各自 max+1 会产生相同 id——这是必须修的既有坑）。
7. **写口「保留区 apply」修复（头号 bug）**：`profile:save` 现在按白名单重建对象字面量，**未来新字段（learnedAt/tombstones）会被静默抹掉**；`favorites:save` 同款问题。统一改「以磁盘原始 JSON 为基底 apply 补丁，未知键全保留」；时间戳/墓碑维护**主进程独占**（渲染层不写这两字段，读口剥墓碑）。
8. **条件写口径（总审裁决：最小缝）**：`stamp = {epoch, rev}` 形状落地；**epoch 强制**（切盒/登出后旧 epoch 写一律拒——它有真实消费者：干涸协议测试）；**rev 只记录与返回、暂不强制拒绝**，「冲突→重载→重放 pendingOps」的完整消费者**推迟到 P10.3**（那时同步引擎才是第二写者；现在强制只会引入没有消费者的假冲突源）。写口函数从第一天就分「用户写口（维护墓碑）」与「合并应用口（**不**维护墓碑，P10.4 实现）」两条路径——防将来合并顺手复用用户写口把「跨设备减少」误盖成「now 删除」。
9. **同步状态占位**：`accounts/<id>/.sync/state.json`（`activatedAt` = 激活标志=幂等守卫；docs 摘要/revision、blocked、pendingPush 字段形状）。
