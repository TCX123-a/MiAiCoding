## 一、审查方法（为什么查 npm 而不是 GitHub）

**本喵没有去 GitHub 看源码，而是去查 npm 上真正发布的那个包。**

理由是本次调研中**踩过的两个真实陷阱**：

| 包 | GitHub 仓库显示 | npm 上真正发布的包 |
|---|---|---|
| PrimeVue | 根目录 `LICENSE.md` 至今写着 **MIT** | 5.x 起是**商业许可**，还带运行时授权校验器 |
| animate.css | main 分支是 **Hippocratic License 2.1** | npm 上的 4.1.1 是 **MIT** |

**仓库里的东西 ≠ 你装进来的那个包。** 中间隔着一次构建、一次打包、一次上传，任何一步都可能不一样。所以要审，就审**真正会被装进来的那个东西**。

**具体做法**：

1. 从 npm 官方注册表（和本机配置的国内镜像，两边都取）读取**包的元数据**
2. 把发布的 tarball 解压到**临时目录**（`C:\Users\<用户名>\AppData\Local\Temp\audit\`），逐个文件读源码
3. 对源码做**危险模式扫描**（清单见第三节）
4. **全程没有执行过包里的任何一行代码**——只是当普通文本读

### 3.2 唯一几处"命中了但良性"的，逐条说明

扫描不是"零命中"就完事——有几处命中了关键词，本喵**逐条看过，确认无害**，在这里交代清楚：

**① `require('./module.json')`（auto-animate）**
出现在 `nuxt/module.cjs` 里。这是 Nuxt 框架的模块注册文件，本项目**用的是 Vue + Vite，根本不走 Nuxt**，这个文件永远不会被执行。而且它读的是**同一个包内的相对路径**，不是外部文件。

**② `require("vue")`（splitpanes 的 CJS/UMD 构建）**
这是老式模块格式的写法，意思是"我需要 Vue"。本项目会用 ESM 构建产物（`splitpanes.esm.js`），里面是正常的 `import`。而且 Vue 本来就是本项目的核心依赖。

**③ `Object.defineProperty(el, '__aa_del', ...)` 和 `Object.assign(el.style, ...)`（auto-animate）**
看起来像"原型污染"（往对象上乱塞属性）的形态，实际是：
- `el` 是**一个 DOM 元素**，不是 `Object.prototype`
- `__aa_del` / `__aa_tgt` / `__aa_new` 是它在**元素自己身上**贴的便签，用来记录"这个元素要被删了/是新的"
- `.style` 是元素的样式对象

**没有一处碰 `__proto__` 或 `prototype`**。这是正常 DOM 操作。

**④ `scripts` 字段（最高危项）——这就是重点**

npm 包的 `scripts` 里如果藏了 `preinstall` / `postinstall` / `prepare`，**安装的那一刻就会执行任意代码**，这是供应链攻击最常用的入口。

```json
auto-animate : "scripts": {}                    ← 完全是空的
splitpanes   : "dev": "vite",
               "build": "vite build",
               "build-bundle": "BUNDLE=true vite build",
               "serve": "vite preview",
               "release": "npm run build-bundle && git add . && git commit -m 'Release.' && git push"
```

- auto-animate：**`scripts` 是个空对象**，干净到不能再干净
- splitpanes：只有 5 条，全是**开发者自己在本地敲的命令**。其中 `release` 里有 `git push`，但那是**维护者发版时手动跑**的，**你 `npm install` 的时候一条都不会触发**（触发安装钩子必须叫 `preinstall`/`install`/`postinstall`，这里一条都没有）

### 3.3 本节结论

**两个包加起来 39 个文件，没有一行在联网、读文件、执行命令、或收集信息。** 它们干的事就是：算元素位置、做动画、切分面板。

## 五、第四项：依赖树——会不会引发"连锁污染"

### 5.1 两个包声明的依赖

### 5.2 这说明什么

**"依赖污染"是最现实的供应链风险**：你装 1 个包，它拉了 30 个包，那 30 个里任何一个出事都会算到你头上（`event-stream` 事件就是这么发生的——攻击者没动主包，而是污染了它依赖的一个小包）。

**这两个包一个依赖都不拉。**

- `auto-animate`：**真·零依赖**。装它，`node_modules` 里只多它自己
- `splitpanes`：**零运行时依赖**，只声明需要 Vue。而 **Vue 本来就是本项目的核心依赖（3.5.42），完全满足 `^3.2.0` 的要求**，不会额外装任何东西

**引入这两个包后，本项目的依赖树只会多出 2 个节点，不会多出任何传递依赖。** 这是能拿到的最好结果。

## 六、超出你要求的四项，本喵还顺手查了这些

### 6.1 镜像给的包，和官方的**是不是同一个东西**（重要）

**发现**：本机 `.npmrc` 配置了 `registry=https://registry.npmmirror.com`（阿里的国内镜像）。

这意味着：你 `npm install` 时，包**不是从 npm 官方服务器拿的，是从国内镜像拿的**。镜像本身是合法且国内广泛使用的，但**它是你和官方之间多出来的一个环节**——理论上，镜像可以给你一个被改过的包。

**所以本喵做了逐字节比对**（只是读元数据，没有下载）：

| 包 | 镜像给的完整性哈希 | 官方给的完整性哈希 | 结果 |
|---|---|---|---|
| `@formkit/auto-animate` | `sha512-KGomRttjUfORuPUaR/ZGQw+6xfMrTM+sxnILv7JAd9AmabU9rg9i6gF/iC0Ih+QpKCubJpCA/1DX9UHKE8cX+A==` | 完全相同 | ✅ **一致** |
| `splitpanes` | `sha512-frNchoCv7w0nMQEuaDGgMGMU6jv3NhN6bBGQVfCNgwJdVcYaRmi1dwYDjp7SifAoUFdiQjBRB254LJNidzo15Q==` | 完全相同 | ✅ **一致** |

**结论**：**镜像给的，就是官方那个字节的包。** 而且 `npm install` 时 npm 会自动校验这个哈希——**下载到的文件只要被动过任何一个字节，安装会直接失败**。这是一道自动的防篡改闸门。

### 6.2 发布来源的可验证性（provenance）

| 包 | 注册表签名 | SLSA 溯源证明 |
|---|---|---|
| `auto-animate` | ✅ 有 | ✅ **有**（`https://slsa.dev/provenance/v1`） |
| `splitpanes` | ✅ 有 | ❌ **无** |

**"溯源证明"是什么**：它是一份由 npm 和 CI 系统（GitHub Actions）共同签发的证明，能 cryptographic 地证明**"这个包是从那一个 GitHub 仓库的那一次提交，通过官方发布流程构建出来的"**。

**为什么它强**：即使维护者的 npm 账号被盗，攻击者在**本地**构建一个带毒的包上传，**签不出这份证明**（因为它必须由 GitHub Actions 的官方身份签发）。

**auto-animate 有，说明它的发布流程很规范；splitpanes 没有，这是它相对弱的一点**——不是说它有问题，只是少了一层可验证性。已如实记入第七节。

### 6.3 发布历史有没有"投毒特征"

**账号被盗投毒的典型特征**：包休眠一两年没人管，某天突然冒出一个新版本。

实测两个包最近的发版节奏：

## 七、本喵不放心的地方（诚实清单）

**这一节是这份报告里最该看的部分。** 上面全是"干净"，但**没有任何审查能证明"绝对无毒"**。以下是本喵明确知道的边界和保留意见：

### 1. `splitpanes` 只有一个维护者，且社区规模小得多 ⚠️

| | auto-animate | splitpanes |
|---|---|---|
| 维护者 | 4 位（`justin-schroeder`、`boyd`、`lnguyen-braid`、`devoidofgenius`） | **1 位**（`antoniandre`） |
| GitHub star | 约 13,900（页面显示 13.9k） | **约 2,300** |
| 仓库 fork | 260 | 189 |
| 未决 issue | 38 | 23 |
| 提交数 | — | 531 |
| 仓库是否归档 | 否 | 否 |
| 仓库显示的协议 | MIT | MIT |

**为什么这是个风险**：单人维护意味着**单点故障**——账号被盗时没有人能及时发现和阻止，也没有第二双眼睛审代码。前面提到的几个真实投毒事件，全都发生在单人维护的包上。而 splitpanes 的社区规模（2.3k star）**比 auto-animate 小一个数量级**，意味着"众人替你审过"的强度也弱得多。

**本喵的判断**：**这个风险是真实的，但不足以否决使用。** 理由：

1. 它已经稳定运行 **8 年、80 个版本**，节奏均匀（见 6.3）
2. **零依赖**（见第五节）——没有可以被"绕道"污染的下游，这是最关键的
3. 代码量很小（12 个文件、约 81 KB），真出事也容易看清
4. 我们只把它当**纯 UI 组件**用，不涉及任何敏感数据（不碰文件、不碰网络、不碰用户信息）
5. 仓库未归档、仍在维护，不是"弃坑包"

### 2. `splitpanes` 没有溯源证明 ⚠️

如 6.2 所述。有注册表签名（能证明"这个包确实是被那个账号发布的"），但没有 SLSA 溯源（不能证明"是从那个仓库的那次提交构建的"）。**比 auto-animate 少一层。**

### 3. GitHub 仓库数据是**从网页读的**，不是 API（API 被限流了）⚠️

**过程如实交代**：本喵先走 GitHub 官方 API，两次都被限流（`API rate limit exceeded for 185.220.239.20`）。于是改读**仓库的公开网页**，拿到了第七节 1 那张表里的数据。

**这带来两个具体的不确定**：

- **快照时间不明**：网页上的 star / issue 数是**实时数字**，会变；而 npm 那边的数据（2.1、2.2）是有明确时间窗口的
- **口径差异**：GitHub **API** 的 `open_issues_count` 字段**把 Pull Request 也算作 issue**，而网页上的 Issues 标签页只数真 issue。两个口径会差 6 个左右。本报告统一采用**网页口径**（真 issue），所以你如果拿 API 去复核，看到的数字会比本报告大一些——**那不是对不上，是口径不同**

**已经确认一致的**：auto-animate 的 star 数，API 早先给出 13,919，网页显示 13.9k，**两者吻合**，说明网页数据可信。

### 4. 本机用的是国内镜像 ⚠️

见 6.1。**逐字节比对已经确认这次是一致的**，且 npm 会自动校验哈希。但这是一个**持续存在的信任外延**——以后每次装包都经过镜像。

**如果你希望彻底消掉这一层**，本喵可以在安装时不走镜像（临时指定官方源）。但这会让安装变慢，需要你拍板。

### 5. 【重要】本喵之前在调研文档里**写错了一个数字**

上一份 [开源炫酷UI版面调研与筛选.md](开源炫酷UI版面调研与筛选.md) 里，本喵写"**11 个运行时依赖**"（出现在第 50 行和 407 行）。

**实际是 16 个。** 今天查依赖树时才实测出来——很可能是本喵当时把 `@codemirror/*` 这一组当成一个包数了。

**这个错误不影响那份文档的任何结论**（"项目已经是重依赖了，别再加最重的那个"这个判断反而**更成立**了），但**它确实是个事实错误，本喵该说**。要不要本喵顺手把那份文档改对，你说一声。

### 6. 本喵自己犯过一个错，也记在这里

扫描"代码混淆"时，本喵的正则表达式里 `\\x[0-9a-fA-F]{2}` 被 shell 吃掉了一层转义，退化成"字母 x + 两个十六进制字符"，结果**误报**——它匹配到的是 `inde`**`xed`**`Panes` 里的 "xed"。

**当场发现并用正确写法重跑，结果是 0 命中。** 记在这里是因为：**一份"全绿"的扫描报告，如果扫描器本身有 bug，会一直绿下去而没人怀疑**。（这个坑本喵在另一个工具 `scripts/审计/verify-validator-guards.mjs` 里也踩过，本项目对这类错误有专门的防线。）

### 7. 模式扫描的固有局限

第三节的扫描是**照着已知的危险形态去找**。它能抓住"用了 `eval`""往外面发数据""装了安装钩子"这类**已知手法**。

**它抓不住的是**：某种本喵没想到的新手法、或者藏在正常逻辑里的微妙后门（比如"当颜色值是某个特定值时，偷偷……"）。

**所以本喵的诚实结论是**：**"没有发现任何可疑之处"，而不是"证明没有可疑之处"。** 这两个说法的差别，值得你知道。
