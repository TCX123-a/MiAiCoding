| **编辑器控件没得选** | Qt 唯一好用的代码编辑器 QScintilla 是 **GPLv3 或商业授权**，且**只绑 PyQt、官方根本没有 PySide 绑定**（社区替代品是个位数 star 的个人项目） |

### 1.3 Windows 上白捡的一层保护：libuv Job Object

**【调研】** Node 在 Windows 上会创建一个全局 **Job Object**（作业对象），设了 `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`，并把所有**非** `UV_PROCESS_DETACHED` 方式创建的子进程都放进去。

**意思是**：只要主进程一死，作业对象关闭，**里面所有子进程被系统自动连带杀死**——我们白捡了一层"主进程崩了也不会留下孤儿程序"的保护。

**⚠️ 触发代价**：`spawn(..., { detached: true })` 会退出这个作业对象 = **白扔这层保护**。

**【实测】** 全仓搜索 `detached` = **0 处命中**——我们现在没有踩这个坑，保持住就行。

> 补充一条：作业对象里有 `SILENT_BREAKAWAY_OK`，**孙进程会跑出作业对象**。所以主进程自己还活着的时候超时，仍然必须靠 `taskkill /T` 杀树——这层保护替代不了它。

## 二、🟡 仅可借鉴（抄思路，不抄代码）

### 2.1 freeCodeCamp 的题目文件组织

**【实测】** `freeCodeCamp/freeCodeCamp` ★**455,351**（本次 API 实查），TypeScript，未归档。

**做法**：一道题 = 一个 markdown 文件，用固定分隔符把不同用途的内容**分区塞进同一个文件**：

```
# --description--     题干正文
# --instructions--    要求做什么
# --hints--           提示（可折叠）
# --seed--            初始代码
# --solutions--       参考答案
```

**为什么值得抄**：题干、提示、初始代码、参考答案**在同一个文件里物理相邻**——改题的时候不会出现"改了题干忘了改提示"。

**对我们哪里有用**：**M7 的 194 课题库**。我们现在的设计是 `lesson.md` + `questions.json` 两个文件（比它更严格，题库是结构化的），但**它这个"分区"思路可以用在 `lesson.md` 内部**——把「钩子／比喻／代码示例／提示框／小任务」用注释锚点标出来，将来想批量重组或局部返修时，脚本能精准定位。

> ⚠️ **注意**：不要照搬成"把题目也写进 md"。我们的 `questions.json` 是结构化 JSON，能过 schema 校验、能被判分引擎直接吃——**这比 freeCodeCamp 的纯文本分区更强**，不要倒退回去。

### 2.2 Exercism 的测试用例纪律：**UUID 化，只增不改**

**【实测】** `exercism/exercism` ★**7,586**，未归档。

**做法**：每道题的每个测试用例都有一个 **UUID**。要改一个用例，**不是删掉旧的改新的**，而是**新增一个 UUID、同时把旧的标记为废弃**。

**为什么值得抄**：学员的进度记录里存的是"我做到哪一题了"。如果直接删改题号，**老学员的进度会错位**——昨天做的第 3 题，今天变成另一道题了。

**对我们哪里有用**：我们的题目 id 是 `q1..q10`（见 docs/09 §2.2）。**这意味着一旦题库更新时删改题目，老用户的错题本和进度会对不上号。**

> **✅ 这条在拍板「纯 DeepSeek 动态出题」之后变得更重要了**（见 docs/08 §6.4）：AI 会**不断生成新题**，如果它生成的题 id 也叫 `q1`，就会**和内置题撞车**——用户的错题本会指向一道完全不同的题。
>
> **落实办法（M6 动工前定）**：
> - 内置题保持 `q1..q10` 不变；
> - **AI 生成的题必须带命名空间前缀**（如 `ai-<时间戳>-<序号>`），**永远不复用 `q` 开头的 id**；
> - 内置题只增不改，要改就新增并用 `deprecated: true` 标记旧的。

### 2.3 Oppia 的 schema 版本纪律 ⭐ **这条对我们有实际改动**

**【实测】** `oppia/oppia` ★**6,799**，Python，未归档。

**做法**：任何**改变数据结构**的动作，必须同时做两件事：
1. 把 `schema_version` 加一
2. **写一个把旧数据搬到新结构的迁移函数**

**为什么值得抄**：没有迁移函数，旧数据会**带着老结构被新代码加载** → 字段是 `undefined` → 崩溃或静默丢数据。

**⚠️ 本喵顺手查了我们的代码，发现这个缺口是真的：**

**【实测】** `src/shared/types.ts` 里：

```ts
export interface UserProfile { version: number; ... }   // L121
export interface AppConfig   { version: number; ... }   // L172
```

**但是** `src/main/store/json-store.ts` 里**没有任何一行代码读这个 `version`**。加载逻辑只有：

```
解析成功 → 拿到什么就是什么
解析失败 → 回退 .bak
再失败   → 重建空结构
```

**这意味着什么（用大白话说）**：

> 将来 v1.1 想给用户档案加一个新字段。老用户升级后，他的 `profile.json` 会**带着旧结构直接加载**，新字段是空的 → 轻则功能异常，重则崩溃；**一旦崩了走"重建空结构"，用户攒了很久的学习进度就被悄悄清零了。**

**现在动手的代价是零**（只有你一个用户，数据删了重来也无所谓）；**将来动手的代价是"用户的进度已经没了"。**

> **建议落成硬规则**（本喵会写进 docs/08 §4）：
> **改 `profile.json` / `wrongbook.json` / `config.json` 的结构，必须同时 bump `version` + 写迁移函数；禁止静默重建。**

## 四、本次调研顺带查出的真问题（**M5-03 待办清单**）

> 这些是核对 `src/main/runner/runner.ts` 时发现的真问题，**按你的指示暂时不写代码**，先记录在案。
> 每一条都标了**是实测还是推断**——请区别对待。

| # | 问题 | 严重度 | 证据强度 |
|---|---|---|---|
| **1** | `killTree` 里的 `spawn('taskkill')` **没有 `'error'` 监听 → 主进程直接崩溃** | 🔴 **高**（应用闪退） | ✅ **本机实测复现** |
| **2** | 编译和运行**共用同一个超时** | 🟡 中 | ⚠️ 代码确认；**本机无 Java/gcc，无法实测** |
| **3** | `spawn` 失败时 `RunResult` **没有 message**，用户看到"无解释的失败" | 🟡 中 | ✅ 代码路径确认 |
| **4** | 临时目录可能含**非 ASCII 路径**（中文用户名） | 🟢 低（本机是 ASCII） | ✅ 本机实测 + 潜在风险推断 |
| **5** | C/C++ 的运行目标是不带目录的 `prog.exe` → **Windows 上 spawn 只查 PATH、不看 cwd，六条样例全挂** | 🔴 **高**（功能不可用） | ✅ **2026-09-13 装上 gcc 后本机实测复现** |

### 问题 1（最严重）：`taskkill` 拉不起来 → 整个软件闪退

`runner.ts:131-145` 的写法：

```ts
try {
  const killer = spawn('taskkill', [...], { windowsHide: true, stdio: 'ignore' })
  killer.unref()
} catch { /* 杀不掉就算了 */ }
```

**【实测】这段 `try/catch` 是抓不住错误的**——因为 `spawn` 是**同步返回**、错误是**异步**通过 `'error'` 事件抛的。本喵在你这台机器上跑了一遍复现：

```
node:events:505
    throw er; // Unhandled 'error' event
Error: spawn definitely_not_a_real_exe_xyz ENOENT
```

**进程直接退出（exit code 1）。**

**放到 Electron 里意味着**：`taskkill` 一旦创建不出来（杀软拦截进程创建、句柄耗尽 `EMFILE`/`EAGAIN`、PATH 异常），**整个主进程死亡 = 软件闪退**，用户正在写的代码和进度一起没。

> **正确写法**（写代码时再动）：
> ```ts
> const killer = spawn('taskkill', [...], {...})
> killer.on('error', () => { /* 降级到 process.kill */ })   // ← 补这一行
> killer.unref()
> ```
> 另外 `runProcess` 的 spawn（`runner.ts:153`）**已经有** `child.on('error')`（L190），**只有 killTree 这一处漏了**。

### 问题 2：编译和运行共用一个超时

`runner.ts:219` 算出一个 `timeoutMs`，然后**编译**（L253）和**运行**（L279）都用它。

**风险**：Java 的 `javac` 冷启动 + JVM 启动通常要 1～3 秒，C++ 带一堆 `#include` 也慢。如果用户在设置里选了 5 秒，**javac 可能被误杀**，用户看到「编译太慢被喵爪按停了」——但他代码其实一点没错。

> **建议**：编译给独立的宽超时（30～60 秒），运行用用户设置的超时（10 秒）。
> ⚠️ **诚实说明**：本机**没装 Java 和 gcc**，这条**没法实测**，是读代码 + 经验推断。等 M5 装了工具链要**实测确认**。

### 问题 3：失败时没有解释

`runProcess` 在 spawn 失败时走 `finish(null)`（L190）→ `exitCode: null` → `ok: false`，但**整条路径都没有给 `message` 赋值**。用户看到的是「运行失败」和一片空白，**没有任何提示**。

> **建议**：spawn 失败时给一句猫娘话术，比如「翻译官喵好像不在家，去设置页看看环境装好没喵～」。

### 问题 4：临时目录可能是非 ASCII 路径

`runner.ts:248`：

```ts
const dir = mkdtempSync(join(tmpdir(), 'miai-run-'))
```

**【实测】** 你这台机器 `os.tmpdir()` = `C:\Users\<用户名>\AppData\Local\Temp`——**纯 ASCII，本机没问题**。

**但是**：如果用户的 Windows 用户名是中文（比如 `C:\Users\小明\...`），临时目录就带中文。`javac` / `java` 在非 ASCII 路径下的行为是经典坑。

> **建议**：把临时目录钉到纯 ASCII 位置。另外顺手记一笔：**docs/08 §5.2 写的是 `app.getPath('temp')`，代码里用的是 `os.tmpdir()`**——文档和代码对不上，一并统一。

### 问题 5：C/C++ 跑的是 `prog.exe` 这个名字，而不是「那个文件」（**已修复**）

`runner.ts` 的 `planForLang` 给 C/C++ 的 `run` 是 `{ exe: 'prog.exe', args: [] }` —— **一个不带目录的名字**。

**Windows 上 `spawn('prog.exe')` 只按 PATH 找，完全不看 `cwd`。** `cwd` 只决定子进程的工作目录，不参与可执行文件的查找。于是：

```
编译成功 → prog.exe 就躺在临时目录里 → spawn('prog.exe') → ENOENT
```

**【实测】2026-09-13 本机装上 gcc 后第一次真跑，六条 C/C++ 样例全红：**

```
[c]   hello: ok=false exit=null match=false   spawn prog.exe ENOENT
[cpp] hello: ok=false exit=null match=false   spawn prog.exe ENOENT
...(math / input 同样)
```

同时 Java 和 Python **六条全过** —— 因为它们跑的是 `join(dirname(javac),'java.exe')` 和检测出的绝对路径，**自带目录**，所以只有 C/C++ 踩这个坑。

> **这个 bug 逃过所有测试的原因，比 bug 本身更值得记：**
> ① 只有装了 gcc 的机器才复现，而本机此前一直没有 C/C++ 工具链，那六条样例长期处于「跳过」状态；
> ② 更糟的是 `runner.test.ts` 里有一条断言 `expect(p.run).toEqual({ exe: 'prog.exe', args: [] })`
> ——**测试把这个错误值原样钉住了**，谁改谁红。
>
> **教训**：「环境依赖的用例跳过」是必要之恶，但**跳过的闸门等于没有闸门**。
> 纯逻辑部分必须有不依赖工具链的守卫（本次补的是 `resolveExe` 那组），不能全指望 e2e。

**修法**：加 `resolveExe(exe, cwd)`，在**运行处**（`runCode` 里，此时才知道临时目录在哪）把运行目标解析成绝对路径；plan 保持裸名字不变（它只描述「产物叫什么」）。回归守卫：`runner.test.ts` 的 `resolveExe` 组（不装 gcc 也跑）+ `samples-e2e` 扩到四语言共 14 条（本机真跑）。

### ❌ 一条被实测推翻的"问题"（记下来提醒自己）

本喵原本还怀疑 `killTree` 里**紧接着**的 `process.kill(pid, 'SIGKILL')`（L141）会**抢在 `taskkill /T` 前面把父进程杀掉，导致 `taskkill` 找不到树、孙进程漏杀**。

**实测结果是猜错了：**

```
场景A（现行写法：先同步 kill 父，再 taskkill /T）
   孙进程 PID 39620 → ✅ 已死
场景B（改成先等 taskkill 走完树）
   孙进程 PID 22480 → ✅ 已死
```

**结论：现行顺序没问题**，Windows 的进程快照记录了父子关系，父进程死了 `taskkill /T` 照样能追到孙进程。**这一条不用改。**

> 记下来是因为：**本喵也会猜错。标【调研】和标【实测】必须分开看。**
