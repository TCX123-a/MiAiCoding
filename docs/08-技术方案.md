## 3. 内容 Schema

### 3.1 lesson.md（Markdown + YAML frontmatter）

frontmatter 必填字段：`id`（如 `common-01`、`c-stage1-07`）、`lang`（common|c|cpp|java|python）、`stage`（common 恒 0；语言课 1/2/3）、`order`（阶段内顺序）、`title`、`tags[]`、`required[]`（解锁前置 id，缺省=同阶段上一课）、`crossRefs[]`（可空）、`estMinutes`、`keywords[]`（英文关键词，搜索增强）、`compare[]`（可选，引用通用概念课 id）。

正文规则：
- 只用品类安全的 Markdown（标题/列表/加粗/表格），**禁用原始 HTML**（渲染 `html:false`）
- 代码围栏带语言标注：` ```c ` ` ```cpp ` ` ```java ` ` ```python `
- 四语言对比用自定义围栏（只放通用模块）：
  ````markdown
  ```compare
  c::
  for (int i = 0; i < 3; i++) { printf("第 %d 圈喵\n", i + 1); }

  python::
  for i in range(3):
      print(f"第 {i + 1} 圈喵")
  ```
  ````
- 提示框：`::: tip 猫娘提示` / `::: warn 小心喵`（markdown-it-container 渲染为圆角提示卡）
- 表情只用 Unicode emoji，不引外部图片；正文篇幅**不限**（以讲透为准，规则见 `docs/09`）；术语必须用 glossary 映射说法

### 3.2 questions.json（同目录，5-10 题）

```json
{
  "lessonId": "common-06",
  "version": 1,
  "questions": [
    { "id": "q1", "type": "choice", "stem": "题干喵？", "options": ["A", "B", "C", "D"], "answer": 1, "explanation": "猫娘解析，讲为什么" },
    { "id": "q2", "type": "fill", "stem": "填空白：`for i in ____(3):`", "answer": "range", "accept": ["range"], "explanation": "猫娘解析" },
    { "id": "q3", "type": "code", "lang": "python", "code": "print(1+2)", "stem": "输出几喵？", "answer": "3", "accept": ["3", "3\n"], "explanation": "猫娘解析" },
    { "id": "q4", "type": "codefill", "lang": "python", "code": "for i in ____:\n    print(i)", "stem": "把空填上喵～", "blanks": [{ "answer": "range(3)", "accept": ["range(3)"] }], "explanation": "猫娘解析" },
    { "id": "q5", "type": "codefix", "lang": "python", "brokenCode": "print(1+2", "stem": "它跑不起来喵，帮本喵修好它～", "expectedOutput": "3", "referenceFix": "print(1+2)", "explanation": "猫娘解析" },
    { "id": "q6", "type": "codewrite", "lang": "python", "stem": "打印 1 到 3，每个数字一行喵", "expectedOutput": "1\n2\n3", "referenceSolution": "for i in range(1, 4):\n    print(i)", "explanation": "猫娘解析" }
  ]
}
```

**六种题型，两条判分路径**（完整字段表见 `docs/09-内容生成规范.md` §2.2）：

| 判分路径 | 题型 | 怎么做 |
|---|---|---|
| **同步字符串比对** | `choice` / `fill` / `code` / `codefill` | `gradeQuestion()` 纯函数，现有实现一行不改 |
| **异步真跑比对** | `codefix` / `codewrite` | 走 `runner:run` 真编译真运行，用输出的 stdout 与 `expectedOutput` 比对 |

> ⚠️ **「不实际执行」这条已经作废**（旧版本文档如此断言）。`code` / `codefill` 仍然不执行，但 `codefix` / `codewrite` **必须真跑**——因为它们的答案是一整段学员自己写的代码，不跑就无法判断对错。

**真跑判分的三个硬约束**：

1. **绝不能只判「没报错」** —— 把代码删光同样不报错。`expectedOutput` 是唯一的判据，它存在的理由就是这个。
2. **判分与错误库必须分开** —— 判分只认真跑出来的输出，**永远不看命中了哪条错误规则**。错误库的正则按书写顺序匹配、命中第一条即返回，实测存在「规则被抢」（本意匹配 A、实际命中 B），拿它当判分依据会给出错误答案。错误库只用于**给学员生成报错解释卡**。
3. **参考解不是判分依据**（2026-09-15 补）—— `referenceFix` / `referenceSolution` 只做三件事：生成时被 `npm run check:questions` 真跑一遍、证明 `expectedOutput` 不是一句没人验过的断言；学员卡住时当示范；证明这道题**有解**。判分永远只比「学员代码跑出来的输出」与 `expectedOutput` 两个字符串。**不能拿学员代码去和参考解做文本比对** —— 这道题的教学目的恰恰是「怎么写都行，结果对就行」，文本比对会把每一份「写法不同但结果正确」的答案判错，而且是**越会写的人越容易被判错**。

**⚠️ 真跑题型的解析卡与参考解按钮，共用同一道门槛**（2026-09-15 定，`REVEAL_AFTER_WRONG = 2`）：

其余五个题型的解析是「讲为什么」，判完就该看见。真跑题型不一样 —— **它的解析本身就是答案**（「改成 `i <= 5` 就对了喵～」）。答错一次就摆出来，等于把「看看猫娘怎么改的喵」那个按钮白设了：学员错一次拿到散文版答案、错两次再拿到代码版，而**中间那段挣扎被整个跳过**，那正是这个设计唯一想要的东西。

- 门槛的真源只有 `REVEAL_AFTER_WRONG` **一处**，`stores/quiz.ts` 的 `canRevealReference`（按钮）和 `canShowExplanation`（解析卡）都读它，改数字两边一起动。
- 判据是「**答对**」**或者**「错够次数」；`checked` 是前提，没提交之前什么都不给（学员自己都还没表态，摆一张「你答错了」的红卡是在替一件还没发生的事下结论）。
- 界面层**不许**自己看 `s.checked[s.index]` 当判据 —— 对真跑题型来说答错之后它也是 `true`，照它显示就绕过了上面那道闸。这条是 2026-09-15 修掉的真实 bug（解析卡曾经就是这么绕过去的）。

**输出比对契约**（`expectedOutput` vs 学员真实输出，四条）：换行统一（`\r\n`/`\r` → `\n`）、去掉每行行尾空白、去掉首尾空行、**大小写敏感**。即「行内和行首空格有意义，行尾空格和末尾换行不算数」。

> 🔴 **第 1 条（换行统一）是这条链路能不能用的前提，不是锦上添花。** 2026-09-15 本机实测（`<workspace>\_crlf-probe.mjs`）：**四门语言的工具链在 Windows 上吐出的 stdout 全部是 `\r\n`**（C `"3\r\n甲\r\n乙\r\n"` / C++ / Java / Python 同）。而**运行器的解码环节不会剥掉 `\r`**（`runner.ts:35-45` 只做编码转换 + BOM）。
>
> **当时的 `normalizeCode()`（`src/shared/quiz-grading.ts`）单独用会全盘判错**：它确实处理了每行的行尾空白（`[ \t]+$`），但 **`\r` 不在 `[ \t]` 里**，所以实测 `normalizeCode("3\r\n")` 得到 `"3\r"`，与 `normalizeCode("3")` 的 `"3"` **不相等**；多行时**每一行**末尾都会残留 `\r`。
>
> ⚠️ **这个 bug 当时是睡着的**：`code` 题比的是**学员手打的文本**（永不含 `\r`），所以一直没暴露。而 `codefix` / `codewrite` 比的是**程序真实 stdout**（永远含 `\r`）——不修的话每一道真跑题都会永远判错，学员代码一个字没写错也过不了，且肉眼看输出完全一样、根本查不出原因。
>
> **所以**：真跑题型**另写了一个**规范化函数 `normalizeRunOutput()`（`src/shared/run-grading.ts`），把上面四条一起实现。上面那两句"必须另写、不能复用"记的是**当时**的结论。
>
> ✅ **已合并（2026-09-15，同一个批次内）**：`normalizeCode()` 改成**转调** `normalizeRunOutput()`，两者在任何输入上都不可能再分叉。方向是唯一可行的那个 —— 让 `normalizeCode` 也认 CRLF，而不是让真跑链路去掉这条规则（那会变成每一道真跑题都判错）。守这件事的测试在 `src/shared/__tests__/run-grading.test.ts`（"任意输入上都不分叉"那条）。
>
> **同一处还挖出第二个洞，也一并修了**：`code` 题里有 **9 道题的答案本身就是好几行**（`"1\n2\n3"` 这种），而收答案的输入框一直是单行 `<input>` —— 学员**根本打不出换行**，回车一按就当成交卷了。这 9 道题**永远做不对**。现在答案含换行时输入框自动变多行（`MiInput` 的 `multiline`）：回车是换行，Ctrl+Enter 才是交卷。

**超时预算**：编译有独立的 60s 宽限，运行用用户的 `runTimeoutSec`（默认 10s），**最坏单题阻塞 70 秒**。答题界面必须有等待态 + 防连点（主进程单任务队列**只保证串行，没有取消排队中任务的入口**，指望不上队列）。

> ✅ **实现状态（2026-09-15）**：`choice` / `fill` / `code` / `codefill` / `codefix` / `codewrite` **六种题型全部已实现并有内容**。契约见 `docs/09-内容生成规范.md`，真跑判分在 `src/shared/run-grading.ts`。

### 4.1 schema 迁移纪律（硬规则，对应 CLAUDE.md 铁律 6）

**现状（2026-09-15 更新，此前这里记的是「全仓 0 处迁移」）**：`json-store.ts` 至今**仍不读 `version`**（这是设计，见下「为什么迁移不写进 json-store」）。但迁移基建**已经不是 0 了**：

| 文件 | 迁移状态 |
|---|---|
| `config.json` | ✅ **已有**。唯一真源 `src/shared/config-migrate.ts` 的 `migrateConfig()`，当前 `CURRENT_CONFIG_VERSION = 6`（v1→v2 soundEnabled、v2→v3 theme、v3→v4 nativeRunEnabled、v4→v5 sfxVolume、v5→v6 favWrongToBook）。单测 `src/shared/__tests__/config-migrate.test.ts` |
| `profile.json` | ✅ **已有**（2026-09-29 学习闭环·阶段 0）。`src/shared/profile-migrate.ts`，`CURRENT_PROFILE_VERSION = 2`（v1→v2 加 `rewards` 奖励台账）；读口收归主进程 `readProfile()`，`version` 归主进程写死（渲染层手滑盖不回去） |
| `wrongbook.json` | ✅ **已有**。裸数组 → `{ version, entries }` 信封（兼容老文件），条目加 `source` / `removed(+At)` / `hole`；归口在 `main/store/wrongbook-merge.ts` 的 `normalizeWrongbook`，坏条目丢弃 + 出声 |
| `favorites.json` / `practice.json` / `ai-cache.json` | ✅ 出厂即 v1（学习闭环新增；各有 `main/store/` 下的合并/规范化模块与单测） |

**为什么迁移不写进 `json-store`**：`json-store` 是**通用**的原子读写器，它不认识任何一种业务结构 —— 让它去 `switch` 文件类型，等于把「谁是当前 schema」这件事复制到两个地方。所以迁移函数放 `src/shared/`，由**各自的读口**调用。

**`config.json` 的读口是唯一的**（`src/main/index.ts` 的 `readConfig()`），所以迁移挂在那里就**结构上不可能漏**。`readConfig()` 迁完会比对 `raw.version !== cfg.version`，不同就顺手写回 —— 于是磁盘上那份的版本号会自己追上代码。

⚠️ **`layout` 是历史欠账的收编对象**：它是加本机制**之前**新增的字段，补齐逻辑写在 `layout.ts` 的 `normalizeLayout()` 里、每次读配置时跑。文件里的 `version` 因此**永远停在 1**，事后分不出是哪一代的配置。v1 → v2 让它走一遍 `normalizeLayout()`，**行为与老代码完全一致**（不会把谁拖好的宽度弹回去），只是从此有了版本记录。

**风险**：v1.1 给 `UserProfile` 加字段后，老用户的 `profile.json` 会**带着旧结构被新代码直接加载** → 新字段 `undefined` → 轻则功能异常、重则崩溃；而一旦解析或运行失败走到「重建空结构」分支，**用户的学习进度会被静默清零**。

**规则**：

1. 改 `config.json` / `profile.json` / `wrongbook.json` 的**任何字段结构**，必须同时做三件事：
   - bump 对应类型的 `version`（`config.json` 是 `types.ts` 的 `CURRENT_CONFIG_VERSION`，**它同时是搬迁的目标版本和默认配置的版本号**，必须一起改）；
   - 写一个 `migrate*(raw: unknown) → 新结构` 的纯函数，放 `src/shared/` 以便 Vitest 直接测（`config.json` 的已经有了：`config-migrate.ts`，**照它抄**）；
   - 在**那个文件唯一的读口**调用它；**迁移函数必须能被单测喂旧版 fixture 验证**。
   > 「唯一的读口」不是每个文件都有的待遇 —— `config.json` 有（`readConfig()`），`profile.json` **没有**（渲染层 store + 主进程都可能碰）。给 `profile.json` 做迁移时，**第一步是先把读口收成一个**，否则一定会漏路径。
2. **禁止**静默重建：`read()` 走「主文件 → .bak → 重建空结构」的最后一步时，必须留日志/事件，不得无声无息。
3. **新增字段一律给默认值**，迁移函数只需补默认值，不做破坏性重命名。

> 参考：Oppia 的纪律（每次改结构都 bump `schema_version` + 强制迁移函数），见 `docs/12-开源项目借鉴清单.md` §2.3。
> **现在动手成本为零（只有 1 个用户）；等用户攒了进度再改，代价就是他的进度没了。**

#### （一）挂点：唯一一个是 `stores/challenge.ts` 的 watcher

### 6.2 DeepSeek（main/ai/deepseek.ts）

### 6.3 联网能力与数据同步（零服务器架构）

**总原则：核心功能离线可用，联网只做「增量增强」，绝不成为使用前提。**

| 能力 | 联网 + 已填 Key | 断网 / 未填 Key |
|---|---|---|
| 学习 / 练习 / 错题本 / 复习 / 跑代码 / 搜索 | 不受影响（纯本地） | **完整可用** |
| 194 课正文与题库 | **始终来自内置 `content-bundle.json`**（随软件版本发布） | 同左，完全一致 |
| 每日挑战出题 / 错题延展练习补题 | 由 DeepSeek **现场生成**（带本地缓存，同一提问不重复烧额度） | 回退本地题库；补不足时如实提示「只能出 N 道」 |
| 报错解释 | 未命中内置错误库时走 DeepSeek | 回退通用猫娘兜底话术 |

**架构约束（对应 CLAUDE.md 铁律 3）：**

1. **不搭自建服务器**。所有网络请求都是主进程**直连第三方 API**（默认 DeepSeek 的 OpenAI 兼容端点），Key 由用户在设置页自填、只存 main 侧 config，renderer 永远拿不到。
2. **请求失败静默降级**。网络异常 / Key 无效 / 额度不足，一律不弹错误弹窗、不阻塞界面，仅记录日志并回退本地题库。
3. **`content/` 仍是唯一真源**。AI 生成的题目写入**本地缓存层**；`content/` 目录与 `content-bundle.json` 仍是可离线分发的基线——AI 生成是「加菜」，不是「换地基」。
4. **缓存带版本与校验**。缓存落盘复用既有 json-store 原子写（tmp + rename + .bak），带 schema 版本号；解析失败或版本不兼容时**自动丢弃并回退内置版本**，绝不让坏缓存卡死软件。

### 6.4 题库更新数据源（✅ 已拍板 2026-09-12）

> **决策：采用「纯 DeepSeek 动态出题」，不做任何第三方托管**（不建 GitHub 题库包、不用网盘）。先把本地 API 调用跑通。

**这个决定改变了什么：**

| | 原设想 | 拍板后 |
|---|---|---|
| 题库内容 | 联网时从远端**增量同步**题库包 | **不做同步**——194 课正文与题库**只随软件版本发布**，永远来自内置 bundle |

| 需要托管什么 | GitHub 仓库或网盘 | **什么都不用托管** |

**为什么这样更好**：架构**最简单**——零托管、零镜像、零版本管理、零额外维护成本，也不用担心国内直连 GitHub 不稳。

**代价（明说）**：

1. **不填 Key 就没有"题目多样化"能力**，只能从本地 194 课题库里随机抽题（软件仍完整可用，符合铁律 3）。

3. 生成的题目**必须过 `questions.json` 同款 schema 校验**才能进缓存——AI 输出不可信，不允许未经校验直接进判分引擎。

- **题量**：5~20 步进器（读入也钳、记忆上次选择）；不限次、随时可开；中途退出练习史本轮不记（与其它模式一致），但答错的题已在提交时进错题本（2026-10-01「提交即记」口径）。
- **全对奖励**：从 `profile.rewards.gallery` 未获得的图里发 1 张 → 奖励弹窗 +「保存图片」（`gallery:save-image`；取消返回「取消」值不抛异常）；集齐后如实提示「图库待扩充」。

## 8. 搜索

构建期生成每课 `{id, title, tags, keywords, text}`（text = 正文剥标记 + 代码原文 + 题干）；运行时全量内存扫描（194 课 ≈600KB，<5ms），`toLowerCase` 子串匹配（中文无需分词）；排序：标题 ×3、tags/keywords ×2、正文 ×1；结果高亮 + ±40 字上下文，按模块分组；入口：侧栏搜索框 + Ctrl+K 命令面板，200ms 防抖。拼音检索 v1.1。

## 10. Electron 架构与安全

- 进程分工：main（生命周期/所有 IPC/持久化/runner/winget/DeepSeek）；preload（仅 contextBridge 白名单 `window.miai`）；renderer（纯 Web，只经 window.miai 交互）。
- 安全基线：contextIsolation:true、nodeIntegration:false、sandbox:false（与 electron-vite 官方模板一致，preload 为白名单 CJS）、webSecurity:true、CSP（default-src 'self'；script-src 'self'；style-src 'self' 'unsafe-inline'；img-src 'self' data:）、无远程内容、外部链接交系统浏览器、autoHideMenuBar、原生标题栏（自绘拖拽 bug 不值当）、单实例锁（second-instance 聚焦已有窗口）。
- **IPC 通道清单**（ipc-channels.ts 唯一真源；main 对每个 handler 做类型+长度入参校验）：
  - invoke/handle：`env:detect`、`env:install-start {lang}→{installId}`、`runner:run {lang,code,stdin?,timeoutSec?}→RunResult`、`config:get/set`、`profile:get/action`、`practice:record`、`wrongbook:list/resolve/remove`、`review:get-due/complete`、`ai:explain {lang,code,error}→{text}`、`backup:export/import`
  - send（main→renderer）：`env:install-progress`、`review:due`、`app:second-instance`
