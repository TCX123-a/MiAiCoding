# 咪爱编程 · 无限题库架构（`codefix` / `codewrite` 的长期供给）

> **状态**：设计方案，**待主人确认后才动代码**（2026-09-15）
> **要解决的问题**：本地题库要大到让学员连续用一年基本看不到重复的 `codefix` / `codewrite`，而纯手工写不现实。
> **配套契约**：题型字段见 `docs/09-内容生成规范.md` §2.2 / §7 / §8。

---

## 0. 一句话结论

**不要「让 AI 写 200 道题」，要「让 AI 写 60 个模板，让本地编译器把题目算出来」。**

模板定一次，实例由**本地真跑**产出——`expectedOutput` 是**跑出来的**，不是 AI 写的。于是：不但不重复的问题解决了，**「AI 把 expectedOutput 写错导致这题永远做不对」这个致命风险从根上消失了**（它是免费附送的，不是额外代价）。

## 1. 先算清楚需要多少题

### 1.1 一年要多少道

每日挑战**抽整个已学题库**（2026-10-10 起：无固定题数、答对继续答错即止；`CHALLENGE_RUN_MAX = 5000` 只是健全性上界，不是产品上限）。一局里有多少道 `codefix` / `codewrite` 随池子与连对情况浮动，下面的配额推算按 **2 题/天（推荐值）** 估：

| 大题/天 | 一年需要「不重复」多少道 |
|---|---|
| 1 | 365 |
| **2（推荐值）** | **730** |
| 3 | 1095 |

再加**语言课本身**：180 节语言课，每节至少 1 道 `codefix` + 1 道 `codewrite` = **360 道**。

> ⚠️ 这 360 道和上面的 730 道**不能重叠**：同一道题在课后练习出现过，就不能再在每日挑战里当"新题"。所以总量是**相加**的。

**合计：一年约 1100 道不重复的大题。**

### 1.2 主人的目标值（100~200 道）差一个量级

**100~200 道只够撑 50~200 天**（按 1~2 道/天算），不是一年。这个数必须往上修——但不是靠"多写题"，而是靠下面这个乘法。

### 1.3 模板的乘法

设模板数 `T`、每个模板可用参数组合数 `P`：

- **容量** = `T × P`
- **模板冷却**（同一个模板多久能再出现一次，设 `C` 天）：因为每天要出 2 道且不能撞模板，所以 **`T ≥ 2C`**

| 模板冷却 C | 需要的最少模板数 T |
|---|---|
| 14 天 | 28 |
| 21 天 | 42 |
| **30 天（推荐）** | **60** |

**`T = 60`、`P = 25` → 1500 道实例 ≥ 1100 道需求 ✓**

> **所以真正的目标不是「写 1100 道题」，而是「写 60 个模板」。** 数量级完全不同。

#### ⚠️ 但 `容量 = T × P` 对 `codefix` 会**高估**（2026-09-15 实现后发现）

`codewrite` 的参数轴是**真**的：数字一变，学员要算的东西就变了，答案跟着变。

`codefix` 不一样。看这个模板：

```jsonc
"params": { "a": {"kind":"int","min":2,"max":9}, "b": {"kind":"int","min":2,"max":9}, ... }
"brokenCodeTemplate": "int add(int a) { return a; } ... printf(\"%d\", add({a}, {b}));"
"referenceFixTemplate": "int add(int a, int b) { return a + b; } ..."
```

参数组合有 64 套，但**学员要做的事从第一套到第六十四套一模一样**：把 `int add(int a)` 改成 `int add(int a, int b)`。数字只改了 `printf` 里打印什么，**改错的那一处一个字节都没变**。

也就是说：**`codefix` 的参数轴基本是「防硬编码的装点」，真正的乘数是「有几种不同的 bug」，也就是模板数本身。**

| | `codewrite` | `codefix` |
|---|---|---|
| 参数变了，学员要做的事 | **变**（要算的数变了） | **不变**（改的还是同一处） |
| 有效容量 | `T × P` | **约等于 `T`** |

**对 `T ≥ 60` 那个结论的影响**：60 个模板如果全是 `codewrite`，结论成立；如果是 `codefix`，**60 个模板就是 60 道题**，不是 1500 道。要达到 1100 道的量级，`codefix` 得靠**模板数量**堆，不能靠参数。

**落地时的做法**：第一批（Python 入门 5 节）就按这个判断摊了模板 —— 每课 1 个 `codefix` 模板 + 1 个 `codewrite` 模板，`codefix` 给 1~2 个实例（只为让题面数字不固定），`codewrite` 给 3 个实例。**没有从 1 个 `codefix` 模板刷出 10 道题** —— 那 10 道里学员要做的事完全相同，等于只有 1 道。

**判据（一句话）**：**参数变了，学员要做的事情变不变？** 不变，那就不是参数化，是换皮。

## 2. 四个核心设计决策

### 决策 1（最关键）：`expectedOutput` 由**本地真跑**算出来，绝不交给 AI 写

这是整个架构的地基，也是它最大的价值。

```
模板（含 referenceFix / referenceSolution）
   ↓ 参数实例化
题目实例
   ↓ 本地真跑参考解（gcc / g++ / javac / python）
expectedOutput ←── 【算出来的，不是写出来的】
```

**为什么必须这样**：`expectedOutput` 是真跑题**唯一的判据**。让 AI 手写一个连它自己都没跑过的 `expectedOutput`，就是在**生产「学员永远做不对」的题**——因为 LLM 心算代码输出的准确率远低于它的自信程度。

**这条同时也是成本上的巨大优势**：实例化 + 真跑**完全在本地**，**一个 token 都不花**。

### 决策 2：题库进 `content/`，随 bundle 发布，**不做运行时可写文件**

- 题库落在 **`content/challenge-bank/<lang>/<lessonId>.json`**
- 由 `scripts/content-build.mjs` 打进 `content-bundle.json`，和现有课文走同一条路
- **不**放在 `userData` 下做成运行时可读写

**理由**：
1. **开箱即用**——新装的软件就有完整题库，不需要先跑一次脚本
2. **单一真源**——不会出现「bundle 里一份、磁盘上另一份」的漂移
3. 与现有架构一致：`docs/08:30` 明确「运行时零文件读取、零 IPC、天然离线」
4. 体积代价可忽略：1100 道 × 约 800B ≈ **0.9MB**（现有 bundle 约 600KB）

> 代价要说清楚：**扩题库要重打 bundle + 重出软件**。本项目里主人既是开发者又是用户，而且内容批次本来就要跑 `build:content`，所以这个代价是零。

### 决策 3：去重历史用**独立的 `questionHistory.json`**，不塞进 `challenge.json`

**它已经有类似机制了**：`challenge.json` 会算出一个 `lastSeen`（题 key → 最后出现日期，窗口 30 天，`challenge-merge.ts:147-168`），用来让每日挑战不重复出题。**但它的作用域只覆盖"每日挑战"**。

而主人要的去重范围是**学员见过的每一道大题**，包括：

| 来源 | 会被 `challenge.json` 记录吗 |
|---|---|
| 每日挑战 | ✅ 会 |
| 课后练习随机组卷（`PracticeView`） | ❌ **不会** |
| 错题重做 | ❌ **不会** |
| 将来的复习模式 | ❌ **不会** |

把课后练习的历史硬塞进 `challenge.json`，会让这个文件的名字变成一句谎话，也把两个功能耦在一起。

> **命名建议**：主人说的是 `challengeHistory.json`，但它管的**不止挑战**。建议叫 **`questionHistory.json`**，名实相符。名字一旦定下就改不动了，所以现在提出来。

### 决策 4：题库**按课号索引**，接进现有的 `learned` 过滤

现有的抽题池只收**已学过**的课（`buildPool` 过滤 `status === 'learned'`，`src/shared/challenge.ts:40-54`）。

题库沿用同一套逻辑：**每道题带 `lessonId`，每日挑战只从"已学过的课"的题库里抽。** 这样"学员还没学过递归，就绝不会抽到递归题"这件事**免费得到**，不需要新机制。

```

        ▼
```

## 4. 数据结构

### 4.1 题库条目 `content/challenge-bank/<lang>/<lessonId>.json`

```jsonc
{
  "lessonId": "python-stage1-08",
  "bankVersion": 1,
  "items": [
    {
      "id": "bank-py-s1-08-0007",
      "type": "codefix",              // codefix | codewrite
      "lang": "python",
      "stem": "……（猫娘口吻，写死输出格式）",
      "brokenCode": "……",              // codefix 专有
      "expectedOutput": "10",          // ← 本地真跑算出来的
      "referenceFix": "……",            // codefix 专有
      "starter": null,                 // codewrite 专有
      "referenceSolution": "……",       // codewrite 专有
      "stdin": "3\n5\n2\n",
      "explanation": "……",
      // ↓ 溯源与验证戳（新题型专用，不参与判分）
      "templateId": "py-s1-sum-loop",
      "params": { "n": 3, "unit": "颗猫粮", "verb": "囤" },
      "verified": {
        "at": "2026-09-15T10:00:00Z",
        "hash": "<上面那些内容字段的 sha256 前 16 位>"
      }
    }
  ]
}
```

**`verified.hash` 是防「静默跳过」的关键**：验证戳记的是**内容哈希**，不是时间。以后有人改了 `referenceFix` 而忘了重新验，哈希对不上，闸门自动变红——**不会出现「改了题但验证戳还是绿的」**。

### 4.2 去重历史 `<userData>/questionHistory.json`

```ts
interface QuestionHistory {
  version: number
  /** 题目 key → 最后一次出现的本地日期 YYYY-MM-DD（保留 180 天） */
  seen: Record<string, string>
  /** 模板 id → 最后一次使用的本地日期（保留 180 天） */
  templates: Record<string, string>
}
```

- **`seen`** 管实例级去重：180 天内同一道题不再出现。
- **`templates`** 管模板级冷却：同一个模板的**不同实例**也不能挨太近——否则学员看到的是"同一道题换了几个数字"，比重复出同一道题更让人腻。
- **裁剪**：写入时丢掉超过 180 天的条目，文件大小有上界（约 1100 条 × 60B ≈ 66KB）。

> ⚠️ **新增这个文件会触发 CLAUDE.md 铁律 6**（`config` / `profile` / `wrongbook` 的字段结构变更须 bump `version` + 写迁移函数）。它是**全新文件**、没有老数据要迁，所以现在只要做到两件事：**① 从第 1 版就带 `version` 字段；② 登记进迁移框架**，别再制造一个 "version 是装饰品" 的文件。
>
> 而且项目的迁移基建目前**是 0**（全仓 `migrate` 零命中）。这个文件很适合当第一个——它结构简单、可丢弃重建（最坏情况就是去重历史丢了，不影响学习进度）。

## 5. 模板机制

### 5.1 模板长什么样

```jsonc
{
  "templateId": "py-s1-sum-loop",
  "lang": "python",
  "stage": 1,
  "lessonId": "python-stage1-08",       // 挂到哪一课
  "type": "codewrite",
  "concept": ["for", "range", "累加"],

  // 参数域：实例化时从这里抽样
  "params": {
    "n":    { "kind": "int",  "min": 3, "max": 6 },
    "unit": { "kind": "pick", "values": ["条小鱼干", "颗猫粮", "个毛线球"] },
    "verb": { "kind": "pick", "values": ["捞", "叼", "囤"] }
  },

  // 这些字段里可以出现 {参数名}
  "stemTemplate": "……",
  "referenceSolutionTemplate": "……",
  "explanationTemplate": "……",

  // 测试输入怎么造（也是一个模板）—— 落地成结构，不写散文，见下
  "stdinSpec": { "kind": "ints", "count": "{n}", "min": 1, "max": 9 },

  // ⚠️ 这里没有 expectedOutput —— 它是跑出来的，不是写的
  "expectedOutput": "<<COMPUTED>>"
}
```

**`stdinSpec` 的四种形状**（`scripts/lib/bank.mjs` 的 `makeStdin`）：

| 形状 | 造出来的 stdin | 用在哪 |
|---|---|---|
| `{ kind: 'ints', count, min, max }` | 每行一个数，`n\n` 收尾 | 最常见：读 n 个数 |
| `{ kind: 'ints-one-line', count, min, max }` | 空格分隔一行 | 读一行里的一串数 |
| `{ kind: 'raw', text: '……' }` | 原样，`text` 里可写 `{参数}`。⚠️ 要给**样例**必须再写一段 `sampleText`（见下） | 非数字输入 / 固定输入 |

> ⚠️ **`raw` 的样例是对外要的，不是自动抽的。** 别的几种输入靠"换个种子重抽一套"就能得到和判分输入不同的样例；`raw` 的正文**写死了、不看种子**，重抽 50 次拿回来的还是同一串字。
>
> 2026-09-16 之前它因此是**文档里写着支持、实际一跑就把生成器炸掉**的一档：`drawInputs()` 那个重抽循环一路空转到头抛错，而报错写的是「多半是参数值域太小」——**一条把人引到错误方向的诊断**（模板作者会去翻参数域，而参数域完全没问题）。
>
> 现在的规矩：`raw` 要样例就写 `sampleText`（写死了，且生成器会**验一下它真的和 `text` 不同**——复制粘贴忘了改的话，等于把判分输入印在题面上，学员 `print(样例答案)` 就能过）；不写就是「这道题没有样例」，题面里也就不该出现 `{sampleInput}`。
>
> ⚠️ **写下 `sampleText` 之后还要自己保证：对参数空间里的每一套参数，它都不等于 `text`。** 「生成器会验」这句话只保证**当场报错**，不保证**写得出来**。第一次写 `py-s1-try-divzero` 时就踩在这里：判分输入是 `"{a}\n{b}\n"`（`a ∈ 4..9`）、样例是 `"{c}\n{d}\n"`（`c ∈ {8,9}`），于是 `a` 和 `c` 同时取到 8 或 9 的那 4 套参数上两边一模一样 → 生成器报「`raw` 的 sampleText 和 text 一模一样」。这**不是**随机碰运气，是**枚举**：只要两个值域相交，交出来的那些组合**必然**报错。
>
> 稳妥写法是**让样例的取值范围和判分的取值范围不重叠**（`c` 挪到 `{10,11,12}` 就一劳永逸），而不是在 `text`/`sampleText` 里各加一个错开的偏移量 —— 偏移量读代码的人看不出来它为什么在那儿。这条对其它几种 stdin 形状不适用：它们会**换种子重抽**，天然抽得出一组不同的。
| 上面任意一种 **+ `head`** | 在数字**前面**再打一段，`head` 里可写 `{参数}` | 先读一个 n、再读 n 个数 |

**为什么 `head` 必须存在**：`{ kind: 'ints', count: '{n}' }` 只会造出 n 个数，而「**先读一个 n，再读 n 个数**」这个形状是入门练习里最常见的一种，没有 `head` 就写不出来。而且**这种错不会报错** —— 少读一个数，程序照跑，只是结果不对。落地时第一批模板就撞上了它。

> ⚠️ `head` 是 2026-09-15 实现时才补上的（本文档早先只写了 `stdinTemplate` 这个散文占位符）。**散文占位符没法被机器执行** —— 这一段从「一句话描述」变成「一个结构」，本身就是实现阶段最有价值的一次修正。

### 5.2 三条必须遵守的实例化规则

**规则 1：题干里的示例输入，必须和判分用的 stdin 用不同的参数。**
否则学员可以 `print("10")` 硬编码答案——**而且他会被判对**，什么也没学到。

**规则 2：题干里示例的输出，也要跑出来。**
题干写「比如输入 3 5 2 就要输出 10」——这个 `10` 也是本地跑出来的，不是模板作者手写的。同一个理由。

**规则 3：`brokenCode` 必须真跑一遍，断言它「确实坏」。**
「坏」的判据比 docs/09 现在写的更宽一点，见 §5.3。

### 5.3 ⚠️ 需要修订 docs/09 的一条规则：`brokenCode`「必须报错」太窄了

`docs/09` 现在写的是「`brokenCode` **必须是真的会报错的代码**」。但有一大类**极常见、极有教学价值**的改错题是**根本不报错的**——逻辑写对了但结果算错了（off-by-one、边界条件、累加初值）。

**更好的判据**（而且机器可验）：

> **`brokenCode` 真跑一遍，必须满足：`跑失败` **或** `输出 ≠ expectedOutput`。**

- 这条**更宽**（容纳逻辑错误），也**更强**（它能抓住"看着像错的、其实跑起来完全正确"的题——那种题学员改了也白改）。
- **代价**：不报错的题，界面给不出报错讲解卡（错误库匹配不到东西），学员只能看到「输出不对」。这个差异要在界面上说清楚。
- **`common-12`「看懂翻译官喵的报错」例外**：那一课就是要教读报错，它的题**一律要求真报错**。

> ⚠️ **判据是对「每一套参数」说的，不是对「这道题」说的。**
>
> `verifyRunQuestion()` 一次只看一套参数（一道题），但生成器会拿**参数空间里的每一套**去过它（见 §5.2 规则 1）。所以模板里那句「坏代码会出错」必须对**所有**组合成立，而不是「大部分」。
>
> 2026-09-16 第一次写 `py-s1-try-valueerror` 就栽在这儿：参数写的是 `text ∈ ['12','7','喵喵','三只猫']`，坏代码是 `n = int(text); print(n + 1)`。本意是**让一半实例的输入是数字**，好堵住「学员直接 `print("这不是数字喵")` 也能过」这条路。
>
> 结果生成器当场报 `brokenCode 没有坏（跑出来就等于 expectedOutput）`：`text="12"` 时坏代码跑出 `13`，而正确答案也是 `13` —— **它压根没坏**。
>
> 根因不是参数选错，是**两个要求在结构上打架**：只要判分输入是数字，任何「正确转换、正确加一」的代码都等于正确答案，想「坏」就必须在**成功路径**上也写错。而 `input-no-int`（`a + b` 把两串数字接起来）、`loop-off-by-one`（圈数差一）之所以能带 stdin，正是它们的 bug **就在成功路径上**。
>
> **两条出路，选一条**：
> 1. **把参数域收进「坏代码一定坏」的那一侧** —— `text` 只取非数字（`['喵喵','三只猫','一打小鱼干']`）。代码坏得干净、学员只需要加 `try/except` 一件事，最贴本课。代价：输出对每套参数都是常量，**理论上可以硬编码答案通过**——而这不是本模板独有的问题：**22 个 `codefix` 模板里有 20 个没有 stdin**，输出本来就是常量。这条路与仓库既有做法一致。
> 2. **把 bug 挪到成功路径上** —— 让坏代码对数字也给出错的答案。能保住「输入不同 → 输出不同」，但学员要同时修两处，题就不再是「只教 `try/except`」了。
>
> 当时选了 1。**别把它当成"参数没调好"，它是模板类型和题目意图的匹配问题** —— 遇到就回来读这一段。

### 5.4 ⚠️ `fill()` 认花括号 —— 所以模板里写不了 Python 的 f-string 裸变量

`fill()` 的正则是 `/\{([A-Za-z_][A-Za-z0-9_]*)\}/g`，对**每一个**匹配到的 `{名字}` 都要求它是已声明的参数，不认识就**抛错**。

于是 `print(f"还剩 {n} 条")` 这句话在模板里有两种命运，**两种都不好**：

| 参数表里有没有 `n` | 会发生什么 |
|---|---|
| **没有** | `fill()` 当场抛错：「模板里用了 `{n}`，但参数域里没有这个参数」 |
| **正好有** | 被**静默替换成参数值** —— 代码变成 `f"还剩 7 条"`，参数失去了作用 |

第二条更阴：题**还是对的**（`expectedOutput` 由真跑算出、全程自洽），只是它退化成了一道参数不影响输出的废题 —— **没有任何一道闸门能发现**。

**【这不是 bug，是取舍的副作用】** `fill()` 是**故意**只认窄形状的（理由见 `bank.mjs` 里那段注释）：正则一放宽，C / Java / C++ 模板里的 `int add(int a) {` 就会被当成占位符而炸掉，那样**每一份 C 模板都写不出来**。窄的代价，就是 Python 的 f-string 和占位符长得一模一样 —— 而 Python 正是模板最多的那门语言。

**【能写什么】** 花括号里只要不是「光秃秃一个名字」，就安全：

```python
print(f"平均每只猫分到 {a / b:.2f} 条{dish}")   # ✓ 里面是表达式 + 格式串，fill 认不出来
                                                  #   {dish} 是参数，**故意**注入
print(f"约等于 {sqrt(n):.3f}")                    # ✓ 带格式串
print("还剩 " + str(n) + " 条")                    # ✓ 干脆不用 f-string
```

**写不出来的只有 `f"{n}"` 这一种形状。**

**【题面和解析里同样不能出现 f-string 的字面样子】** 那是另一道关：`finalizeDraft()` 会拿 `leftoverPlaceholders()` 扫题面和解析，而它认的形状很宽（`\{[^{}\n]{1,60}\}`）—— `{n:.2f}` 会被当成"没填掉的占位符"，定稿直接失败。所以讲 f-string 语法时只能用文字描述（「在引号前面写个字母 f，把名字放进花括号里」），**不能在题面里摆一个真的 f-string 例子**。

**【为什么全仓 38 个模板一个 f-string 都没有】** 因为这条约束**从来没被写下来过**。`py-s2-*` 是第一批撞上它的模板（2026-09-16），而且是撞在 01 课「f-string 大全」上 —— 想演示 f-string 就得改用表达式 / 格式串，或者退回 `str()` 拼接。

> **给模板作者的两条规矩**
> 1. f-string 的花括号里写**表达式**（`{a / b:.2f}`），别写裸名字；确实要注入参数时，那个名字必须是**故意**的。
> 2. 讲 f-string 语法时，题面和解析里**只描述、不举例**。

### 模板 A · 入门 · `codewrite` · 全参数化（**可行，且很省**）

```jsonc
{
  "templateId": "py-s1-sum-loop",
  "lang": "python", "stage": 1, "lessonId": "python-stage1-08",
  "type": "codewrite",
  "concept": ["for", "range", "累加"],
  "params": {
    "n":    { "kind": "int",  "min": 3, "max": 6 },
    "unit": { "kind": "pick", "values": ["条小鱼干", "颗猫粮", "个毛线球"] },
    "verb": { "kind": "pick", "values": ["捞", "叼", "囤"] }
  },
  "stemTemplate": "本喵今天{verb}到了 {n} 筐{unit}喵～\n\n请你写个程序：**读入 {n} 个整数（每行一个）**，把它们**加起来的总数**打印出来。\n\n比如输入是：\n{sampleInput}\n就要输出：\n{sampleOutput}",
  "referenceSolutionTemplate": "total = 0\nfor _ in range({n}):\n    total += int(input())\nprint(total)\n",
  "stdinTemplate": "{{n 个 1~9 的随机整数，每行一个}}",
  "explanationTemplate": "累加要用一个「从 0 开始的碗」喵：先 `total = 0`，每读进来一个数就加进去，最后打印。{n} 个数就转 {n} 圈～"
}
```

- 参数空间：4 × 3 × 3 = **36 种组合** ✓
- `{sampleInput}` / `{sampleOutput}` / `expectedOutput` 全部由本地真跑产出
- **概念完全不变**——变的只是数字和名词，这正是模板化该有的样子

### 模板 B · 入门 · `codefix` · 编译期报错（**可行，且能接上错误库讲解卡**）

```jsonc
{
  "templateId": "c-s1-func-arity",
  "lang": "c", "stage": 1, "lessonId": "c-stage1-12",
  "type": "codefix",
  "concept": ["函数声明", "参数个数", "编译错误"],
  "params": {
    "a": { "kind": "int", "min": 2, "max": 9 },
    "b": { "kind": "int", "min": 2, "max": 9 }
  },
  "stemTemplate": "本喵写了段代码想算两个数的和，可是翻译官喵气得直跺脚喵……\n你帮本喵看看它为什么跑不起来，改好它。\n\n改好之后，程序应该打印出 **{a} 加 {b} 的结果**。",
  "brokenCodeTemplate": "#include <stdio.h>\n\nint add(int a) {\n    return a;\n}\n\nint main(void) {\n    printf(\"%d\\n\", add({a}, {b}));\n    return 0;\n}\n",
  "referenceFixTemplate": "#include <stdio.h>\n\nint add(int a, int b) {\n    return a + b;\n}\n\nint main(void) {\n    printf(\"%d\\n\", add({a}, {b}));\n    return 0;\n}\n",
  "explanationTemplate": "`add` 只收一个参数，你给它塞了两个，翻译官喵当然不干喵～把它改成 `int add(int a, int b)` 就好啦。"
}
```

- 参数空间：8 × 8 = **64 种组合** ✓
- `brokenCode` 确实**编译失败**（`too many arguments to function`）→ 能命中错误库、能出讲解卡 ✓
- **`brokenCode` 和 `referenceFix` 只差一处，且差的正是本课刚教的**（函数参数）——这条是改错题的教学质量底线
- ⚠️ **`stem` 里不能写「第 3 行错了」**，那是学员要练的能力

### 模板 C · 反例 · 看起来能参数化，其实不能

```jsonc
// ❌ 这样是假参数化：
{
  "templateId": "py-s2-bubble-sort",
  "params": { "n": { "kind": "int", "min": 5, "max": 8 } },
  "stemTemplate": "请用冒泡排序给 {n} 个数排序"
}
```

**为什么不算数**：不管 `n` 是 5 还是 8，学员写的代码是**同一套**，学到的也是同一个东西。36 种组合里**没有任何新东西**——这不叫 36 道题，叫同一道题做了 36 遍，而且学员**看得出来**。

**判据**：一个模板算不算真参数化，就看**参数变了，学员要做的事情变不变**。
- 「读 n 个数求和」：n 变 → 循环次数变、测试数据变 → **真参数化** ✓
- 「给 n 个数排序」：n 变 → 算法一模一样 → **假参数化** ✗

**这条判据决定了模板化的覆盖率上限**（见 §7），也决定了「生成 60 个模板」这个目标到底是轻松还是困难。

## 7. 诚实的边界：哪些课能模板化，哪些不能

| 阶段 | 课数 | 模板化可行性 | 说明 |
|---|---|---|---|
| **Stage 1 入门** | 60 | **高（约 70-80%）** | 变量 / 循环 / 条件 / 数组 / 函数 / 字符串——全是「对一组参数化数据做一件事」，天然可模板化 |
| **Stage 2 进阶** | 60 | **中（约 40-50%）** | 集合 / 字符串处理 / 文件 IO 可以；「实现一个接口」「设计一个类层次」**没有可参数化的正确答案** |
| **Stage 3 精通** | 60 | **低（约 15-25%）** | 反射 / 注解 / 设计模式 / Stream——大多是「用对某个 API」，换参数不换知识 |

### ⚠️ 一个会让判分范式直接失效的坑：非确定性输出

**多线程、异步、并发**这些课（`*-stage3-03/04/05/09/10/11` 等）**输出顺序天生不确定**，而我们的判分范式是「逐字比对输出」——**在这些课上它直接失效**，不是难，是**不可用**。

三条出路，按优先级：

1. **把题目设计成确定性输出**（推荐）：要求学员 `join` 之后再统一打印，或者只打印一个汇总值。**多数多线程课的核心知识点都可以这样考**（比如"用锁把计数改对"→ 打印最终计数，这个值是确定的）。
2. **这些课不出 `codewrite`**，只出 `codefix`（改错题可以只要求"它现在不崩了 + 最终值对"）。
3. **引入"忽略顺序"的比对模式**（成本最高，且会削弱判分严格性，**不推荐**）。

**这一条必须现在就知道**，否则会到写 stage3 的时候才发现——那时候前面 120 节课的模式已经定型了。

## 8. 生成脚本设计

### 8.1 强烈建议用 `.mjs`，**不用 Python**

主人说的是「`scripts/` 下的 Python 批量预生成脚本」。**建议改用 `.mjs`**，理由只有一条但很硬：

> **验证环节必须使用应用自己的输出规范化函数。** 用 Python 就得**手抄一份**比对规则——而项目审计台已经立过铁律：「参数与匹配算法**必须抄应用**」，手抄就会漂移。
>
> Node 24 **可以直接 import 项目里的 TypeScript**（本机已实测：`import('./src/shared/quiz-grading.ts')` 成功）。于是 `gen-bank.mjs` 能直接调那个新写的规范化函数，**结构上不可能漂移**。

次要理由：`scripts/` 下现存的 6 个 `.mjs` 是同一套惯例（路径锚定、注释风格）；Node 24 自带全局 `fetch`，调 DeepSeek 不需要任何 HTTP 库；现有 Python 只在 `scripts/审计/` 和 `scripts/图片工具/` 里，都是**独立工具**，不碰内容管线。

> 如果主人坚持 Python：缓解办法是**写一个测试，把两边的实现喂同一批 fixture、断言结果相等**。这是额外的工作量，而且是可以避免的工作量。

### 8.2 脚本流程

```
node scripts/gen-bank.mjs --lang python --lessons python-stage1-08 --count 8
```

| 步骤 | 干什么 | 花 API 吗 |
|---|---|---|
| ① | 读模板库 `scripts/bank/templates/*.json` | ❌ |
| ② | 抽样参数，**跳过题库里已存在的 `(templateId, params)` 组合** | ❌ |
| ③ | 实例化模板（题干 / 代码 / stdin） | ❌ |
| ④ | **本地真跑** `referenceFix` / `referenceSolution` → **算出 `expectedOutput`** | ❌ |
| ⑤ | **本地真跑** `brokenCode` → 断言它确实坏（§5.3 的判据） | ❌ |
| ⑥ | 跑一遍题干示例，得到 `{sampleInput}` / `{sampleOutput}`，**回填进题面和解析**（`finalizeDraft`） | ❌ |
| ⑦ | *（可选）* 调 DeepSeek 给每道题写 `explanation` 文案 | ✅ |
| ⑧ | 写 `content/challenge-bank/<lang>/<lessonId>.json`，盖验证戳 | ❌ |
| ⑨ | 打印 **token 用量 + 折算花费**（读 API 返回的 `usage` 字段） | ❌ |

> 💡 **注意 ④~⑥ 全在本地，一个 token 都不花。**「生成 1000 道题」这件事本身**是免费的**——AI 只在**写模板**（一次几十个）和**写解析文案**（可选）时用到。

> ⚠️ **⑥ 的"回填"必须覆盖题面**和**解析**两个字段，而且回填完还要**两个字段都查一遍**有没有剩花括号。这两件事都收在 `bank.mjs` 的 `finalizeDraft()` 一处。
>
> 2026-09-16 之前它们是分开写的、且**只作用于 `draft.stem`**。后果不是"少填一处"，而是：`py-s1-read-two-sum` 的解析里写着「哪怕你在键盘上敲的是 `{sampleInput}` 里的数」，那五个字母**随题库上了线** —— 生成器绿灯、七道闸门全绿，只有学员的眼睛能发现。同类漏检能活下来，是因为闸门检查的是"这道题对不对"，而 `{sampleInput}` 既不影响判分、也不影响参考解跑不跑得起来。
>
> 现在唯一的入口是 `finalizeDraft()`：想回填就得连解析一起，想查残留也得连解析一起，**绕不过去**（有单测钉着）。

### 8.3 API Key 怎么读（**绝不能出现在命令行**）

- 从 `<userData>/config.json` 的 `ai.apiKey` 读（路径解析与应用一致：安装版 `%APPDATA%\咪爱编程`，便携版 `<exe目录>/data`）
- 支持 `MIAI_API_KEY` 环境变量覆盖（方便临时用一个专门的 Key）
- **绝不接受 `--key` 命令行参数**：命令行会进 shell 历史，也会进我的对话上下文
- 脚本**任何输出（含错误信息、日志）都不许回显 Key**，只打印前 4 位 + 长度用于确认读到了

### 8.4 成本预估（如实说明）

- **写模板**：60 个模板，分几批调，每批输出约 3~6k tokens → 总量约 **20~40 万输入 / 10~30 万输出 tokens**
- **写解析文案**（可选）：1100 道 × 约 300 tokens ≈ **33 万输出 tokens**
- **实例化**：**0**

> 具体金额按 `deepseek-chat` 的价目表折算即可，**但我不在这里写死数字**——脚本会打印 API 返回的真实 `usage`，用真实数字比用我记的价目表可靠。主人的习惯也是"别估，从记录里精确加总"。

### 8.5 断点续跑与幂等

- 脚本**可重复跑**：已存在的 `(templateId, params)` 组合直接跳过，不会重复生成
- 中途失败不会破坏已生成的内容（每课一个文件，写完才落盘）
- `--dry-run` 只打印要生成什么，不调 API、不写文件

## 9. 验证与门禁

### 9.1 新增一道闸门：`npm run check:bank`

对题库**每一条**：
1. 真跑 `referenceFix` / `referenceSolution` → 断言输出**逐字等于** `expectedOutput`
2. 真跑 `brokenCode` → 断言它**确实坏**（§5.3）
3. 断言 `verified.hash` 与当前内容哈希一致（**内容改了就自动失效**）
4. 扫题面/解析里的原术语，**错误级**（2026-09-16 补，见 §9.5）

> 题库自己这一层不判「这节课的题型配比够不够」—— 那要跨「手写题 + 题库」两个来源取数，
> 判据挂在 `content-validate.mjs`（**第 8 条**），由来见 §9.6。

### 9.2 增量验证（必须做，否则闸门慢到没人跑）

1100 道题全量真跑一遍：Python 每题约 0.3s、Java 冷启动约 1~2s → **全量约 15~30 分钟**。作为每次提交都跑的闸门，太慢。

**做法**：**只验哈希对不上的条目**。

- 常规运行：只跑「新增的」+「内容被改过的」，通常 < 10 秒
- `npm run check:bank -- --all`：全量重验（发版前跑一次）

> 这不违反「静默跳过 = 把没验过伪装成验过了」那条铁律——**恰恰相反**：哈希戳让"验过了"这件事**有了可核对的对象**。跳过的是**内容没变过的条目**，而它们的验证结论依然成立。这跟"压根没验过却当作验过了"是两回事。

### 9.3 反向验证（项目惯例）

故意改坏一道题的 `expectedOutput` → 确认 `check:bank` 变红 → 改回来。

> ⚠️ **这一步不是走过场 —— 它当场抓出了一个死判据。**（2026-09-15）
>
> 第一版 `check-bank.mjs` 里「验证戳过期」那一条**从来没生效过**：代码把它和「要真跑的」分进了两个数组，一个装的是副本、一个装的是原件，运行循环里读的是没带现算哈希的那一份，于是 `t.现算` 永远是 `undefined`，整条分支是死代码。表现是：把 `verified.hash` 改成任意假值，**闸门照样全绿、退出码 0**。
>
> 抓出它的正是"故意改坏 → 期望变红 → 结果是绿的"。**一条判据写完不算完，「它确实会红」必须被真的看到一次。**

> ⚠️ **但"改坏"要改的是产物，不是模板**（2026-09-16 批 6 订正，这条差点被当成配方发出去）。
>
> 批 6 的任务书里我把配方写成了「把模板的 `referenceSolutionTemplate` 改坏一个字 → `gen-bank --force` → `check-bank` 必须变红」。
> **这条配方永远变不了红**，原因就在生成器的设计里：
> `gen-bank.mjs:324` 的 `expectedOutput` 是**跑参考解现推**出来的（`normalizeRunOutput(ref.stdout)`），
> 模板里自带 `expectedOutput` 会被 `:134` 直接拒收（"它是参考解真跑出来的，不是写的"）。
> 所以改坏参考解 = 期望输出跟着一起改 = 产物**自洽**；而信任戳记的是产物自身的 `contentHash`
> （`lib/bank.mjs:329-343`，覆盖 expectedOutput/referenceFix/referenceSolution 等十个字段），重新生成时一并更新。
> **模板 + 答案 + 戳三者同向移动，闸门没有任何理由红。**
>
> 正确配方就是本节开头那一句：**改产物文件**（`content/challenge-bank/<语言>/<课号>.json` 里的 `expectedOutput`）→
> `check-bank --all <课号>` 变红 → `gen-bank --template <id> --force` 还原。
> 批 6 代理按这条走通了；我在另一课上独立复现过一遍：**红 = 退出码 1 + 2 道真跑不过，还原后 12/12、戳回到 `b95b3746e5e317c8`**。
>
> **为什么值得单独记一笔**：一条**跑不出来的验证配方**比没有配方更坏 —— 它会被照着执行、会一路全绿，
> 然后被当成"验过了"。这正是铁律「静默跳过 = 把『没验过』伪装成『验过了』」最隐蔽的一种形状：
> 跳过的不是判据，是**判据的方向**。
>
> ⚠️ **同一天我在反方向又栽了一次（假红）**：想验「验收脚本的 `finally` 把产包还原干净了没」，
> 我拿产包的**字节哈希**前后比，一跑就"不同" —— 看着像脚本没还原。实际是 `content-build.mjs:322` 的

### 9.5 ⚠️ 补上的缺口：题库文案此前**没有任何闸门扫过**（2026-09-16）

### 9.7 写模板时踩到的坑（2026-09-16 批 4 汇总，全部有实证）

批 4 里给 `c-stage2-04` / `c-stage3-03` / `java-stage1-16` 写模板时踩出来的，**下次写模板直接照着躲**：

1. **`check-bank` 的信任戳是「题自身」的**：改模板**不会**让已产出题目的戳失效，`npm run check:bank` 会把它们全部算成「戳对得上免跑」。所以改完模板**必须自己补一次** `node scripts/check-bank.mjs --all <课号>` —— 不补，就是拿旧戳给新内容背书。
2. **改一条已产出的模板 = 删掉那张题再重跑**（或 `--force`）。跳过判据看的是**参数组合**（`gen-bank.mjs:284` 的 `existing.has(paramsKey)`），**不是内容哈希** —— 参数没变就一直跳过，改动**一个字都落不了盘**。
3. **gcc 16 默认 C23**：缺 `#include <stdlib.h>` 就用 `malloc` 是**硬错**（老 gcc 只是警告）。所以 C 的 `codefix` 最好挑「编不过」或「编过也必摔」两类，别挑"只警告"的。
4. **Java 单文件运行 ⇒ 模板里绝不能有 `package`**（`findJavaClass()` 只认 `public class X`）。「包与导入」这一课只能靠 `import` 教，统一 `public class Main`。
5. **术语阈值 0 会咬住「类」**：`scanExcludes.lookBehind` 放行 人/分/种/之/同/归/门/鱼/肉/那/**这**/**各**/**此**（这/各 是 2026-09-15 补的，**此 是 2026-09-16 批 7 补的**），`lookAhead` 放行 型/别/目/似/句/操/错。
   ⚠️ 补「此」的经过：批 7 课 05 的写手写「依此类推」被算成 1 处泄漏，他**改掉了文案**。但那是**判据漏了一格**，不是他写错了 ——
   「依此类推」「诸如此类」是最普通的白话，跟 class 毫无关系，而排除表里没有「此」。
   **代价是实打实的**：假警报会逼着写手把通顺的中文改掉（= 为了迁就判据而降课程质量）。
   补完之后 `<workspace>\_term-probe.mjs` 加到 21 条：两条归 0，而 7 条**真泄漏**（子类/父类/个类/这一类/自定义异常类…）**一条都没放过** —— 判据变松必须先证「真货仍然抓得住」。
   ⚠️ **本条原先举的例子是错的，2026-09-16 批 6 订正**：原文写「`这类的岔路` 照样中招」，而「这」就在排除表里 ——
   `<workspace>\_term-probe.mjs` 拿**这句原话**当探针实测 **0 处**（探针里那条就是照抄本行）。真正会中招的是**排除表里没有的前字**：
   `这一类` / `这两类` / `这些类` / `异常类` / `父类` / `子类` —— 挨着「类」的分别是 一/两/些/常/父/子，一个都不在表里。
   （批 6 的 13 课写「自定义异常」时正撞在这上面：那课全文 **「类」字 0 个**，是靠全程绕开写过去的。）
   **教训**：`scanExcludes` 的原表在 `content/glossary.json`，文档**复述一遍表 = 造了第二份尺子**，复述的那份会漂 ——
   这条漂了，批 6 任务书照抄又漂一次。要判断某句话会不会中招，去跑 `_term-probe.mjs`，别读文档。
6. **`<stdlib.h>` 这种尖括号会撞 HTML 形状正则**：题面里一律写 `` `stdlib.h` ``；连 javac 的 `note: include '<stdlib.h>'` 都不能原样引用。
7. **`spreadIndices` k=2 取首尾**：两个参数若同区间，会双双取到 min/min 与 max/max —— 参数域要错开（如 a 1..4 / b 5..9）。
8. **别在解析里给不存在的摔点**。批 4 抓到的两处内容错误都是这一类：`c-s3-empty-chain-crash` 原写「报一条空链子会摔」（**报空链子其实不摔**，`print_list` 遇 NULL 直接印 `NULL`），`c-s2-malloc-report-reversed` 的「读到第 3 个就说不出第 0 个」也不是真的。**这类断言必须真跑一次再写。**
9. **`--template <id>` 挡不住别人的坏模板**（2026-09-16 批 7 实测）：`gen-bank.mjs` 在按 `--template` 过滤**之前**会 lint **全部**模板文件（`:174-188`），任何一个有问题就整体 `exit 1` —— 而报错里出现的是**跟你毫无关系的文件名**。
   5 个代理并行写模板时**必然**撞上（批 7 的 01 号代理为此被卡两次，报的是 02 号正在写的半成品）。
   **看到别人的文件名 → 等十几秒重试**，绝不许去改别人的模板。
   （这是并发批量写模板的结构性问题，不是谁的错；哪天要治，治法是「`--template` 时把 lint 范围也收窄到那一份」。）
10. **闸门在程序跑成功时只读 stdout，stderr 整个丢掉**（`scripts/lib/run-code.mjs:273`；只有**失败**时才把 stderr 拼上，`:275-276`）。
    实测：`print("正文里的字")` + `logging.warning("日志里的字")` 一起跑，工具拿到的 `output` 只有 `"正文里的字"` —— **日志行一个字都不在里面**。
    所以任何走 stderr 的东西**不能**写进 ` ```text ` 当输出（写了必红，而作者会觉得「它明明印出来了」）。
    连带纠正一个**我原先猜错的事实**：`logging` 的默认格式是 `级别:名字:消息`，**本来就没有时间戳**（要展示日志就 `basicConfig(stream=sys.stdout)`，实测可行且确定）。
    → 内容侧的完整规则在 `docs/09 §2.1`，**这里不复述**（复述就是造第二份尺子）。
11. **网络课的样例：`Date:` 头每次都在变**（2026-09-16 批 8 实测，跑两遍 diff 出来的就是这一行）。
    只许印**状态行 / 状态码 / 正文 / 内容长度**；响应原文（含 `Date:` 与 `Server:`）不许整段进 ` ```text `，否则**永远修不好**（同 Python Traceback 里那个随机临时目录）。
    端口写 `0` 让系统挑（免得撞上"端口被占"的偶发失败）但**不许印端口号**；`BaseHTTPRequestHandler` 默认往 stderr 打**带时间戳**的访问日志，**必须覆写 `log_message` 成空函数**。
12. **⚠️ 锁的判分拦不住「忘了加锁」——别在题面里写「不加锁一定会算错」**（2026-09-16 批 7 课 03 的代理发现，我另写探针复跑确认）。
    判分是**输出逐字比对**，而本机 CPython 3.12.10 上这个形状**事实上是原子的**：

    | 形状 | 3 只猫 × 100 万次，跑 3 遍 |
    |---|---|
    | 紧圈 `碗[0] = 碗[0] + 1`（学员最自然的写法） | 3,000,000 → **3,000,000 / 3,000,000 / 3,000,000，一次没丢** |
    | 把切换点塞进读-改-写中间（`v = 碗[0]` → `sleep(0)` → `碗[0] = v + 1`） | 3,000,000 → **1,000,106 / 1,000,085 / 1,000,000，丢得干干净净** |

    原因是 3.11+ 的 eval breaker 只在**回跳/调用**处检查，而 `for` 循环的回跳落在**圈与圈之间**，不在「读-改-写」中间。
    **后果**：一道「用锁保护共用大碗」的题，**学员不写锁也能过**。所以 ——
    - 题面可以写「**有可能**读到同一个旧数」，**绝不许**写「一定会少记 / 一定会算错」：那是一句**跑不出来**的断言，写了就是拿没验过的话教人；
    - 锁的教学价值靠**解析**，不靠判分，这是这一档题目的固有性质，**不是模板写坏了**；
    - 想真判出「锁有没有生效」，得让坏法**换一种坏**（缺 `if __name__ == '__main__':` 抛 `RuntimeError`、`args` 没打包抛 `TypeError`、篮子没共享恒印 `0` —— 批 7 课 04 的三种坏法都是这样选的，全部确定、不依赖竞态）。
13. **死锁型坏法是靠 20 秒超时判出来的 —— 那是设计，不是故障，别去"修"**（2026-09-16 批 7 课 03 实测）。
    `RUN_TIMEOUT_MS = 20_000`（`scripts/lib/bank-verify.mjs:40`，**全局常量，模板改不了它**）。
    「锁只 `acquire` 不 `release`」这种坏法**不吐报错，只在屏幕上留一片安静**，只能等超时 —— 于是每个实例 20s、两个实例 **40s/次**，
    该模板每跑一次 `gen-bank` 或 `check-bank --all` 都要付这 40s。
    ⚠️ 应用发给学员的运行超时是 **10s**（`runTimeoutSec` 默认值），比闸门短 —— 学员看到的是「超时」而不是被讲清楚的「死锁」，错误库也匹配不到它。
    这笔时间**接受**：死锁是真实存在的 bug 类别，且判据确定（永远超时，不看运气）。但要先知道它会慢，别把它当成偶发卡顿去重试。
14. **输出里带花括号的题（JSON / 字典），样例输出「摆不出来」**（2026-09-16 批 8 课 07 的代理撞上，我读了判据源码 + 全库扫了一遍确认）。
    `leftoverPlaceholders()` 认的形状是 `\{[^{}\n]{1,60}\}`（`scripts/lib/bank-verify.mjs:158`），**很宽**；而 `finalizeDraft()` 拿它扫**题面和解析**，
    `{"名字": "小鱼干", "口味": "原味"}` 正好落在这个形状里 —— 于是「照任务书把 `{sampleOutput}` 填进题面」当场**定稿失败**（`gen-bank` 退出码 1）。
    **这不是缺陷，是那条例行检查的必然代价**：它的活是"抓住没填掉的占位符"，认宽才抓得住 `{ n }` `{a + b}` `{中文}` 这些写坏的样子。
    实测佐证：**全库 401 道题、题面与解析里命中该形状的 = 0 处**（`node` 读原始字节扫的）—— 说明这道关一直在生效，每一批的写手都躲开了。
    躲法（`docs/14 §5.4` 已写全，**这里只说结论**）：**用文字描述标点形状**（大括号、双引号、冒号后一个空格、逗号后一个空格），别把样例输出摆出来；
    或者把输出设计成不带花括号的形状（逐行 `名字`↵`数量` 那种）。
    ⚠️ **批 8 的任务书必读清单里漏了 §5.4** —— 写手是自己撞上才发现、并把它当成"没人写过的结构性缺陷"报上来的。
    **以后写题库任务书，必读清单里必须带 §5.4**（f-string 与花括号这两道关都在那一节）。
15. **shell 会把反斜杠减半 —— 数反斜杠别用 `grep`，读原始字节**（2026-09-16 批 8 我自己踩的，`od -c` 当场印证）。
    实测：我在命令里写 `'\\\\u'`（4 个反斜杠），**shell 实际只收到 2 个**（`printf '%s' … | od -c` → `\ \ u`）；
    于是 `grep -c` 报「课 07 课文有 **6 行**有问题」，而我用 node 读原始字节数是 **0 处双反斜杠、19 处单反斜杠、跨 6 行**。
    **两个读数各自都对，是我把它们当成同一件事了**（`grep -c` 数的是**行**，且模式早被减半成了"单反斜杠"）—— 差一点照着那个 6 去改 6 行**本来就正确**的正文。
    规矩：① 要数反斜杠 / 引号这类会被 shell 吃掉的字符，**用 node 读原始字节**（`<workspace>\_probe-backslash.mjs` 就是干这个的）；
    ② 非要用 shell，先 `printf '%s' '<你的模式>' | od -c` **看清它到底收到了什么**，别猜。
16. **题面「从外面给」的每一个输入都该进 `params`，否则实例展开变不动它**（2026-09-16 批 8 课 08，我自己读产物量出来的）。
    `py-s3-sqlite-threshold` 的题面写着「**外面只给一个数**，就是门槛」，可 `params` 里只有 `x1/x2/x3`（三格货的条数），**门槛不在里面** ——
    它只活在实例的 `stdin` 字段里。实测两个实例：`-000` 是 `stdin:"3\n"` + 货 2/5/8，`-007` 也是 `stdin:"3\n"` + 货 3/6/9 ——
    **两个实例的门槛都落在 3**。这不是同题重复（数据、输出、行数都不同），但缺了一维可变性，本可以更好。
    **规矩**：题面里凡是「从外面给」的输入，**都要在 `params` 里有一格**（哪怕它同时出现在 `stdinSpec` 里）——
    这样 `spreadIndices` 才有机会去变它。只写进 `stdinSpec` 的输入，等于**放弃了它的可变性**。
17. **能用「判分输入」把题面要求变成可判的，就该这么办**（2026-09-16 批 8 课 08 我自己真跑验证的，代理报的是「拦不住，认了」）。
    题面写死了「名字和条数都要从投喂口递进去（口令里留两个 `?`）—— **不许把名字缝进口令里**」，
    但判分**只比对输出**，缝口令的解法照样能过 —— 代理如实报了这个固有缺口（和 §9.7 第 12 条同一类）。
    本喵拿真跑量了一遍（`<workspace>\_probe-splice-rule.py`，同一份题、只换「判分用的名字」）：

    | 解法 | 名字 = `冻干块`（无撇号） | 名字 = `铲屎官's猫粮`（ASCII 撇号） |
    |---|---|---|
    | f-string 缝口令 | ✅ **过**（缺口就在这） | ❌ **当场红** `sqlite3.OperationalError: near "s猫粮": syntax error` |
    | 投喂口 `(?, ?)` | ✅ 过 | ✅ 过 |

    **结论**：把「判分用的名字」换成**带 ASCII 撇号的**，缝口令的人**必红**，而正确解法一点不受影响。
    这条路子把一句**写在题面上的要求**变成了**判分真的拦得住的要求**，而且拦下来时给出的正是本课教的那个报错 —— 教学上完全对靶。
    **规矩**：设计模板时，凡是题面写死了某个手法（尤其是 `INSERT` 走投喂口这类），**先问一句「换一个判分输入，能不能让违规解法跑不过？」** 能就换。
    ⚠️ 诚实交代：批 8 已出货的那两条 `new-row` 实例**没有返工**（它们的题面、输出、真跑都是对的，只是这条要求拦不住），
    本条作为**面向后面 C/C++/Java 题库的规矩**落地 —— 下一批写 `new-row` 这类模板时，`params` 的 `name` 取值域里就该有一个带撇号的名字。

### 9.8 ⚠️ 还没堵的缺口：「模板改了、产物没重跑」没有任何闸门看得见

**形状和本节前六次一样，但这次缺的不是判据，是"判据与产物之间的那条线"。**

`gen-bank.mjs` 的跳过判据是**参数组合**（见 9.7 第 2 条），`check-bank.mjs` 的信任戳是**题自身的内容哈希**。两条判据都不看模板 —— 于是这个状态可以一路全绿：

> 改了一条模板的题面/解析 → 忘了重跑 → **题库产物里还是旧文案**，学员看到的是旧的那份；所有闸门照常绿。

**现在没红，但只是靠纪律撑着**：§9.5 那批术语修正之所以能确认"确实上线了"，靠的是**术语闸门恰好也会扫题库产物**（`content-validate.mjs:103` 那条判据被 `check-bank.mjs` 共用）—— 凡是"修了术语"的改动，漏重跑一定会被那条判据红出来。**而修错别字、改措辞、补一句解释这类不改变术语判定的改动，是没有网兜的。**

**想补的话，最便宜的做法不是"重跑一遍比对"**（那要给 161 道题各起一次编译器），而是让生成器**把模板的字节哈希写进条目**（如 `templateHash`），闸门只比这一个哈希 —— 纯 JS、零编译。代价要说清：① 条目多一个字段，`contentHash` 要不要把它算进去得先定（算进去 = 现有 161 道的戳一次性全失效，要重跑一遍）；② 已经产出的条目没有这个字段，得先全量重产。**所以它是一次"要专门排期"的改动，不是顺手能加的** —— 先记在这里，等某一批正好要全量重产时一起做。

### 9.9 ⚠️→✅ 曾是个缺口：`codefill` 的答案没有机器背书（2026-09-16 核实，**当天封口**）

**形状和本节前几次一样，但这次连"没验过"这件事本身都是被一句假话藏起来的。**

`check-code-answers.mjs` 的头部原先列了一张分工表，其中一行写着：

> `choice / fill / codefill   纯字符串比对，答案就在题里，校验器看一眼就知道`

对 `choice` 这句成立（答案是**下标**，越界、空选项校验器真验得动）。**对 `codefill` 不成立**：它的答案是**代码**，而 `content-validate.mjs` 对 `codefill` 只验**形状** —— 空位个数和 `____` 对得上、答案非空、不含换行。**那段代码从来没有被跑过一次。** 两道真跑闸门也都不管它：`check-code-answers.mjs:134` 是 `if (q.type !== 'code') continue`，`check-question-code.mjs` 只扫 `codefix` / `codewrite`。

于是这个状态一路全绿：**填错空位的答案照样发布**，而且是双向坏 —— 照着错的学，学到错的东西；把代码读对、写对的学员，比对的是那个错答案，**判他错**（和 `check-question-code.mjs` 头部讲的"学员永远做不对"是同一类，只是这次的洞在 `codefill` 上）。

**当前规模**：`node scripts/check-code-answers.mjs --list` 每次会打印现值（2026-09-16 实测 **43 道**；这个数会随批次涨，别抄进别的地方）。该脚本现在**会把跳过这件事打印出来**，不再静默 —— 「静默跳过 = 把没验过伪装成验过了」这条铁律的直接落地。

**这个洞在别处其实早写着，只有闸门那头说了假话**：`docs/09` §7.3 的每日挑战分档表里，`codefill` 被标成「⛔ 只从本地题库抽」，理由是一整句实话 —— 空位答案是个**精确字符串**，AI 写偏一点（`range(3)` vs `range(1,4)`）就无解，「**且没有便宜的验法**」。所以「没有验法」在规范侧是承认的，只有 `check-code-answers.mjs` 头部把它说成了「校验器看一眼就知道」。顺带：这道真跑闸门补上之后，「本地题库里的 codefill 可不可信」才第一次有机器答案 —— §7.3 那条分档将来要不要放宽，依据就在这里。

**补法（想清楚了，但不在本批做）**：把 `blanks[i].answer` 按空位顺序填回 `code` → 跑 → **不许编译/运行报错**。这是纯增量、零新字段，判据只有一条，真跑一次就能红：把 `yield` 写成 `return`，替换后的程序会 `TypeError`。

**先量了最便宜的那一档（2026-09-16 实测）**：把答案填回空位后只**编译**（`compile(src,'<x>','exec')`，不执行）—— 41 道 Python 的 codefill **全部通过**，另有 2 道是 C / Java（要真编译就得起 gcc/javac，本次不碰；`c-stage3-03/q8`、`java-stage1-16/q8`）。**这只是一条下界**：编译通过 ≠ 答案对（`range(3)` 与 `range(1,4)` 都编译得过）。

**写这道闸门时必踩的两个坑（实测，探针在 `<workspace>\_codefill-parse-probe.mjs`，带自检）**：
1. **不能用 `ast.parse`** —— 它传 `PyCF_ONLY_AST`，**跳过符号表检查**，模块级的 `return` / `yield` 照单全收，而那正是本题型最常见的坏答案。必须 `compile(..., 'exec')` 才会报 `'return' outside function`。探针的自检当场抓出了这一点（"模块级 return 漏判"）。
2. **源码不能走 `sys.stdin`** —— Windows 上 python 的 stdin 按本地编码（本机 GBK）+ `surrogateescape` 解码，UTF-8 的中文标识符（`def 加特效(fn):`）会变成孤立代理对，报 `UnicodeEncodeError: surrogates not allowed`。**第一次跑因此报出"26 道语法不通过"，26 道全是假的。** 走 base64 + `argv` 就绕开了。

**要如实说清它验不到什么**：它只能证明"填进去能编译/能跑"，**证不了"跑出来是对的"** —— 后者需要一个预期输出，而 `codefill` 没有这个字段（它的判分是字符串比对，本来不需要）。所以这道闸门是"拦住"级别的，不是"保证"级别的。

**两个必须先定的设计点**（不定就会变成新的静默跳过）：
1. **不是每道 `codefill` 的成品都是完整程序**（有的空位在类体里、有的只是片段）。这类必须**显式豁免并写明理由**，照抄 `check-code-answers.mjs` 那张 `豁免` 表的形式，**不许写成"跑不起来就跳过"** —— 那等于给这道闸门开了个后门。
2. **跑一遍 43+ 道题要起 43+ 次解释器**，属于真跑闸门，**不能和写内容的子代理并发**（见 `gates-race-with-subagents`），要排在没有代理在跑的空档。

**再往上量了一档：抽查 5 道，语义全对（2026-09-16 实测）**。挑的是最近落地的批 5 五课各一道 codefill，把答案填回空位**真跑**，拿输出对题面承诺的东西：

| 课 / 题 | 空位答案 | 真跑输出 | 判 |
|---|---|---|---|
| `python-stage2-06/q4` | `choice` | `猫粮` | ✓ 从那一排碗里随便挑了一样 |
| `python-stage2-07/q4` | `Animal` | `喵～` | ✓ 子类改写的招式被调到了 |
| `python-stage2-08/q4` | `__add__` | `<__main__.Bowl object at 0x…>` | ✓ 名字对（`+` 没炸），但见下 |
| `python-stage2-09/q4` | `包装` | `【特效：开始】/喵～/【特效：结束】` | ✓ 壳被叼回去且真的套上了 |
| `python-stage2-10/q4` | `yield`×2 | `1`↵`2` | ✓ 一条一条递 |

⚠️ **这 5 道是人工判读的，不是机器判的**：探针（`<workspace>\_codefill-run-probe.mjs`）只打印题面、空位答案、真跑输出，**没有断言** —— 因为 `codefill` 没有 `expectedOutput` 可断言（这正是 §9.9 开头那个缺口的另一面）。**所以"5/5 全对"这句话的可信度取决于读的人，不取决于脚本**，别把它写成闸门结论。剩下 36 道 Python codefill 只有"编译过"那一档，语义仍是未验状态。

**一个必须记住的实现细节**：探针第一版是手搓 `execFileSync('python', …, {encoding:'utf8'})`，五道里四道的中文输出全是乱码（`è��` / `����`）—— **不是内容坏，是读端编码错**：Windows 上 Python 往管道里吐的是本地编码（GBK），按 utf8 硬解就成这样。改用 `scripts/lib/run-code.mjs` 的 `runBlock` 之后干净了（它的 `decodeOutput()` 是 utf8 → gbk 依次试的）。**将来这道闸门必须走 `runBlock`，不许自己 spawn** —— 否则又是"判据两处实现"，而且这一处的漂法是**把好答案报成乱码**，和 §9.9 上面那个 26 道假失败是同一个坑的两副面孔。

**一处次要观察（不是缺陷，不必修）**：`python-stage2-08/q4` 的演示程序跑出来是个**内存地址**。判分不受影响（`codefill` 比的是空位答案，不是输出），但学员自己跑一遍看到 `<__main__.Bowl object at 0x…>` 是看不出"加起来了"的 —— 教学价值打了折（补个 `__str__` 或打印碗里的东西就直观了）。记一笔，不改。

### 9.9-bis ✅ 当天就封了口：`codefill` 的答案现在有真跑背书

上面那一节写的是**缺口当时的样子**，保留不动。同一天它就被堵上了，做法和上面「补法」那段想的一样：`check-code-answers.mjs` 里加了第三节 —— 把 `blanks[i].answer` 按空位顺序填回 `code`，**真跑一遍**（走 `scripts/lib/run-code.mjs` 的 `runBlock`，不自己 spawn）；`accept[]` 里每一条也填回去照跑。

**顺序照规矩走：先证伪、再上岗。**
1. 沙箱 `<workspace>\_codefill-fixture\` 先跑红（**退出码 1**：一道 `yield` 被写成 `return`、一条 accept 是 `SyntaxError`、一道在读 stdin），期望值钉在它的 `README.md` 里；
2. 才让它对真题库说话 —— **真库退出码 0**：

| 行 | 真库实测（2026-09-16） |
|---|---|
| `code` | ✓ 真跑对得上 **82**　∅ 显式豁免 2　✗ 0 |
| `codefill` | ✓ 填回去跑得起来 **47**　∅ 显式豁免 1　✗ 0 |
| `accept` | ✓ 等价答案也跑得起来 **36**　✗ 0 |

唯一那条 codefill 豁免是 `python-stage1-05/q7` —— 它**本来就要读 stdin**（那一课就是「输入与输出」，第一行就是 `input()`），而这个题型没有 stdin 字段，闸门只能喂空输入。**豁免不是一句「我信它」**：`<workspace>\_probe-q7.mjs` 喂 `小橘\n` 之后，主答案与三条 accept 全部印出题面承诺的「你是谁喵？小橘，欢迎光临喵」，反证 `{nane}`（拼错）当场 `NameError`。理由和证据都写在那张表里。

**上线第一天就翻出 5 条真缺陷，零假红** —— 其中**闸门自己抓的 2 条**（下表 #1 #2）、**顺着它的盲区警告人眼读出的 3 条**（#3 #4 #5，第 5 条见下文）。而且是**同一种病**：把「跑不起来 / 根本不存在的写法」当成了「这种写法也对」。

| # | 位置 | 题型 | 收的写法 | 谁发现的 | 填回去真跑出来 | 处理 |
|---|---|---|---|---|---|---|
| 1 | `c-stage3-03/q8` | codefill | accept `null` | 闸门 | `error: 'null' undeclared` | 删掉（C 里只有 `NULL`） |
| 2 | `python-stage2-15/q4` | codefill | accept 裸 `w` | 闸门 | `NameError: name 'w' is not defined` | 删掉（`"w"` / `'w'` 留着） |
| 3 | `c-stage3-03/q5` | **fill** | accept `null` | 人眼 | —— 这个题型跑不了，见下 | 删掉 |
| 4 | `c-stage2-04/q4` | **fill** | accept `null` | 人眼 | 同上 | 删掉 |
| 5 | `common-08/q5` | **fill** | accept `int()` | 人眼 | 填回题面给的形状 `n = ____(n)` 会变成 `n = int()(n)`；`int()` 返回 `0`、`0` 不可调用 | 删掉（题面本来就限了「三个字母」） |

**第 3、4 条暴露了这道闸门自己的一条边界，必须写出来，否则又是一次静默跳过**：
`fill` 题**没有代码上下文**，没什么可执行的，所以这道闸门在结构上**永远验不到它的 accept**。而 `#1` 与 `#3` 是同一支笔、同一种错（`null`），只在有代码上下文的那一半现了形。所以汇总里现在**主动把这件事喊出来**（不喊 = 默许读的人以为它也验过了）：

> ⚠️ 代码语言的 fill 有 7 处 accept（19 条写法，4 份文件）**这道闸门跑不了** —— fill 没有代码上下文。
> · common 的 fill 有 12 处 accept（18 条写法）：文字同义词容错，本来就不需要跑

（两类**必须分开说**：代码语言那些是**真盲区**；common 那些是**本来就不需要跑**。混成一句「跑不了」会凭空造出一笔并不存在的欠账。）

**这 7 处（19 条写法）在 2026-09-16 被逐条人眼读过，判据是一句话**：

> **把它填回题面给出的代码形状里，那段代码还跑得通吗？** 跑不通就是宽容过头了。

按这条又摘掉 1 条：`common-08/q5` 收的 `int()` —— 题面给的形状是 `n = ____(n)`，填进去是 `n = int()(n)`，而 `int()` 返回 `0`、`0` 不可调用，真跑必崩。
**留着的都是正当的**：`int()` / `float()` / `free()` 出现在「写出这一招的**名字**就行」这类题面里（题面没给代码形状，判据不适用）；`python`（小写）是语言名的大小写，不是代码 token。

⚠️ **这条边界只能人眼守，没有机械判据**：`null` 和 `free()` 在形状上一模一样（都是「答案 + 一点变形」），能分开它们的只有题面。**别把这 7 处当成「闸门管着的」** —— 它们是被**读过一遍**的，不是被**验过**的。

**过程中自己踩的一个坑，记一笔**：汇总那行我第一版写成「代码语言的 19 条」+「common 的 12 条」，两个数**单位不同**（前者是 accept 写法条数，后者是题目处数）却并排摆着，看着像一把尺子量出来的。**同一行里两个数单位不一致，比两个数都错还坏** —— 读的人会照着其中一个去核对，然后得出一个错的结论。现在两个都标了单位（`7 处 accept（19 条写法）`）。

**它仍然证不到的**（和上一节说的一样，没有变）：既跑得起来、又跑错了的答案（`range(3)` vs `range(1,4)`）它一个都拦不住。**这道闸门是「拦住」级别的，不是「保证」级别的**。给 `codefill` 补语义背书要么加 `expectedOutput` 字段（动题型契约），要么继续靠人工抽读 —— 两件都不在本批。
