## 0. 摘要与待拍板事项

### 0.1 一句话方案

**本地档案保持第一真源、离线永远完整可用；账号是可选增强**——登录后由主进程直连境内 BaaS（推荐阿里云 PolarDB PostgreSQL 版 Supabase 应用，备选腾讯云 CloudBase），把 profile / wrongbook / favorites / practice 四份 JSON 以「拉取→客户端合并→条件写回」的方式双向同步；API Key 与所有凭据永不入云、永不过渲染层；同步冲突用客户端合并函数裁决，合并规则逐字段定义（§8.3），并有墓碑机制保证删除不会被别的设备复活。

## 1. 现状底账（勘察结论摘要）

### 1.1 数据面

- 7 份 JSON 平铺在 `storageDir()`：config / profile / wrongbook / favorites / practice / ai-cache / challenge。统一信封 `{version, payload}`，`json-store` 原子写（tmp+rename+…bak），读口容忍、写口严格双闸门。
- 惰性迁移：读时按版本号分发 `migrate()`，幂等、纯函数、吃 `unknown`、保留关键字段；`needsRewrite` 触发条件写回。读口单点：`readConfig/readProfile/readWrongbook/readFavorites/readPractice`（src/main/index.ts:142-264）。
- 版本常量：config v9 / profile v2 / wrongbook v1 / favorites v1 / practice v1 / ai-cache v1；challenge **没有版本常量、没有 normalize 读口**（两处例外）。
- **单档案**：没有任何多账号分区。主进程 7 个 store 是模块级常量、读口不带身份参数；渲染层 11 个 Pinia store 启动时一次性加载。
- 关键字段形状（合并设计直接依赖，已逐条对源码核实）：
  - `UserProfile { learned: string[], favorites: string[], history: LessonHistoryEntry[], stats, rewards }`；`LessonHistoryEntry { lessonId, finishedAt }`；`ProfileRewards { gallery, perfectPasses }`。
  - `markLearned(lessonId, learned)` 和 `toggleFavorite` 都是**双向**的（LessonDetailView.vue:132-133、progress.ts:101/124）→ 删除是真实操作，合并必须处理。
  - `WrongBookEntry` 自带 `cleared/clearedAt`（自动毕业，答错复活）与 `removed/removedAt`（手动软删，复活是**删字段**）→ 它已经自带墓碑，是全项目最成熟的可合并结构。
  - `FavoriteItem { key, lessonId, qid, addedAt, folderId?, note? }` 无软删字段；`FavoriteFolder { id, name, createdAt }`；删文件夹=条目回未分组（dropOrphanFolders）。
  - `PracticeSession { id: number 自增（主进程铸）, at, mode, items[] }`；`PRACTICE_KEEP_SESSIONS = 5000`；哨兵课号挡在库外。

### 1.2 通道与网络面

- 27 条 IPC，单一真源 `src/shared/ipc-channels.ts`，preload 白名单 27 方法，`ipc-wiring.test.ts` 静态闸门。
- **唯一网络出口** = `src/main/ai/deepseek.ts`，注入式 `AiDeps = { fetch, getConfig, signal }`；apiKey 只进主进程、永不回渲染层；ai-cache 键 = sha256(model+system+user)，不含 Key。
- 渲染层 CSP `default-src 'self'`，没有 connect-src；contextIsolation:true、sandbox:false、单实例锁。

## 2. 总口径与红线修订

### 2.1 总口径（拍板即生效的设计原则）

1. **本地第一真源**：不登录 = 与今天完全一样；所有功能离线可用。云是副本，不是依赖。
2. **同步失败永远静默降级**：网络问题不影响任何本地功能，只影响侧栏徽章状态。
3. **凭据红线**：apiKey、密码、令牌、service_role key 不入云（Key 相关）、不过渲染层（令牌）、不入日志、不进 AI prompt。
4. **可选增强**：用户永远可以只用游客模式，且游客进度不因登录而移动或删除。
5. **本地写同等级一致**：本地写不是「整份覆盖」而是「读-改-写 + 版本条件写」（§8.2 本地写协议）；切号/登出/注销有显式写入干涸协议（§3.5.1）。

### 2.2 铁律 3 修订措辞（提案）

原文：「绝不搭建自建服务器。一切网络能力 = 客户端直连第三方 API + 用户自带 Key。」

建议改为：

> **铁律 3（修订）：不搭建、不自营服务器。一切网络能力 = 主进程直连第三方服务：①第三方 AI API（DeepSeek，用户自带 Key）；②第三方 BaaS 托管服务（账号与云同步，可选功能，失败静默降级为纯本地）。托管平台的运维归云厂商；我们只定义数据形状、权限规则与合并逻辑。API Key 永不上云。**

修订后原铁律的立意（不自营、不产生运维负担、用户自带 Key）全部保留，只是把「BaaS 托管」从违禁名单里明确放行。

## 3. 问题① 解耦：五层分层与改动影响矩阵

### 3.1 分层图

```
L1 视图层    views/ + components/           只画 + 调 store，不碰数据规则
L2 渲染服务层 stores/ + lib/                 渲染侧状态与文案（copy.ts）；新增 stores/account.ts
────────────── IPC 契约（唯一真源 src/shared/ipc-channels.ts + preload 白名单）──────────────
L3 契约层    ipc-channels.ts + preload       27→36 条通道；渲染层永远只见 AccountState，不见令牌
L4 主进程服务层 src/main/                    读写收口（7 文件 + StoreBox）+ 新增 cloud/ 模块
L5 云适配层  src/main/cloud/provider/        接口 CloudProvider 的两个实现（supabase / cloudbase），可整体替换
```

**关键纪律（全部沿用现有先例）**：

- 渲染层只认识 `AccountState`（登录态/昵称/头像哈希/同步状态），**令牌与密码永不 main→renderer**——与 apiKey 先例完全同构（密码只在注册/登录那一刻 renderer→main 单程经过一次，提交后即清）。
- 网络全部在主进程 → 渲染层**无出网调用面**（CSP 保持 `default-src 'self'`）。注意：这**不等于**渲染层安全已经够——红队复核发现既有导航面有三个实洞（`form-action` 未禁、`openExternal` 不校验 URL、无 `will-navigate` 守卫；窗口一旦被导航走，外部页面能拿到整个 IPC 桥），列入 §3.7 随 P10 一起加固。
- 云适配层写成接口 + 注入，测试用假 transport——与 `AiDeps` 先例同构（新增 `CloudDeps = { fetch, tokenStore, readConfig, now }`）。

### 3.5 关键数据流

- **登录**：LoginPanel → `account:login` → session 拿令牌（密文写 `accounts/<id>/session.bin`）→ 首次登录走收编对话（§8.4）→ **干涸协议**（§3.5.1）→ StoreBox 指向 `accounts/<id>/`、epoch+1 → 各 store 全量重载。
- **离线**：一切照旧；`sync:now` 直接返回 `offline`；徽章变灰。
- **同步**：渲染层调度（§8.2）→ 主进程拉/合并/写盘/条件写回 → 返回 changedDocs → 协调器在安全点重载对应 store。
- **登出**：干涸协议 → StoreBox 指回根目录（客人档案原样）、epoch+1 → 重载；密文删除。
- **切号/注销**：注销时序 = 服务端删除成功**才**动本地；干涸协议 → 按勾选删本地账号目录 → 指回客人档案。任一步失败：整单失败、保留本地、给重试入口（**不做「看起来删了」**）。

**§3.5.1 写入干涸协议（登录/登出/切号/注销共用）**：① 冻结新写（渲染层守卫 + 相关按钮禁用）→ ② flush 所有防抖并 await → ③ 取消全部防抖定时器 → ④ await 在飞请求（同步 / AI 抽题）→ ⑤ 切换 StoreBox（epoch+1；写通道旧 epoch 一律拒绝）→ ⑥ 重载 → ⑦ 解冻。主进程侧：sync 与所有写口在启动时捕获 accountId/epoch，写盘前校验不符即丢弃——**存档边界不靠时序，靠机制**（否则在飞的同步/抽题/防抖定时器会把 A 的数据写进刚切到的 B，注销时还会把刚删的目录重建）。

### 3.6 主进程改造点（改动清单）

1. `main/index.ts` 的 7 个模块级 store 常量 → `StoreBox`（`createStores(baseDir)`），读口经「当前 box」代理（getter，不捕获常量——切号即生效）。
2. **写口从「白名单重建」改为「保留区 apply」**（红队头号修复之一）：今天 profile:save 是对象字面量重建（只列六键）、sanitizeFavorites 只拼三键——任何新字段（墓碑、updatedAt、未来未知键）都会被下一次普通保存静默抹掉。改造后每个文档的写口 = 读磁盘**原始 JSON**（不经 normalize）为基底 → 替换白名单业务字段 → **保留未知键与墓碑区** → 写回。墓碑归主进程独占：读口不把墓碑交给渲染层；写口自己从磁盘取旧墓碑、按集合增减追加/撤销（§8.3）。
3. profile v2→v3、favorites v1→v2、practice v1→v2 迁移（§8.3），在 P10.1 完成——先在本地版落地并过全部既有测试，再动云。
4. **本地条件写**（§8.2 本地写协议）：读口带出 `{epoch, rev}`；写通道校验不符即拒绝并回读新数据；每文档一条串行写队列（主进程内），同步写回同样排队。

### 3.7 既有安全加固项（红队发现，随 P10 一起做，与用户系统解耦但同批）

| # | 洞（现仓库实况） | 加固 |
|---|---|---|
| 1 | 全仓库无 `will-navigate` / `will-frame-navigate` 守卫；主窗口被导航到外部页后 preload 会随文档重新注入，外部页面主世界直接拿到整套 `window.miai`（27 方法，含 runCode 任意代码执行） | 非自家 `file://` 页一律 `preventDefault` + 交系统浏览器 |

### 5.3 推荐与实验定稿流程

**主选：阿里云 PolarDB PostgreSQL 版 Supabase 应用**。核心理由：GA 在售（不是公测）、有白纸黑字的免费试用与公开价格、标准 Supabase 栈让「主进程 Node 直连 + RLS 权限」这条最干净的路径成立、且这正是主人原始直觉（docs/20 写过「Supabase/LeanCloud 类」）的现实对应物。

**备选：腾讯云 CloudBase**。核心理由：生态与文档成熟、等保三级背书明确、用户名密码认证原生；但桌面端零官方指引，需要实验证死两条路（Node 形态 SDK / 云函数中转）。

**决策实验（半天，P10.0，主备各跑一遍）**：

基础五步（两家都要跑）：注册 → 用一次性脚本写入一小段 JSON → 读回 → **双账号互读（A 的凭据读 B 的数据，必须失败）** → 导出一次。
Supabase 路线加测：① 主进程 Electron 里跑 supabase-js（Node 形态）直连；② 关闭邮箱确认或确认「用户名+`@miai.local` 伪邮箱」注册可行（免费版邮件通道额度 ⚠️未核实）；③ **迁移建表 + 建 policy，验证 RLS 实际生效**（迁移文件建表默认**不开** RLS——必须实测并写进 check 脚本）；④ **部署一个最小 edge function（含环境变量与服务端密钥取用）**；⑤ 免费版是否有休眠/冷启动。
CloudBase 路线加测：① Web SDK 的「安全来源」能否登记 file://（预期不能，走 Node 形态或云函数）；② 自定义登录私钥发票据链跑通；③ 安全规则下双账号**四向**越权必败（读/PATCH/DELETE/INSERT）；④ **Node 形态下令牌落点与自动刷新（能否自定义存储、不落 localStorage）**——撞 §6.2 红线就得在 P10.0 就发现。

**实验结论落地判据**：五步基础 + 加测全绿 → 定稿该平台；主选出红 → 备选顶上；两家都红 → 回来讨论「自架轻量服务器」兜底（明确不在本阶段范围）。

## 6. 问题④ 用户数据安全

### 6.1 密码

- 传输：仅 HTTPS（BaaS 官方域名），本地不做任何「加密后传输」画蛇添足。
- 存储：**服务端哈希**——Supabase 路线用 GoTrue 内置（bcrypt）；CloudBase 路线用其内置；**客户端本地永不落盘密码**（不记住密码；如需「自动登录」存的是令牌不是密码）。
- 收集端纪律：PasswordField 一次性提交后即清（不移入任何 pinia 状态）；强度下限 8 位；登录失败走服务端限流（GoTrue 内置）。
- 找回：v1 不做（无邮箱/短信通道，见 §10）；文案明确提示「密码请自己记牢」。

### 6.2 令牌

- 形态：Supabase 系 = access（约 1h）+ refresh（30d，轮换）；CloudBase 系 = 自定义票据/会话 token。
- **只存主进程 `safeStorage`（Windows 下即 DPAPI 当前用户加密）**，绝不放 localStorage、绝不进渲染层。渲染层只拿到 `AccountState`（无令牌字段）。
- **令牌按账号分槽、密文自带身份**（红队修复）：密文文件 = `accounts/<accountId>/session.bin`，明文结构 `{sub, access, refresh, expiresAt}`，`sub` 必须等于目录名。启动时扫描 `accounts/*/session.bin`：恰一份 → 用之；`sub` 与目录不符 → 拒绝并清掉该密文、停在未登录态（**不静默改目录**）；出现多份 → 全部清除、要求重新登录。**禁止用「设备级上次登录账号」指针驱动档案目录**——目录永远从令牌自己的 sub 推导，从机制上消灭同机多账号串号（「A 的令牌配上 B 的目录」这个场景必须失败）。
- 解不开（换 Windows 用户/重装系统/DPAPI 失效）→ 视作未登录，静默要求重新登录，**不许崩、不许静默清数据**。
- 刷新失败连续 N 次 → 置 `expired`，推 `account:changed`，UI 弹重新登录。

### 6.3 权限（「A 绝不可能通过 API 读到 B 的数据」）

**Supabase 路线用 RLS 逐表锁死**（迁移文件里显式写，不依赖 dashboard 默认）：

```sql
alter table public.profiles  enable row level security;
alter table public.user_docs enable row level security;
alter table public.app_meta  enable row level security;   -- 红队补漏：漏了这张，anon key 就能改「协议下限」停掉所有人的同步
revoke all on public.profiles, public.user_docs, public.app_meta from anon, authenticated;
grant select on public.app_meta to authenticated;          -- 只读；写留给人肉/服务端

create policy own_row on public.profiles
  for all to authenticated
  using (user_id = auth.uid()) with check (user_id = auth.uid());

create policy own_row on public.user_docs
  for all to authenticated
  using (user_id = auth.uid()) with check (user_id = auth.uid());
```

存储桶 `avatars`（私有）：策略写全——`for select/insert/update/delete to authenticated using (bucket_id='avatars' and (storage.foldername(name))[1] = (select auth.uid()::text))`，insert/update 另配同名 `with check`；桶级开 `file_size_limit=262144`、`allowed_mime_types=['image/png']`；主进程在 `account:set-avatar` 入口做 PNG 魔数 + 字节上限硬校验（不需图像库，零原生依赖不破）。路径逃逸（`uid/../`）行为属未核实项，P10.0 实测一次再下结论。
**红线**：`service_role` key 只出现在云函数环境变量里，绝进客户端、绝不进仓库；anon key 可进客户端（它本身无权限，权限全在 RLS）。
**CloudBase 路线对应物**：数据库安全规则 `doc._openid == auth.openid`、存储安全规则 `resource.openid`（**仅对客户端直连生效**）。若走云函数中转：**只有一层防线——函数代码**（官方明确「数据库安全规则对服务端 API Key 不生效」，云函数用管理员级凭据执行）；验收直接打云函数 URL（带 A 令牌 + 显式传 B 的 uid 入参，必须失败），并核对每个数据入口只从请求头令牌取 uid、不信任何入参 uid。

**强制验收（不靠承诺）**：双账号**读、写（PATCH）、删（DELETE）、插（INSERT 带 user_id=B）四向**全测——只测读证明不了 `with check` 写没写（这恰是最容易漏的子句，漏了 = A 能改/删 B 的整份进度）；每向都必须失败（空集/0 行/403），全部进 §12 云侧闸门，**种坏值（临时删 policy）必须见红**后才算闸门有效。

### 6.4 边界纪律（照 apiKey 先例的成文法）

| 凭据 | 可存在的最大范围 |
|---|---|
| apiKey | 主进程内存 + 本机 config.json（已有现状，不变）；永不上云 |
| 用户密码 | renderer→main 单程一次；服务端哈希；其余任何地方不得出现 |
| access/refresh 令牌 | 主进程内存 + safeStorage 密文；永不进渲染层/日志/云端 payload |
| service_role / 私钥 | 仅云函数环境变量；永不进客户端与仓库 |

### 6.5 合规落点（查证事实 + 合理推断，最终以云厂商文档为准；不构成法律意见）

- **数据不出境**：选境内地域即可满足；这是排除官方 Supabase 的唯一硬理由。
- **无障碍依据**：桌面应用直连 BaaS API **未发现** ICP/APP 备案义务（文本推断，未核实）→ 保守做法是不用自建域名。
- **PIPL 小体量简化义务**（2026-09-01 生效，<10 万用户适用）：需要 **隐私政策**（设置页入口 + 注册时勾选同意）、**账号注销**（硬义务）、**查阅/复制/导出**（`account:export-data`）、**最小收集**（只要用户名+密码，不收手机号/生日/真名——三家云个人身份也发不了短信，这是设计上的互相印证）。
- **未满 14 岁**：声明「建议 14 岁以上使用」、不收集年龄、注销路径畅通；若日后发现儿童数据，删除即可。
- **等保**：一期自定级为一级（备案非必须）；按二级基线做配置（强口令、最小权限、日志不留敏感字段）。**国密不在本期范围**（三家均未核实是否提供——无官方条目可查；本期不作为选型依据，仅当将来有政企需求再议）。

### 6.6 威胁清单（设计即对策）

| 威胁 | 对策 |
|---|---|
| 抓包读密码 | 仅 HTTPS |
| 数据库被拖库 | 服务端哈希（bcrypt）；payload 里无凭据 |
| 客户端装假用户读别人数据 | RLS/安全规则 + **四向**越权必败自动验收 |
| 令牌被本机其他程序偷 | safeStorage（DPAPI）；渲染层不落 localStorage |
| 日志泄密 | 日志纪律：token/password/apiKey 不进日志（照现有 apiKey 纪律扩展） |
| 注销不彻底 | 服务端删除函数（级联删 user_docs/profiles/头像）+ 本地账号目录可选删除 |
| 恶意构造的同步 payload 打崩客户端 | merge 函数吃 `unknown`、字段级校验、坏输入抛错不写盘（照现有写闸门）；**体积门**：pull 后、merge 前做大小检查，超限暂停该文档（§7.3），DDL 同约束 |
| 渲染层被导航劫持后拿到 IPC 桥 | §3.7 导航守卫 + CSP 加固（既有洞，随 P10 修） |
| 超大/非 PNG 头像吃满存储额度 | 渲染层 canvas 校验只是第一道；桶级 size/mime 限制 + 主进程 PNG 魔数硬校验（§6.3） |

## 7. 云端表结构（具体到字段）

### 7.1 方案选择：文档型先行

v1 用 **`user_docs` 文档模型**（每用户每文档一行 payload）：合并逻辑留在客户端（复用已测试的 merge 函数，这是本项目最宝贵的测试资产）；服务端零业务代码。docs/20 预留的六表（questions/mistakes/favorites/favorite_folders/practice_history/challenge_sessions/challenge_session_questions）**保留为归一化目标**——当将来要做服务端排行榜/防作弊/查询时，再把 user_docs 拆成六表（一次性服务端迁移，客户端协议不变）。附 A 给出字段级映射。

### 7.2 表 DDL 概要

```sql
create table public.profiles (
  user_id     uuid primary key references auth.users(id) on delete cascade,
  nickname    text not null default '',
  avatar_path text,                       -- avatars 桶内路径 {uid}/avatar.png
  schema_ver  int  not null default 1,    -- 云端 schema 版本（§8.6）
  created_at  timestamptz not null default now(),
  updated_at  timestamptz not null default now()
);

create table public.user_docs (
  user_id    uuid not null references auth.users(id) on delete cascade,
  doc_type   text not null check (doc_type in ('profile','wrongbook','favorites','practice')),
  revision   bigint not null default 1,   -- 条件写回（CAS）用
  doc_ver    int    not null default 1,   -- 文档格式版本（服务端第二道闸门：push 时不得小于库中现值）
  payload    jsonb not null check (pg_column_size(payload) < 262144),
  updated_at timestamptz not null default now(),
  primary key (user_id, doc_type)
);

-- 写回有两个可判定分支（0 行都不再笼统当「冲突」）：
-- 建行（首次上传）：insert ... on conflict (user_id, doc_type) do nothing returning revision;
--                    0 行 = 他人先建 → 重拉重合并
-- 更新（CAS）：      update ... set payload=$1, revision=revision+1, doc_ver=$5, updated_at=now()
--                    where user_id=$2 and doc_type=$3 and revision=$4 and doc_ver<=$5 returning revision;
--                    0 行 = 冲突（revision 或 doc_ver 不符）→ 重拉重合并
```

RLS 见 §6.3（含 `app_meta`——红队补漏：它一度漏在 RLS 外，anon key 可改协议下限停掉全量同步）。`app_meta(key,value jsonb)` 记录 schema_ver 与协议下限（客户端只读）。唯一服务端函数：`delete-account`（edge function，service_role，调 `auth.admin.deleteUser` + 级联）——**uid 只从调用者 JWT 的 sub 取，禁止 uid 入参，部署时不许关 JWT 校验**；注销后的验证见 §12.3。
CloudBase 对应物：集合 `profiles`（_id=uid）、`user_docs`（_id=`{uid}_{docType}`）+ 安全规则，机制对应、细节随实验。

### 7.3 索引与限额

- 索引：主键即查询路径（(user_id, doc_type)），无额外索引需求。
- 限额不是「自查目标」而是**三层硬门**（红队修复）：① DDL `check (pg_column_size(payload) < 256KB)`；② 主进程 pull 之后、merge 之前做体积门——超限即暂停该文档（照 §8.5 闸门口径），不进 merge、不写盘；③ merge 入口对大字符串先短路再 `JSON.parse`。
- 头像：256px PNG 目标 < 80KB；硬门 = 桶级 file_size_limit/mime + 主进程 PNG 魔数校验（§6.3）。

## 8. 问题⑤ 同步与迁移策略

### 8.1 三个版本号，各管各的

| 版本号 | 归属 | 例子 | 变更流程 |
|---|---|---|---|
| 本地文件版本 | 每份 JSON 信封 | profile v3、favorites v2 | 照既有铁律 6：migrate 纯函数 + 惰性迁移 + 测试 |
| 云 schema 版本 | `app_meta.schema_ver` + `profiles.schema_ver` | 加一列/改策略 | `migrations/*.sql` 顺序执行 + `check-cloud-rls` 闸门 |
| 同步协议版本 | `SYNC_PROTOCOL_VERSION`（代码常量，云端 app_meta 记下限） | /v1 冻结 | **只增不改**：新行为开新字段/新端点；服务端承诺兼容 N-1 |

### 8.2 同步引擎：拉→合并→条件写回（无 outbox，幂等自愈）

**执行在主进程、节拍在渲染层**（这是关键设计，理由在下面）：

```
渲染层 account store（唯一调度者）
  ├─ 触发点：登录成功后 / 启动后 / 本地写后防抖 30s / 定时 5 分钟 / 窗口 focus / 手动按钮
  │   （全部去重：同步在飞时不新起，把请求并入本轮）
  ├─ 步骤 1：flush 所有 store 的防抖写入（flushNow，await 完成）
  ├─ 步骤 2：invoke sync:now
  └─ 步骤 3：拿到 changedDocs → 安全点协调器重载对应 store（答题会话进行中则挂起，会话结束应用）

主进程 sync:now（无定时器、纯请求-响应、可注入假 transport 测试；**单飞**——在飞时并入当前轮，
  与 withAi 单飞同款先例）
  逐文档（每文档一条串行写队列，与渲染层写通道共用）：
    1. pull(docType) → {revision, docVer, payload} | null（null = 文档不存在）
    2. 体积门（§7.3）→ 超限：暂停该文档（照 §8.5 闸门），跳过 3-6
    3. 版本闸门（§8.5）三态：ok → 继续；blocked → **跳过本文档的 merge、写盘、push**，
       从 changedDocs 剔除，只更新徽章
    4. 重读磁盘 localRaw（**不用任何缓存**）→ merge(localRaw, remoteRaw)（含墓碑合并）
    5. merged ≠ local → json-store 写盘（原始合并结果；随后 push 用同一份）
       ——此写盘同样走 per-doc 队列，不绕过任何写序列化
    6. push(merged, expected {revision, docVer})：分支语句见 §7.2（建行 / CAS）
       0 行 → 重拉重合并（≤3 次），仍不成功 → 本轮放弃该文档、退避
    7. 全部失败 → 静默退避 1→5→15→60 分钟；徽章状态=error 或 offline
```

**为什么执行在主进程**：网络与凭据（令牌）在主进程，与 apiKey 先例同构；假 transport 可测。
**为什么节拍在渲染层**：调度、防抖 flush 与安全点都在渲染层，主进程保持无定时器。

**本地写协议（红队头号修复）**——「flush 后再同步」单独用是不成立的：同步在飞有网络往返、重载还会被答题会话挂起，这两个窗口里渲染层手里是旧快照，而现有保存是整份覆盖、主进程零校验——整份回写会吞掉刚并进来的数据，甚至把「集合收缩」误记成用户删除（假墓碑 → 跨设备删除）。修复三件套：

1. **条件写**：读口带出 `{epoch, rev}`；写通道入参带 `{epoch, baseRev}`，主进程校验不符即拒绝、并回读最新数据。epoch = 账号切换计数（干涸协议里 +1），rev = 该文档写盘计数。云端 CAS 的思路原样用在本地。
2. **冲突处理 = 重载 + 重放**：渲染层收到冲突 → 重载该文档 → 重放本次操作（每个写操作都对应一个可重放的 store 动作，如 `markLearned(id,true)`）。答题会话挂起期冲突 → 记入 pendingOps，会话结束统一「重载 → 重放 → 保存」。**用户操作永不丢。**
3. **per-doc 串行队列**：某文档的所有写（渲染层 save、同步写回、fire-and-forget 差量写）在主线程序列化——Node 单线程，队列 = per-doc promise 链。

**flush 范围**：所有防抖 save（profile / favorites / challenge…）都进 flushNow；`recordPractice / recordWrongbook / clearWrongbook` 这类 fire-and-forget 差量写由主进程 read→apply→write 天然安全，且进同一队列。

**为什么没有 outbox 队列**：文档都是全量的、合并是幂等的。任何一次同步 = 把当前本地与当前云端收敛到同一状态；中断了就下次再来，不需要记录「待发送操作」。

**并发与安全点**：合并结果写盘后，渲染层内存**只允许通过重载跟随磁盘**（条件写保证旧快照写不回去）；**重载**避开进行中的答题会话——协调器检查 QuizOverlay 状态，进行中则挂起，会话结束自动「重载 → 重放 pendingOps」。

### 8.3 逐文件合并矩阵（附反例意识）

| 文档/字段 | 合并规则 | 为什么这样 |
|---|---|---|
| profile.learned | 并集；**条目时间戳 vs 墓碑时间戳，新者胜**（条目胜 → 弃墓碑；墓碑胜 → 删条目）。v3 给 learned 配套时间戳 `learnedAt: Record<lessonId, at>`（markLearned(true) 时刷新；老数据迁移时补齐） | 红队三处独立发现：learned 是双向开关且无时间戳，「并集−墓碑」会让**重新学会被自己的墓碑永久吞掉**——必须给学习侧配时间戳 |
| profile.favorites（课程级） | 同上，配套 `favoriteAt` + `tombstones.lessonFavorites` | toggle 双向，同上 |
| profile.history | 按 **(lessonId, finishedAt) 去重**后取并集（同一事件被两端各记才去重；不同时间=不同事件，都保留） | history 是事件流水不是集合：按 lessonId 收敛会吃掉合法的重学记录、日历少亮点（红队反例，拍板点 #4 已改口径） |
| profile.stats | **不参与合并**；合并后按现有读时规则重算 | 派生值不搬运（照现有纪律） |
| profile.rewards.gallery | 并集（永不裁剪） | 图片奖励只增不删 |
| profile.rewards.perfectPasses | max | 单调计数 |
| wrongbook（按 key，字段级） | wrongCount=max 且 **lastWrongAt=max**（淘汰排序依据，两端必须一致才不振荡）；source 跟随 lastWrongAt 较大者；cleared/removed = 事件时间戳与 **lastWrongAt** 比较（较新事件胜；缺时间戳视为最旧），**复活语义复刻现有 wrongbook-merge**（复用其测试）；hole 无时间戳 → **两端取或**（保留标记是保守方向） | 红队指出原措辞「按各自时间戳」落不了地：cleared 的竞争事件其实是 lastWrongAt、hole 没有时间戳；lastWrongAt 不一致会让 AI_WRONG_CAP=30 的淘汰结果两端不同、永不收敛 |
| favorites.items（按 key） | 并集；同 key 取 `updatedAt` 新者（note 编辑冲突）；条目与 `removedItems` 墓碑**新者胜**（重新收藏可撤销墓碑） | v2 升版加 `updatedAt`+墓碑 |
| favorites.folders | 同 id 取 `updatedAt` 新者；与 `removedFolders` 墓碑新者胜；孤儿 folderId 清空照旧 | 同上 |
| practice.history | 按 **uid（落盘字段）** 并集 → **按 (at, uid) 全序排序裁到 5000**（超限裁最旧）→ 写盘 → push（顺序固定：合并→裁剪→写盘→push，保证两端收敛） | 红队证伪「uid 只在合并时算」：practice 必须升 v2 把 uid **写进文件**，读口去重、append 编号、裁剪排序全部改用 uid——否则下一次读口会按数字 id 去重、把并集删掉一半。installId 存 `device.json` |
| challenge | **v1 不同步**（v1.5：先补 origin 字段治 ai-key 撞主键） | 风险隔离 |
| config / ai-cache | **永不同步** | 设备级 + 含 apiKey |

**墓碑的撤销规则与两个诚实边界**：
0. **墓碑不是只增的**：写口在「集合变大」时撤销对应墓碑（重新标记 = 撤销）；合并按「条目时间戳 vs 墓碑时间戳，新者胜」裁决。没有这一条，用户重新学会/重新收藏会被自己的墓碑吃掉——红队三处独立发现，单机即可复现。
1. **同步上线前的历史删除不可追溯**：首次合并时「云端有、本机没有」无法区分「本机删过」与「本机从没有」→ 按并集处理（顶多把学过的课再标回已学，用户可再取消）；**上线后的删除全部有墓碑、且重新标记可撤销**。此边界写进用户文档。
2. **冲突裁决用墙钟时间戳**，设备时钟漂移是已知限制；因此所有规则设计成「即使时间判断反了，结果也只是保守方向」：并集、max、hole 取或——不出现「静默丢数据」的方向。

**保留区责任（治头号风险，红队加深）**：merge 函数吃 `unknown`、输出保留所有不认识的键；**但真正的守门人是写口**——红队证明「只保 merge 那一次写盘」不够：渲染层下一次普通保存（profile:save 对象字面量重建、sanitizeFavorites 三键重建）就会把未知字段和墓碑一起抹掉，并在下一轮 CAS 推回云端，让所有设备一起丢。修复：每个文档定义**保留区**（未知键 + 墓碑区），**写口以磁盘原始 JSON 为基底 apply 业务字段、合并保留区**；墓碑归主进程独占（读口剥离、写口维护）——这是「渲染层零改动」真正成立的前提。闸门测试 = 端到端一条：「merge 写入未知字段 → 模拟一次普通保存 → 断言未知字段与墓碑仍在」。

### 8.4 首次登录收编（本机进度 vs 云端）

- **云端为空（新账号）**：单问「把本机进度带入这个新账号？（复制，不移动；本机档案保持原样）」→ 是 = merge 后推；否 = 账号从空白开始。
- **云端有数据（第二台设备）**：两选一——「合并本机进度进账号」（推荐，= 一次普通合并）/「账号只用已有的云端进度」。
- **「云端为空」的判定以「首次 push 建行」的结果为准**（§7.2 的 insert-on-conflict），不以登录那一刻的一次 pull 为准——两台设备同时首登时，后到者建行得 0 行 → 自动改走一次「合并再推」，不会覆盖先到者。
- **本机（客人）档案在任何路径下都不移动、不删除**——它永远是游客模式的那份。登出即回到它。
- 引导文案要讲清：「账号里的进度在云端和账号档案里，重新登录就回来。」
- **challenge 归属（拍板 #7 写死）**：challenge **不入收编**——首登收编只覆盖四文档（profile / wrongbook / favorites / practice）；挑战是事件不是档案（docs/26 §1.1 第 7 条），其云端数据以**服务端结算**为准（同日先到先得；同 submissionId 重放幂等、payload 不同 409 `CHALLENGE_DUPLICATE`，docs/26 §5.6）。

### 8.5 版本闸门与老客户端纪律（无自动更新的补偿）

闸门是**三态**的，blocked 必须短路整个文档（merge、写盘、push 全跳过、从 changedDocs 剔除——否则旧版 payload 会带着匹配的 revision 走 CAS 成功，把云端新版数据整份顶掉）：

| 情况 | 行为 |
|---|---|
| 云端 docVer > 本机 CURRENT | 该文档 **blocked**：跳过 merge/写盘/push，徽章+设置页提示「此数据由更新版本写入，请升级应用后同步」；其余文档照常。服务端第二道闸门：push 语句带 `doc_ver<=$5`，doc_ver 倒退写不进（§7.2） |
| 云端 docVer < 本机 CURRENT | 先 migrate 再 merge |
| 协议不兼容（服务端 app_meta 下限 > 本机） | 全量 blocked + 升级提示 |
| **本地文件版本 > 本机 CURRENT**（降级运行） | 读口**只读不写**：不触发 needsRewrite 回写、内存按宽容子集展示、提示「此数据由更新版本写入」；写口比对磁盘 raw.version，高于本机**拒绝覆盖**。没有这一条，老客户端启动一次就把新字段+墓碑重写成旧形状（.bak 只有一层，两次重写就挤掉它） |
| 老客户端（N-1）遇到新客户端数据 | 协议只增不改 + 保留区责任（§8.3）→ 顶格表现为「老客户端看不到新字段，但不会毁掉它——前提是上面『降级只读』与『保留区』都已实现」 |

### 8.6 云端 schema 迁移管理

`supabase/migrations/*.sql` 顺序编号，只在控制台/SQL 执行一次并记入 `app_meta`；`scripts/check-cloud-rls.mjs` 每次部署前跑：从 `pg_tables` **现场枚举 public 全部表**（不手写清单——红队就是在手写清单之外找到 app_meta 这张漏网表的），逐表断言 RLS=on、anon 零授权、策略存在；app_meta 版本匹配（**先种坏值见它红过，再用它的绿**，种坏值含「关掉 app_meta 的 RLS，闸门必须红」一条）。CloudBase 路线对应为一组安全规则 JSON 的核验脚本。

## 9. 技术盲区与待实测（诚实清单）

1. **「Electron 能直接接国内 BaaS 的 Web SDK 吗？」——这就是最大盲区，答案分路线**：Supabase 系（阿里/华为）：主进程 Node 形态直连、无 CORS/来源障碍（**方向乐观，须实验证死**）；CloudBase：Web SDK 在 `file://` 页面受「安全来源」硬限制，能否登记未核实（预期不能）→ 须走 Node 形态或云函数中转（须实验）。**结论：能接，但接的是「主进程 Node 形态」，不是「渲染层 Web SDK」——这也正是本架构想要的形态。**
2. 免费档的具体行为未实测：QPS/连接数/是否有休眠冷启动（阿里免费试用版是否休眠未核实）。
3. 用户名注册在 GoTrue 需伪邮箱（`user@miai.local`）+ 关闭邮箱确认——**必须实验确认可关闭**（免费版邮件通道额度 ⚠️三份报告无出处）；不开邮箱通道 = 无密码找回（已拍板；主要依据是有出处的「个人拿不到短信签名」）。
4. 本机网络环境：主人机器曾出现代理导致的下载问题（DeepSeek 先例）→ 实验时用探针实测到阿里云/腾讯云 API 的直连质量。
5. safeStorage 换 Windows 用户/重装系统后解不开 → 设计已按「解不开=重新登录」处理（不崩不丢数据），但「重装后首次登录」路径要进验收。
6. CloudBase 若走云函数模式：「A 读不到 B」的保证**只有一层——函数代码**（安全规则对服务端 API Key 不生效，官方明确）→ 验收直接打云函数 URL，别只测 SDK 直连那条走不到的路。
7. 头像 256px 缩放要在渲染层 canvas 做（主进程零原生依赖，不引图像库）——实现小实验。
8. 等保/合规口径是「查得到的事实 + 合理推断」，最终以云厂商文档与主管部门要求为准（非法律意见）。
9. Challenge 同步推迟（origin 补丁前，ai-key 有撞主键隐患）。
10. 用户量到几百后的免费额度天花板：限流报错形态未知 → 设计上「限流=可重试退避」，绝不是丢数据；但具体报错码要实验收集。
11. CloudBase 路线备选风险（报告点名）：令牌自动刷新口径文档间冲突、Web SDK 登录态默认落 localStorage、Node 形态自定义存储未核实——已在 §5.3 加测，结论回写 §6.2。
