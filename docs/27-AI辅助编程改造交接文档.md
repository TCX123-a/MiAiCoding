## 1. 背景与目标

### 1.1 软件现状（改造起点）

咪爱编程是离线优先的 Windows 桌面编程学习伴侣：194 课知识库（通用 + C/C++/Java/Python）+ 单文件代码练习器 + 错题本 + 间隔重复 + 每日挑战 + 桌宠 + 壁纸/开屏 + 用户系统云同步。技术栈 Electron + Vue 3 + electron-vite，全栈零原生依赖。

**它与「VS Code 式 AI 编程」的差距不在编辑器，而在 AI 交互层**：目前 AI 只有「一次性问答」能力（讲报错、出题、桌宠聊天），没有对话历史、没有上下文引用、没有内联补全、没有文件级编辑。

### 1.2 本次目标

| 项        | 内容                                          |
| -------- | ------------------------------------------- |
| 用户诉求（原话） | 「把这个软件改成类似于 vs code 那种的现代化的 ai 辅助编程形式」      |
| 追加约束（原话） | 「尽量只加少减，在完整保留软件原有设计功能的基础上追加现代化使用功能，不删改既有能力」 |
| 交付形态     | 双模式：**课程模式（原样保留）+ 工作区模式（新增）**               |
| 非目标      | 不改课程内容体系；不换技术栈；不引入原生依赖；不搭服务器；不推翻既有技术选型      |

## 2. 已拍板的四条决策（2026-10-25）

| #  | 议题          | 结论               | 影响                                                 |
| -- | ----------- | ---------------- | -------------------------------------------------- |
| D1 | 产品定位        | **双模式：课程 + 工作区** | 新增独立的 IDE 式工作区页，课程侧一行不改；两套界面共用同一套 AI 层             |
| D2 | 技术路线        | **先只做 P1 看效果**   | 不立刻做多文件与 Agent；先用最小改动验证"流式 + 侧栏"是否真的改善体验           |
| D3 | AI 对文件的修改权限 | **目标态：工作区内自动执行** | 最终允许 AI 在用户选定目录内自主读写/跑命令；但必须**分期落地**，P1 不碰磁盘       |
| D4 | 模型接入策略      | **维持单 DeepSeek** | 不引入多 Provider 抽象；沿用 `ai.baseUrl` + `ai.model` 两个字段 |

### 2.1 一处必须记住的张力（接手者最易踩）

D2（只做 P1）与 D3（自动执行）**不是矛盾，但必须排序**：

```
P1 只读上下文（不写盘）
P2 建工作区 + 路径围栏（写盘能力就位但不开放给 AI）
P3 内联补全 / 改写（写盘仅限"用户点接受"）
P4 才开放 AI 自动执行（工具调用循环 + 全过程留痕）
```

**不要**把 P4 的权限提前实装进 P1。否则等于把「自动执行」放在没有工作区、没有围栏、没有 diff 记录的裸环境里，一旦出错无法回滚，也无法灰度验证。

## 4. 关键判断与理由（改动前必读，别重新论证）

| #  | 判断                           | 理由                                                                                                                    |
| -- | ---------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| J1 | **不换 Monaco，继续用 CodeMirror** | VS Code 的 AI 体验来自上层交互层，不是 Monaco 本身；Monaco 对四门目标语言仍无补全。现有 `minimalChange`、双主题令牌、语法色对比度体系（`MI_TOKEN_COLORS`）是资产，换掉等于重做 |
| J2 | **必须上流式（SSE）**               | 现状 `stream: false` 一次性返回，「现代化」体感的最大短板就是这里；不流式，侧栏对话永远像在卡顿                                                              |
| J3 | **不做向量库/嵌入检索**               | 离线优先 + 包体积 + 零原生依赖三条都不允许；先用结构化上下文（文件树 + 当前文件 + 选区 + 关键词检索 + `content-bundle.json`）覆盖绝大多数场景                            |
| J4 | **写盘只能走主进程 + 路径围栏**          | renderer 永远不碰 fs，这是 Key 隔离之外的第二个安全地基。AI 的修改必须先回传、由主进程落盘                                                               |
| J5 | **单 Provider 先不抽象**（D4）      | P1 阶段补全尚未实装，抽象 Provider 是过早优化；等 P3 真的需要"小模型补全 + 强模型对话"再抽，届时只动 `deepseek.ts` 一个文件                                      |

## 8. P1 施工图（可直接开工）

### 8.1 IPC 契约（新增 3 条 + 扩展 1 条）

| 通道              | 方向                      | 形状                                                                                  | 说明                      |
| --------------- | ----------------------- | ----------------------------------------------------------------------------------- | ----------------------- |
| `ai:chat-start` | renderer → main（invoke） | `{ messages, context: { code?, selection?, lang?, runOutput? } }` → `{ requestId }` | 立刻返回 requestId，不等模型     |
| `ai:chat-delta` | main → renderer（event）  | `{ requestId, delta }`                                                              | 每个 token/块推一次           |
| `ai:chat-done`  | main → renderer（event）  | `{ requestId, ok, reason? }`                                                        | 成功/失败/取消统一收尾            |
| `ai:cancel`     | renderer → main（invoke） | `{ requestId?: string }`                                                            | **省略参数 = 取消全部**，保持旧调用兼容 |

**preload 追加**（`src/preload/index.ts`，沿用现有 `miai` 对象）：

```ts
aiChatStart: (input) => ipcRenderer.invoke(IPC.aiChatStart, input),
onAiChatDelta: (cb) => {
  const h = (_e, p) => cb(p)
  ipcRenderer.on(IPC.aiChatDelta, h)
  return () => ipcRenderer.off(IPC.aiChatDelta, h)
},
onAiChatDone: (cb) => { /* 同上 */ },
aiCancel: (requestId?: string) => ipcRenderer.invoke(IPC.aiCancel, { requestId }),
```

**禁止**：把 `ipcRenderer` 本身暴露出去；在 renderer 里 `fetch` 模型接口。

### 8.2 并发与取消改造

现状 `app.ts:803` 是单例 `aiAbort`，`ai:cancel` 无参。P1 必须改为：

- `const aiInflight = new Map<string, AbortController>()`
- `ai:chat-start` 生成 `requestId` 入 Map；`done`/`error` 时删除
- `ai:cancel({requestId})` 只 abort 对应项；无参时 abort 全部
- **保留 `withAi()` 的旧语义**（新请求顶掉旧请求）给既有三条主链使用，**不改它们的行为**。这是「只加少减」的硬要求：桌面宠物聊天与出题仍在单飞通道里跑，侧栏对话走新的并发通道，两者互不干扰（可考虑给侧栏设"最多 1 条在飞"的软限制，防止刷额度）。

## 12. 风险与已知坑

1. **光标跳**：任何外部改内容必须走 `minimalChange()`，整篇重写会把光标甩回文首（`editor-setup.ts:141-160` 有实测表）。流式"插入建议"尤其容易踩。
2. **单飞语义变化**：把 `aiAbort` 改成 Map 后，桌宠聊天与侧栏对话可能同时发请求。必须给侧栏加"最多 1 条在飞"，否则用户连续提问会互相 abort，表现为"说到一半自己停了"。
3. **CSP 红线**：renderer 不能直连模型接口。流式只能 `ipcRenderer.on` 转发；不要试图在渲染层用 `EventSource`。
4. **额度**：补全与对话都会花用户自己的钱。P1 就要有最小间隔与失败退避，别等 P3。
5. **180s 出题超时**：流式改造后，出题路径**不要**跟着改成首字/总时长双闸，它需要的是"长尾允许"，改了就回归到"AI 出题不生效"的老 bug。
6. **打包体积**：任何新前端依赖先查 `docs/12`；能用 CodeMirror 现有包解决就不引新包（`@codemirror/autocomplete` 已在依赖里，P3 直接接 `autocompletion()` 即可）。
7. **`ai:chat-done` 的顺序**：`done` 必须先于组件卸载的回调清理，否则流式残留会让 UI 卡在"正在输入"。

### v1.3（2026-10-25）—— 修「侧栏点了没反应」+ 模型事实

**事故现象**：打包测试版里点发送，界面毫无反应（无增量、无报错）。

**根因（已复现、已修）**：`stores/aiChat.send()` 把 `messages.value`（Vue 的**响应式数组**）
直接丢进 `ipcRenderer.invoke`。IPC 入参要过结构化克隆，而
`structuredClone(reactiveArray)` 抛 `DataCloneError: [object Array] could not be cloned`
—— **请求根本没出渲染进程**。项目里 `lib/ipc-safe.ts` 的 `toIpc()` 就是为这件事准备的
（出题链 `challenge.ts` 一直在用），这里漏用了。

四处修复：

| # | 修复 | 说明 |
|---|---|---|
| 1 | `send()` 用 `toIpc(messages.value)` | 纯数据过 IPC；`toIpc` 本身也包进 try，失败给一句人话而不是静默 |
| 2 | `requestId` 改由渲染层预生成 | 否则增量可能比"回话"先到，那一刻 id 还是 null，事件被当别人的丢掉（连 `done` 一起丢 → 永远"正在输入"）。主进程原样沿用（`AiChatStartInput.requestId` 为可选新增字段） |
| 3 | 看门狗 25s | 接受了请求却一个增量都没来（事件丢了）→ 取消 + 复位 + 一句"等太久了"，不再无限转圈 |
| 4 | 失败带上「排查用：」小灰字 | `failDetail` 显示 HTTP 码 / 异常 message。以前失败只有人话，"点了没反应"这类报障完全查不出来 |
| 5 | 顺手修 `rollback()` 丢草稿 | 它先 splice 再从数组里捞原话，捞到的永远是空 —— 被 busy/throttled 挡下时用户输入会消失 |

**新增测试**：`src/renderer/src/stores/__tests__/ai-chat-payload.test.ts`（5 条）——
入参必须可 `structuredClone`、`requestId` 出发前已定、只带非空消息、上下文原样、拒绝时回滚。
这套件当场抓到了上面第 5 条。

**模型事实（2026-10-25 用真实 Key 实测，非推测）**

| 项 | 实测结果 |
|---|---|
| `GET /models` 返回 | `deepseek-flash`、`deepseek-v4-pro`（**没有** `deepseek-v4-flash` / `deepseek-v4.1-flash` 这类名字） |
| 用 `deepseek-chat` 请求 | HTTP 200，响应体里 `"model":"deepseek-flash"` —— **别名已指向 flash**，不是旧模型 |
| 结论 | 不需要改代码；想显式固定就在「设置 → AI → 模型」填 `deepseek-flash`，想要更强推理填 `deepseek-v4-pro`（该字段是自由文本，每请求现读） |

### v1.5（2026-10-25）—— 修 @选区：侧栏搬到外壳后取值线断了

**现象**：侧栏底部「带上：」那一行里，「选中片段」永远是灰的，一直显示
「（先在编辑器里选一段）」—— 在编辑器里选了字也不亮。

**根因**：p1 起初把面板挂在 `PlaygroundView` 里，用 `:get-selection` 把选区取值
传进去；v1.2 搬到 `App.vue` 外壳右栏时**没有把这条线接上**（外壳拿不到
`RunnerPanel` 的 ref）。于是 `props.getSelection` 恒为空 → 那颗勾恒灰。

**修法**（跨层取值的桥，沿用项目里 `lib/pet-work-rect.ts` 的登记/撤销模式）：

| 文件 | 作用 |
|---|---|
| `renderer/src/lib/editor-selection.ts`（新增） | 登记处：`registerSelectionSource` / `releaseSelectionSource`（**比对是不是自己**才清，防路由切换时旧组件误剪新登记）/ `readSelection()`（每次现取，不缓存快照）/ `selectionAvailable`（响应式布尔） |
| `components/domain/CodeEditor.vue` | `defineEmits` 追加 `selection-change`；`EditorView.updateListener` 里只在 `selectionSet \|\| docChanged` 时广播一个**布尔**（不播正文） |
| `components/domain/RunnerPanel.vue` | 挂载时登记取值函数、卸载时撤销；把编辑器的布尔透传给登记处 |
| `components/domain/AiPanel.vue` | 去掉 `getSelection` prop，改读登记处；`selectionReady` 依赖 `selectionAvailable`，选中即亮 |

**测试**：新增 `lib/__tests__/editor-selection.test.ts`（6 条，含"旧函数不许误剪新登记"），
全量 **4579 passed**。

**三个上下文开关的语义（用户问过，记下来免重复解释）**

| 开关 | 亮 / 灰的判据 | 灰的时候发什么 |
|---|---|---|
| 当前代码 | 一直可点（勾着） | 编辑器为空时不发，其余照发（含语言名） |
| 选中片段 | `selectionAvailable` 为真（编辑器里确实有非空选区） | 不发选区；提示「（先在编辑器里选一段）」 |
| 运行输出 | `runner.lastResult !== null`（跑过至少一次） | 不发；提示「（还没跑过）」 |

三个开关只影响**这一次请求带什么**；勾上的内容会同问题一起发往用户配置的 API，
路径 / Key / 错题本永远不发（`.ctx-privacy` 那行就是这句承诺）。

### v1.6（2026-10-25）—— 灰键要能解释自己

**反馈**：「这个按键怎么还是灰色的？」—— 用户看到面板底部灰着的一片，界面没有
任何说明"为什么灰、去哪儿点亮"。

**处置**：四颗会灰的控件全部补上 `title`，把判据写成一句人话：

| 控件 | 灰的条件 | 悬停文案（要点） |
|---|---|---|
| 选中片段 | 当前页面没有编辑器 / 没选中文字 | 先去「练习场」拖选一段文字，回来就会亮 |
| 运行输出 | 还没跑过 | 去练习场点一次「运行」（报错也算） |
| 发送 | 输入框为空 | 先在框里写点什么 |
| 清空 | 没有对话可清 | 还没有可以清的对话 |
| 当前代码 | 恒可点 | 会带上编辑器里这段（含语言） |

**设计判断（写下来免得再来一次）**：「灰」本身没错，错的是**灰而不解释**。
这四颗的灰状态都是真实语义（没有可带的内容 / 没有可发的字），
不该为了"看起来能点"而把它们点亮 —— 点亮等于让用户发一条空请求。
所以做的是**让悬停能自证**，而不是放松判据。
