## 钩子：C 那边的猫要自己扫猫砂

上一课本喵在 0 和 1 上做了一阵子手脚，这一课把镜头拉远一点：一段 Java 程序跑起来的时候，它的东西都放在哪儿。

在 c-stage3-01 里，本喵带你进过 C 那边的四间屋。那会儿最要命的一条是：**现要现租的仓库，用完得自己还** —— 忘了还就叫漏水，程序越跑越肿。

Java 这边的猫不管这件事。你只管 `new`，还的事**一句都不用写**。这不是因为 Java 的程序不漏水，是因为院子里养着一只自动铲屎官（内存回收 / 垃圾回收）：它自己看谁没人要了，自己扫走。

这一课就三件事：

1. 一段程序跑起来，谁住在**栈**上、谁住在**堆**里、谁住在**图纸柜**里；
2. 铲屎官凭什么判断「这只没人要了」（提示：它顺着一串牌子走路）；
3. 它什么时候来 —— 以及为什么 `System.gc()` **只是一句建议**。

## 一、三间屋：东西分别放在哪

先摆一张表。这是本喵这台机器上跑 Java 时的分法，四门语言各养各的院子，别处的猫不一定这么分：

| 屋 | 本喵的叫法 | 里面放什么 | 活多久 |
|---|---|---|---|
| 栈 | 一摞叠起来的猫粮碗 | 每喊一次招式就摞一只新碗上去。碗里放的是这趟自己的小鱼干仓库（局部变量），加上它手里攥着的那些猫爪指向牌（引用） | 招式一收工，这只碗马上端走 |
| 堆 | 院子 | `new` 出来的真猫都住这儿，连它肚子里的字段一起。牌子指向的就是它 | 只要还有牌子指得到，它就一直在 |
| 方法区 / 元空间 | 图纸柜 | 猫猫图纸的底稿（类元信息）、`static` 的那几格、还有一张名字总表（字符串常量池） | 从开跑到收工，装一次用到底 |

三间屋，三种活法：

- **栈上的碗来来去去** —— 它管的是「这会儿谁在干活、手上攥着什么牌」；
- **堆里的盒子活得久** —— 它管的是「东西本身」；
- **图纸柜从头稳到尾** —— 它管的是「这东西按哪张图纸做的、图纸上写了什么」。

::: tip 猫咪提示
本喵在第二阶段给账本加的那个盖子（封装）管的是「谁的手能伸进来改」；它管不着「这只盒子什么时候被收走」。那是两件事，一件在 java-stage2-01，一件在这一课喵。
:::

**招式收工了，碗端走了，碗里那只盒子呢？** 看一段：

```java
class Cat {
    String name;

    Cat(String name) {
        this.name = name;
    }
}

public class Main {
    static Cat 生一只猫() {
        Cat 屋里那只 = new Cat("小橘");
        return 屋里那只;
    }

    public static void main(String[] args) {
        Cat 外面拿着的 = 生一只猫();
        System.out.println(外面拿着的.name);
        System.out.println(外面拿着的 == 生一只猫());
    }
}
```

```text
小橘
false
```

第一行印得出名字：招式收工、碗端走了，可**盒子还在院子里**，因为本喵把牌子**叼了回来**，外面接住的那只手还攥着它。第二行 `false` 说的是：那一招喊了两次，每次都是**新搬一只盒子**，两张牌指的当然不是同一只（`==` 比的是牌子，第六节细说）。

## 二、牌子与盒子

堆里那些盒子，本喵怎么使唤？靠**牌子**。所以有三种动作，长得像、意思差得远：

- `new` 一次 = 搬一只新盒子进院子，同时在栈上**立一张新牌子**；
- `b = a` = **又立了一张一样的牌子**，两张牌指着同一只盒子 —— 没有新盒子；
- `= null` = **把这张牌子放下**。盒子还在，只是这张牌不再指着它了。

把这三种动作各写一遍，跑出来看看：

```java
class Cat {
    String name;

    Cat(String name) {
        this.name = name;
    }
}

public class Main {
    public static void main(String[] args) {
        Cat 小橘 = new Cat("小橘");
        Cat 另一张牌 = 小橘;
        小橘 = null;
        System.out.println(另一张牌.name);
        System.out.println(小橘 == null);
    }
}
```

```text
小橘
true
```

第一行印 `小橘`：第一张牌已经放下了，盒子还在院子里，第二张牌照样报得出它的名字。第二行 `true`：那张放下的牌子确实是空的。

那**牌子空了之后再伸手去摸它**呢？本喵试了：

```java
class Cat {
    String name;

    Cat(String name) {
        this.name = name;
    }
}

public class Main {
    public static void main(String[] args) {
        Cat 小橘 = new Cat("小橘");
        小橘 = null;
        System.out.println("小橘的名字是：" + 小橘.name);
    }
}
```

翻译官喵让你跑，可它一跑起来就当场断了：

```text
Exception in thread "main" java.lang.NullPointerException: Cannot read field "name" because "<local1>" is null
at Main.main(Main.java:13)
```

第一句的意思：**那张牌子是空的**（`null`），你却让本喵顺着它去读 `name`。`<local1>` 是翻译官喵临时起的代号 —— 编译的时候没把本喵那个中文名字记下来，报错时只好用编号。要记住的是这两句：

- **放下牌子不会毁掉盒子**（第一段程序证明了）；
- **放下之后你自己也不能再用那张牌**（第二段证明了）—— 从这张牌往前走的那条路，断了。

铲屎官认的正是「路」：还有没有一条路走得过去。

## 三、谁算「还有人要」：顺着一串牌子走

铲屎官的活儿只有一件：把没人要的盒子扫走。可「有人要」它怎么判？它不看这只盒子多旧、也不听你嘴上怎么说 —— 它做一件事：

> **从几个「根」出发，顺着一串牌子一路走，看走不走得到这只盒子。**

根是哪几个？

- 还在栈上立着的那些碗里的牌子 —— 也就是这会儿正在干活的招式手上的那些；
- 图纸柜上 `static` 那几格里放的牌子。

走得到 = 这只盒子还**够得着**，先留着；走不到 = 没人要了。

本喵举个最能说明问题的例子：**两只猫互相拿牌**。要是按那种老路子的数法（引用计数）—— 只数「有几张牌指着我」—— 这两只各有一张，谁也数不成 0，永远收不走。

```java
class Cat {
    String name;
    Cat 朋友;

    Cat(String name) {
        this.name = name;
    }
}

public class Main {
    public static void main(String[] args) {
        Cat 甲 = new Cat("小橘");
        Cat 乙 = new Cat("狸花");
        甲.朋友 = 乙;
        乙.朋友 = 甲;
        System.out.println("甲的朋友是：" + 甲.朋友.name);
        System.out.println("乙的朋友是：" + 乙.朋友.name);
        甲 = null;
        乙 = null;
        System.out.println("外面两张牌都放下了");
    }
}
```

```text
甲的朋友是：狸花
乙的朋友是：小橘
外面两张牌都放下了
```

跑完之后，两只盒子还在院子里互相指着对方，可**外面已经没有一张牌指得到它们了**。顺着一路走：根上找不到它们 → 走不到 → 在铲屎官眼里，它们已经是没人要的了。

哪怕它们互相还攥着对方的牌，也照样算没人要 —— **「够不着」是从根上看的，不是从盒子看盒子。**

## 四、自动铲屎官什么时候来

那本喵能不能催它一句，让它**现在**就来？

Java 里确实有这么一句：`System.gc()`。听起来像命令，其实是**一句建议**。JVM 可以立刻动手，也可以说「我等会儿自己来」；开跑时给它传过 `-XX:+DisableExplicitGC` 那种开关的话，它连理都不理。

那本喵怎么知道它到底干活没有？看**可观测的量**：`Runtime.getRuntime()` 上挂着两个读数 —— `totalMemory()`（院子一共多大）和 `freeMemory()`（还空着多少）。本喵真跑了这段：

```java
public class Main {
    static String report(Runtime rt) {
        return "院子一共 " + rt.totalMemory() / 1024 / 1024 + " MB，还空着 "
                + rt.freeMemory() / 1024 / 1024 + " MB";
    }

    public static void main(String[] args) {
        Runtime rt = Runtime.getRuntime();
        System.out.println("刚开跑：" + report(rt));

        for (int round = 0; round < 3; round++) {
            String[] pile = new String[100000];
            for (int i = 0; i < pile.length; i++) {
                pile[i] = new String("小鱼干" + i);
            }
            System.out.println("堆了 " + (round + 1) + " 轮：" + report(rt));
            pile = null;
        }

        System.gc();
        System.out.println("喊完 System.gc() 之后：" + report(rt));
    }
}
```

**这一段本喵故意不抄成一段「输出」贴上来** —— 这几栏数会随机器、JDK 和当时的情况变，抄下来毫无意义，你照着跑也未必对得上。本喵这一回跑出来的是这样（**只看趋势**）：

- 刚开跑：`totalMemory` 那一栏是 **508 MB**，空着 **504 MB**；
- 堆到第一轮、第二轮：空着的那栏掉到 **496 MB**、**488 MB** —— 新盒子真的占了地方；
- 第三轮反而回了一点血（**499 MB**）：本喵一句话没说，铲屎官自己动了一次手；
- 喊完 `System.gc()` 之后：`totalMemory` 从 508 MB **缩回 16 MB**。

最后那一栏最实在：**院子一共**这个数会缩，说明 JVM 是真把地方还回来了，不是嘴上答应。不过要记住这四栏数**只属于本喵这台机器这一回** —— 换台机器、换个 JDK，第一栏就不是 508 MB，回血的时机也说不准。**它们只能看趋势，不能当尺子**；你跑出来的数和本喵不一样，不是你写错了。

::: warn 小心喵
**别把 `System.gc()` 写进笔记当开关。** 有三种情况它「看着没反应」：

- 本来就没多少没人要的盒子：铲屎官觉得不值当，直接略过；
- JVM 把这一句当成一次**强烈的暗示**，挑别的时候动手；
- 开跑时的开关（`-XX:+DisableExplicitGC` 这类）明说过「别理它」。

所以课文里、笔记里、考试的卷子上，都别写「调了它就一定回收」这句话喵。
:::

那它自己什么时候来？**院子快满的时候。** 新盒子搬不进来，它才动手 —— 那时候不动手，就真没地方放了。

## 五、分代直觉：小猫箱和老猫箱

铲屎官还有一手安排：它把院子分成两间。

- **小猫箱**（新生代）：新搬进来的盒子先搁这儿。这间小，铲得勤；
- **老猫箱**（老年代）：在小猫箱里挺过好几轮还没被扫走的，挪到这儿。这间大，铲得少。

凭什么这么分？因为经验是这样：**绝大多数盒子活得很短**。一串临时拼出来、用完就丢的字，一次算完就不要的中间结果，搬进来没一会儿就没人要了。既然大半的垃圾都在小猫箱，**只盯着一间小屋子勤扫**就比每次把整个院子翻一遍划算得多。

这也是为什么你会看到两种动静：**小扫**只翻小猫箱，快；**大扫**要连老猫箱一起翻，慢。第四节读到的「第三轮回了一点血」，多半就是一次小扫 —— 它没跟谁打招呼，自己就来了。

::: tip 猫咪提示
「分代」是个**经验**，不是规矩。你要是造了一院子**都留着不撒手**的盒子（比如一排放满长命东西的架子），它们迟早全搬进老猫箱，小扫就救不了你了。到那时再抱怨「怎么越跑越肿」，得回头看看是不是有牌子一直没放下喵。
:::

## 六、两个容易记岔的地方

**第一件：`==` 比牌子，`equals` 比内容。**

本喵在 java-stage1-12 里讲过 `==` 和 `null`。放到这一课看：`==` 问的是「是不是同一只盒子」，`equals` 问的是「盒子里装的东西一不一样」。这跟图纸柜上的**名字总表**有关系 —— **直接写出来的那串字只做一份，搁在总表上**：

```java
public class Main {
    public static void main(String[] args) {
        String a = "喵";
        String b = "喵";
        String c = new String("喵");
        System.out.println(a == b);
        System.out.println(a == c);
        System.out.println(a.equals(c));
    }
}
```

```text
true
false
true
```

- 第一行 `true`：`a` 和 `b` 都是照着**名字总表上那一份**立的牌子，指的是同一只盒子；
- 第二行 `false`：`new String("喵")` 是**另做了一只新盒子** —— 装的内容一样，位置不一样；
- 第三行 `true`：`equals` 比的是内容，两边的喵都是那只喵。

这跟铲屎官有什么关系？关系在于：**名字总表是从头到尾都够得着的**（图纸柜是根之一），那几份字永远扫不走；而 `new` 出来的新盒子，谁不指了，谁就可以被扫。

**第二件：别把遗言当归宿。**

早年间 Java 给盒子留过一招「临死前喊一声」的遗言：`finalize()`。这一招从 JDK 9 起就被打上废弃的记号了，而且它本来**就不保证一定被喊到** —— 铲屎官忙不忙、程序什么时候退，都能让它错过。所以：

- 要收拾的东西，写在明明白白的地方 —— 用完就 `close()`，别等遗言；
- 别把「反正有遗言」当设计。

::: warn 小心喵
**三种说法都是错的**，听见就绕开走：

- 「调了 `System.gc()` 就一定回收」—— 它只是建议；
- 「牌子一置成 `null`，盒子立刻就没了」—— 盒子只是**够不着**了，扫不扫、什么时候扫，铲屎官说了算；
- 「两块牌子互相指着，就谁也收不走」—— 数牌子那套老路子才会这么想，铲屎官走的是从根出发的路。
:::
