## 钩子：一句把读者带沟里的注释

大肥鱼今天收工前清理旧稿，翻到一段，看着看着炸了毛：「这代码写得太丑啦喵！」—— 稿子里有这么一段：

```java
public class Main {
    public static void main(String[] args) {
        int fish = 3;
        fish = fish + 1;  // 把鱼干吃掉一条
        System.out.println("筐里还剩 " + fish + " 条");
    }
}
```

```text
筐里还剩 4 条
```

它盯着行尾那句注释（`// 把鱼干吃掉一条`）看了半天：**代码写的是「加一条」，注释说的却是「吃掉一条」** —— 两句里必有一句在撒谎，而下一个读到这行的猫，信的多半是注释。本喵把爪子搭上去：「注释写歪了，比不写注释还坏。今天这把尺子，量它就是量的这个。」

## 一、两种注释，两张面孔

Java 里的注释有两副面孔，职责分得很清：

- **行内注释**：`//` 开头那种（`/* */` 包起来的也算），夹在代码缝里，是**写给正在读这段代码的人**的便条；
- **文档注释**：`/** */` 开头（注意多了开头那颗星），写在图纸和招式的头上，是**写给所有要用它的人**的说明书。

第二副面孔你以后会常听到它的名号 —— **Javadoc**：它既指这套写法，也指 JDK 自带的那只**文档工具**。那只工具会把所有 `/** */` 捡出来、编成一套网页版说明书。换句话说：文档注释不是写给自己看的草稿，而是**要拿去发表的公开文字** —— 写它的时候，默认「读者手里只有这份说明书，没你的稿子」。

## 二、文档注释写什么

写在图纸头上：一句话说清「这是什么、管哪一摊」。写在招式头上，标准格式是两段：

1. 先是说明：一句话总结这只招式干什么，需要时再补一句细节；
2. 后面跟**标记**（英文名 tag）：每个入口一条 `@param`，写「入口的名字 + 它是什么」；有东西交出来的话，再补一条 `@return`，写「交出去的是什么、什么单位」。

没有入口的招式就不用 `@param`，没有东西交出来的就不用 `@return` —— 标记跟着实情走，不凑数。图纸头、招式头都该写；越是**别人要用到的地方**，越不能少。

为什么值得写？因为「下一个读代码的人」里，也坐着半年后的你自己。IDE 里把光标往招式上一悬，弹出来的浮窗读的就是这些文档注释 —— 写得好，别人不用点开稿子就知道怎么用；写空了，弹窗里连一句「干什么的」都找不着。

## 三、`@param` 与 `@return` 上手

看本喵真跑过的一段账本稿子（重点不在逻辑，在注释）：

```java
/**
 * 鱼干账本：记着现在有多少条鱼干。
 *
 * @author 本喵
 * @date 2026-10-11
 */
public class Main {
    /** 账本上此刻的条数 */
    private static int stock = 0;

    /**
     * 收鱼干：把新到的条数记进账本。
     *
     * @param incoming 新到的鱼干条数
     * @return 记完之后账本上的总数
     */
    static int receive(int incoming) {
        stock = stock + incoming;
        return stock;
    }

    public static void main(String[] args) {
        int total = receive(7);
        System.out.println("收完这一笔，账本上是 " + total + " 条");
    }
}
```

```text
收完这一笔，账本上是 7 条
```

上面的注释逐条对一下：

- `@param incoming 新到的鱼干条数`：标记后面**先写入口的名字**（`incoming`），再写它是什么、什么单位。本喵拿一段故意写错名字的稿子实测过：名字对不上号，文档工具当场报错「@param name 未找到」；漏了哪只，它会点名说 `incoming` 没有 `@param` —— 它对得上号才肯放行；
- `@return 记完之后账本上的总数`：说清**交出来的东西是什么**、哪个时刻的数。读者最常问「这个数是收完之前的还是之后的」，写清楚省一轮来回；
- 格式的惯例：标记排在说明后面、一句一行、紧挨着收尾的 `*/`；
- **`@author` 是标准标记，`@date` 不是**：本喵实测把上面这段交给文档工具，它直接报错「未知标记: date」，命令失败退出（硬报错，不是软警告）。工具只认标准名单里的标记 —— 想写日期，要么当普通说明文字写进内容，要么用团队自己约定的标记。

## 四、行内注释的时机

行内注释守一条线：**说「为什么」，不说「做什么」**。

- 代码自己已经把「做什么」说清了 —— `stock = stock + incoming;` 后面再跟一句「// 把 incoming 加到 stock 上」就是废话。**废话注释的坏处不是占地方，是稀释**：一页里八句废话挤着，剩下两句金句就没人看见了；
- 「为什么」才是代码写不出来的东西：`// 先扣再补：负数是退款单`、`// 顺序不能换：先记账再发货，失败了好回查` —— 这类注释每写一句，帮读者省十分钟；
- 时机也就出来了：**当代码没把意图写出来的时候**才值得写。写得越少，每个字越重。

## 五、注释与代码同步

钩子里那段稿子的病根，落在这一条上：**注释和代码必须同步**。改了代码、忘了改注释，注释就从「帮手」变成了「凶手」—— 读者对注释天然带着信任（「这是作者特意写给我看的」），于是他照着「吃掉一条」去推，推出个错结论，还理直气壮。

两条规矩：

- **改代码的时候，顺手把挨着的注释读一遍**，对不上就当场改掉；
- 翻到一句对不上的旧注释：**宁可直接删掉**（没有注释，读者会老老实实读代码），也别留着它继续骗人。

还有一种隐藏的过期源：注释里写**会变的数字** —— 「已经有了 3 条」「总数装得下 100」这种，代码一改注释就过期。能写成「当前条数」的，就别把具体数字写死。

## 六、带着尺子做一次体检

把上面的尺子合起来，看本喵再掏出的这段七行小稿（重点仍是注释）：

```text
/** 鱼干账本：记着现在有多少条 */
public class FishLedger {
    int total = 0;  // 已经有了 3 条
    /** 加上 n 条 */
    public void add(int n) {
        total = total + n;  // 加 n
    }
}
```

一行一行过尺子：

- 第一行 `/** 鱼干账本：记着现在有多少条 */` —— 合格：图纸头上一句话，把「是什么」说清了；
- 第三行 `int total = 0;  // 已经有了 3 条` —— **不合规①：注释和代码不同步**。代码写着 `= 0`，注释却说「已经 3 条」，两个里必有一个是旧的；而且「当前数字」本来就不该写死在注释里；
- 第四行 `/** 加上 n 条 */` —— **不合规②：招式的文档注释缺项**。这只招式明明收了一个入口 `n`，却没有一条 `@param` 说它是什么 —— 说明书上只有一句空话，读者还是不知道 `n` 从哪来、什么单位；
- 第六行 `total = total + n;  // 加 n` —— **不合规③：废话注释**。代码写得明明白白，注释只是把符号又念了一遍；
- 其余各行（图纸那一行、收尾的括号）都过。

数下来：**三处**。

## 七、让工具收尾

- **`/**` + 回车**：在 IDEA 里对着一只招式的名字，在它上面敲下 `/**` 再按回车 —— 它会自动补出一套文档注释骨架：总结的位置、每个入口的 `@param` 占位、`@return` 占位，全摆好。骨架是**占位**，别留着空的不填 —— 空占位比不写还空洞；
- **`Ctrl + Alt + L`**：上一课学的排版键，注释块照样排队（`*` 对齐、缩进归位）；
- **`javadoc` 工具**（JDK 自带）：把全工程的文档注释编成一套网页版说明书。它只认标准标记名单 —— 自创标记的下场，前面 `@date` 已经演示过了。

::: warn 小心喵
两种注释别混用：该给「要用它的人」看的说明书（图纸头、招式头），就老老实实用 `/** */` —— 写成 `/* */` 或 `//`，文档工具捡不到，等于没写。另外别把「给自己看的草稿」留在注释里：「TODO」「暂时这么写」「测试用」这类没有主人的尾巴，评审席上都是扣分项；真要留，就写上名字和日期，让它有个负责人。
:::

## 小任务

对着上一课改好的祖传文件（`OrderService`）做三件事：

1. 给图纸头和 `main` 的头上各补一条文档注释：图纸头一句说清「这是什么」，招式头一句说清「它演示什么」；
2. 在 IDEA 里对着一只招式敲 `/**` 再回车，看骨架怎么长出来，把占位一格一格填实；
3. 翻翻自己的旧稿子，找一句「和代码对不上」的注释 —— 要么改对，要么删掉，不许留着。

::: tip 猫咪提示
这一课记三句话：**文档注释**（`/** */`）写给「要用它的人」，图纸头和招式头上要有，招式里配 `@param` / `@return`；**行内注释**（`//`）说「为什么」，不说「做什么」；**注释和代码必须同步** —— 写歪的注释比没有注释更坏。到这里，一学段的功夫串成了一条线：从一只 `.java` 稿子，到大宅子、管家、名字的尺子、注释的规矩 —— 写的每一笔，都想到「下一个读代码的人」喵。
:::

🐾 题外一句：这一学段练的全是「工程素养」—— 它不像新招式那样一眼见功，但以后你每一次把稿子交出去，这些规矩都在暗处替你说话喵。
