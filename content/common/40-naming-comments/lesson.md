## 钩子：前辈留下的三个名字，让本喵舌头打了结

上一课立下的规矩是**「代码是写给人看的」** —— 可「让人看得懂」这件事，落笔的第一个路口就是**起名**。本喵今天就在项目里撞上了一堵墙：前任作者写的三个名字排着队喵：

```python
DaZhePromotion = 0.8
ShangPinJiaGe = 100
zheKouLv = 0.9
print(DaZhePromotion * ShangPinJiaGe * zheKouLv)
```

```text
72.0
```

跑得动，印出来 `72.0`（这段本喵真跑过）。可本喵把它们念出声的那一秒，舌头就打了结：`DaZhePromotion` —— 一半拼音一半英文；`ShangPinJiaGe` —— 全拼音；`zheKouLv` —— 拼音加缩写。**三个名字，三种劈叉**，读代码的人得先考个拼音证才能进这扇门喵。

名字和注释，是代码里**出现频率最高的两样东西** —— 每一行都可能有名字，每一段都可能贴注释。这两样的手艺不过关，前面学的都白搭。这一课就练这门手艺。

## 起名，是写代码里最频繁的那件事

本喵做过一次统计（凭手感，但八九不离十）：写一个功能，本喵敲下的名字比敲下的逻辑还多 —— 给仓库起名、给招式起名、给文件起名、给常量起名……**一天下来，起名说不定占了三分之一的手速。**

这么高频的动作，却最容易被当成「随手打两个字」。划算是划算了，代价在下一课呢 —— 读的人每天都要和你的名字打照面。所以工程圈给起名立的第一句口诀是：

**名字要为一个「不在这个团队里的新读者」优化。**

他没听过你们开会的上下文、不知道历史包袱，只能从名字读出意图。你起名的时候脑子里装着他，名字就及格了一半。

## 好名字的四个标准

本喵把各家规矩熬成一锅，捞出来四条喵：

1. **说人话。** 读完名字就能猜到它装什么、干什么：`total_fish` 比 `tf` 好，比 `a1` 好上一百倍。名字**宁可笨一点、长一点，也别含糊**。
2. **能读出声。** 名字是给耳朵也过一遍的：站起来读它，同事能听懂。单字母别用 `l`、`O`、`I` —— 它们和 `1`、`0` 站在一起，肉眼根本分不出来。
3. **别把缩写缩过头。** 通用缩写（如 `id`、`url`）大家都认，留着没事；自造的缩写（`zheKouLv` 里的 `Lv`、`js` 当「计算」）只有你自己认 —— 那是给读者挖坑。
4. **长度与作用域成比例。** 只活两行的计数，可以短；全项目共用的角色名，就该完整。**看得见的人越多，名字越要说全话。**

四条之外还有一条最硬的：**拼音和中文别上桌。** 下一节就拆它为什么不行喵。

## 拼音和中文为什么不行

「用拼音多亲切」—— 这个念头本喵也有过。可三条线摆出来，结论就翻不了身了：

- **编码这条线。** 中文和拼音进到名字里，就得靠每一件工具都拿对编码表。你今天的环境是全绿的，换台机器、换个老工具、日志转一手编码，名字就可能变成一串乱码 —— 而名字是**定位用的路标**，路标花了，抓虫时两眼一抹黑。翻译官喵也许照单全收，工具链可不一定。
- **工具链这条线。** 搜索、替换、命令行、自动化脚本、大小写转换……整套家伙什都是按英文习惯设计的。名字全英文，工具一叫一个准；名字里掺点拼音，工具们集体发懵。
- **协作这条线。** 读你代码的同事要去搜文档、要复制名字去问人、要把名字打给机器人；拼音混拼（`DaZhePromotion`）读起来还要先「解码」。**给读者省一步解码，就是给团队省一笔钱。**

阿里的 Java 手册把这条写成了强制级的规矩：**不能拼音与英文混着拼，纯拼音更要躲开。** 本喵再补一刀 —— 拼音还常常拼得不统一：同一个人写 `zheKou` 和 `zhekou`，谁是谁都分不清喵。

```java
double DaZhePromotion = 0.8;
int zheKouLv = 1;
```

这两行翻译官喵是放行的（名字合法），但读代码的人当场叛逃。**合法，不等于体面。**

## 注释写什么、不写什么

名字之外的第二样高频事物是注释。先说一句炸场的：**注释不是「解释代码干了什么」的地方。** 代码自己已经说了它干什么；注释要说的是三件名字说不清的事：

1. **为什么这么做** —— 决定背后的理由。「猫昨天吃坏过肚子，今天只许喂一条」—— 没有这句，下一位读者永远不知道那条规矩是故意立着的；
2. **这里有什么坑** —— 反直觉的地方、绕开某个老工具毛病的写法；
3. **怎么用它** —— 给别人用的口子，说清规矩（什么范围算正常、出错怎么回话）。

看一段对照着读喵：

```c
#include <stdio.h>

int main(void) {
    int fish = 3;
    /* 猫昨天吃坏过肚子，今天只许喂一条 */
    fish = fish - 1;
    printf("%d\n", fish);  /* 把剩下的印出来 */
    return 0;
}
```

```text
2
```

同一段里两处注释，一好一坏：

- 第一句（**为什么**）：留下了，后来的人不会手痒把「只喂一条」改成「能喂多少喂多少」；
- 第二句（**复述**）：「把剩下的印出来」—— 这一行代码自己就是「把剩下的印出来」，注释把代码又说了一遍，属于白写。**复述代码的注释，是注释里最该删的一种。**

再记两个格式上的小规矩：井号（或双斜杠）和注释正文之间，留**一个空格**；行尾注释和代码之间，至少留**两个空格**。看着是小事，读起来是呼吸感喵。

## 改了代码，记得改注释

注释最毒的一种坏法，不是写得多、写得浅 —— 是**和代码分了家**。本喵见过一句祖传魔咒：

`i = i + 1  # 这里减一`

代码在加，注释在减。谁对？读的人无从判断 —— 代码不会报错，注释也不会报错，两个都对不上时才最要命。工程圈的规矩很干脆：**与代码打架的注释，比没有注释更糟。**

- 改代码的时候，顺手看一眼头上的注释**还对不对**；
- 对不上时，两条路：**改它**（推荐），或者**删它**（宁可没有，别留误导）；
- 别指望「以后一起改」—— 以后没有「一起」。

## 同一件小事，好名字长这样

规矩说了一路，看活喵。同一件小事 —— **把筐里的鱼数出来** —— 四门语言各起各的好名字：

```compare
c::
#include <stdio.h>

int count_fish(const int fish[], int size) {
    int count = 0;
    for (int i = 0; i < size; i++) {
        if (fish[i] > 0) {
            count++;
        }
    }
    return count;
}

int main(void) {
    int basket[] = {1, 1, 1};
    printf("筐里有 %d 条喵\n", count_fish(basket, 3));
    return 0;
}

cpp::
#include <iostream>

int CountFish(const int basket[], int size) {
    int count = 0;
    for (int i = 0; i < size; ++i) {
        if (basket[i] > 0) {
            ++count;
        }
    }
    return count;
}

int main() {
    int basket[] = {1, 1, 1};
    std::cout << "筐里有 " << CountFish(basket, 3) << " 条喵" << std::endl;
    return 0;
}

java::
public class Main {
    static int countFish(int[] basket) {
        int count = 0;
        for (int fish : basket) {
            if (fish > 0) {
                count++;
            }
        }
        return count;
    }

    public static void main(String[] args) {
        int[] basket = {1, 1, 1};
        System.out.println("筐里有 " + countFish(basket) + " 条喵");
    }
}

python::
def count_fish(basket):
    count = 0
    for fish in basket:
        if fish > 0:
            count += 1
    return count


basket = [1, 1, 1]
print(f"筐里有 {count_fish(basket)} 条喵")
```

```text
筐里有 3 条喵
```

四段本喵全真跑过，输出逐字相同。名字上的看头喵：

- **C**：`count_fish` —— 说人话的招式名，全小写加下划线；
- **C++**：`CountFish` —— 同一个意思，开头抬了头（大驼峰）；
- **Java**：`countFish` —— 小驼峰，头一个字低着；
- **Python**：`count_fish` —— 又是下划线；四家里装鱼的筐**都叫 `basket`** —— 注意了：连形状都还没统一，四家却在「说人话」上完全一致。

装鱼的筐、数鱼的招式 —— 名字各自怎么拐弯先放一边，**读完就知道在干什么**，这四条标准是四家的公共底线喵。

::: tip 猫咪提示
今天的手艺，一句话一套收好喵：

1. **起名先说人话** —— 为一个不在你团队的新读者优化；
2. **四个标准** —— 说人话、读得出声、别缩过头、长度与作用域成比例；
3. **拼音和中文不上桌** —— 编码、工具链、协作三条线都在拦它；
4. **注释答三问** —— 为什么、什么坑、怎么用；复述代码的注释删掉；
5. **改了代码记得改注释** —— 与代码打架的注释，比没有更糟。
:::

::: warn 小心喵
三件事别做，做了要还债：**名字图短**（`tf`、`js`）、**注释复述**（代码说什么它说什么）、**注释分家**（代码改了它不改）。三个坑都属「当场没事、日后爆炸」喵。
:::

## 一句话对照表

| 本喵写下的 | 它的意思 |
|---|---|
| `total_fish` | 读完就懂的仓库名：鱼的总数 |
| `tf` / `zheKouLv` | 缩过头 / 拼音缩写：只有作者认识的坑 |
| 「为不在你团队的新读者优化」 | 起名的第一条尺子 |
| 「长度与作用域成比例」 | 看得见的人越多，名字越要说全话 |
| 「不许拼音混英文」 | 阿里手册的强制条款，编码/工具/协作三线都拦 |
| 「猫昨天吃坏过肚子，今天只许喂一条」 | 好注释答「为什么」 |
| 「把剩下的印出来」 | 坏注释复述代码本身，删 |
| 「与代码打架的注释，比没有更糟」 | 注释和代码分家，宁可删掉 |
| 井号与注释正文之间留一个空格 | 格式上的呼吸感 |

## 小任务

1. **动脑**：给你的项目里三个名字「体检」：拿四标准各过一遍（说人话吗？读得出来吗？缩写过头吗？长度配得上作用域吗？），列出「会诊意见」再动手。
2. **动手**：把钩子里的三个拼音名字重起名（提示：折扣率、商品价格、打折促销），把它们跑一遍，确认输出还是 `72.0` —— 尝尝「同样的值、不同的名字」差在哪。
3. **再动手**：翻自己旧文件里的一条注释，问它属于三问里的哪一问；答不上来（多半是在复述代码），删掉它，跑一遍确认什么坏事都没发生喵。

这一课收在「起名」和「注释」上，可它们终究要落在**具体某一门语言**里 —— 同一个意思，Java 叫 `totalFish`、Python 叫 `total_fish`，C++ 还有自己的倔强。下一课把四家的「方言」摆成一排：《四种方言四种规矩——跨语言规范对照》见喵。给别人的口子写注释的那手细活，Java 线有《写给下一个读代码的人——Javadoc 注释规范》等着你～ 🐾
