## 钩子：查一行，凭什么这么快

上一课的修路和排期，把图论这条线收了个尾：该连的连上、该排的排好，谁先谁后一目了然。本喵刚想把图纸卷起来收工，面试官大肥鱼「啪」地把笔记本电脑转了过来——屏幕上是一张鱼干订单表，**几百万行**，一行行记着谁买的、什么时候买的、买了几条小鱼干。

「查一行。」大肥鱼用鱼鳍敲了敲屏幕，「订单号 618324，就这一行。你倒是说说，**凭什么这么快？**」

本喵愣了一下。几百万行，一行一行翻，翻到猫毛都白了也翻不完喵。可数据库偏偏一眨眼就把那一行叼了出来，连个哈欠都不打。这一课就拆这台戏法——**B 树与索引**。

## 慢在哪儿：一次读盘，抵得上几万次比较

要弄明白数据库为什么快，得先知道它慢在哪儿。

数据不是飘在空气里的，它躺在**磁盘**上。查询的时候，数据库得先把数据从磁盘搬进内存，才看得见。这一搬，叫一次**磁盘 I/O**。它到底有多慢？本喵列一张粗略的量级表（只记数量级，别当精确值喵）：

| 动作 | 大概耗时 | 折算成「一次比较」的倍数 |
|---|---|---|
| 内存里比较两个数 | 约 1 纳秒 | 1 倍 |
| 读一次内存 | 约 100 纳秒 | 100 倍 |
| 固态硬盘随机读一页 | 约 100 微秒 | 十万倍 |
| 机械硬盘随机读一页 | 约 10 毫秒 | 一千万倍 |

看清楚这张表喵：**内存里比一次是纳秒，磁盘上随机读一次是微秒到毫秒**——中间隔着五到七个数量级。你在内存里多比较一百次，可能还不如少读一次盘来得划算。

这里冒出一个关键结论，本喵先把它钉在墙上：

> **索引要优化的是「读几次盘」，不是「比较几次」。**

很多人一听「查找快」，脑子里第一反应是「比较次数少」。在内存里这么想没错；可数据在磁盘上，**比较几乎不要钱，读盘才要命**。谁能让读盘的次数变少，谁就赢。

数据库还把磁盘切成一块一块的**页**——MySQL 的 InnoDB 默认一页 **16KB**。读的时候不是想读几个字节就读几个字节，而是**至少搬一整页**。所以本喵下面说「读一个节点」，意思就是「搬一页，也就是一次磁盘 I/O」。

## 会分叉的猫爬架，栽在磁盘上

前面学过一种会分叉的猫爬架——**二叉搜索树**：每个节点一个键，左小右大，查一个数就顺着分叉往下走。

在内存里，它挺神气。可搬到磁盘上，它有个要命的毛病：**一个节点只装一个键、最多两个孩子**。一页 16KB 的磁盘块，它只用了开头几十个字节，剩下九成九全浪费了。

100 万行数据，树高是多少？按 2 一次次分下去：

> log₂(1,000,000) ≈ 19.93

也就是**大约 20 层**。最坏情况下，查一行要从根一路走到叶子，**读 20 个节点**。每个节点各占一页，就是 **20 次读盘**。

20 次读盘是什么概念喵？按机械硬盘一次 10 毫秒算，光是读盘就要 200 毫秒——你点一下搜索，猫都打了个哈欠回来。

更要命的是「平衡」这件事：二叉搜索树要是长歪了（比如订单号是递增插进来的），它会退化成一根斜着的棍子，树高变成 100 万层。那就不叫查了，那叫从头翻到尾。

所以问题很清楚：**树太瘦太高，每下一层就多读一次盘。** 想少读盘，就得让树**矮下来**。怎么矮？——让每个节点多装点东西。

## 矮胖的树：一个节点塞几百个键

B 树的想法特别朴素：**既然一次读盘本来就搬回一整页，那这一页里为什么只放一个键？** 一页 16KB，一个键加上一个孩子的位置，假设占几十个字节——一页足足能塞下**几百个键、几百个孩子**。

这个「一个节点能挂几个孩子」的数，叫**扇出**。扇出是 B 树家族的命根子喵。

B 树有这么几条规矩（教科书上的标准说法）：

1. **一个节点里有多个键、多个孩子**，不是「一个键两个孩子」；
2. **所有叶子在同一层**——树是齐刷刷的，不会一边高一边低；
3. **节点里的键按顺序排好**，从左到右一个比一个大；
4. 查找的时候，**先在节点内部做二分**：几百个键排好队，分十几次就能定位到该往哪个孩子走。

第 4 条特别妙：节点里那几百个键是**在内存里**比的，二分一次只要十几步，几乎不要钱；真正花时间的是「把这一页读进来」那一下。**用内存里的比较，换掉磁盘上的读盘**——这就是矮胖树的全部生意。

于是树高从「按 2 缩」变成了「按扇出缩」。扇出 100 时，每往下一层，节点个数就乘以 100：

| 层 | 这一层有多少个节点 | 每个节点往下指 |
|---|---|---|
| 第 1 层（根） | 1 | 100 个孩子 |
| 第 2 层 | 100 | 100 个孩子 |
| 第 3 层 | 10,000 | 100 个孩子 |
| 第 4 层（叶子） | 1,000,000 | 每个放一行，没有孩子 |

乘起来：1 × 100 × 100 × 100 = 1,000,000。这就是「100 万行、扇出 100，一共 4 层」的来历——**根算第 1 层，叶子算第 4 层**，别少数成 3 层喵。

这里有个诚实的说明：上面是把「每一行」都当成一个叶子条目来数的，所以 100 万行要 100 万个叶子。真实数据库里，一片叶子页能装几百行，层数只会更少——**4 层是最保守的上界**，拿来和二叉搜索树的 20 层对比，已经足够说明问题了。

本喵用一段代码把这两笔账一起算出来：

```python
rows = 1_000_000

probes = 0
reach = 1
while reach < rows:
    reach *= 2
    probes += 1

reads = 1
covered = 1
while covered < rows:
    covered *= 100
    reads += 1

print(f"binary probes: {probes}")
print(f"btree reads: {reads}")
```

```text
binary probes: 20
btree reads: 4
```

两段绕圈，各算各的账喵：

- 上面那段：每翻一倍记一次探测，2¹⁹ = 524288 还盖不住 100 万，2²⁰ = 1048576 才盖住——所以二叉搜索要 **20** 次。
- 下面那段：每乘一次扇出记一次读盘，100、10000、1000000，三次就盖住了 100 万行；再加上根那一层，正好 **4** 次。

**底数从 2 换成 100，次数就从 20 掉到 4。** 20 次读盘和 4 次读盘，差的是五倍；再乘上每次读盘的时间，就是「卡一下」和「一眨眼」的区别。

## B+ 树：数据全在叶子上，叶子还牵着链子

B 树已经很能打了，可大多数关系型数据库（比如 MySQL 的 InnoDB）用的还不是它，而是它的升级版——**B+ 树**。两者的区别，本喵用一张表摆出来：

| | B 树 | B+ 树 |
|---|---|---|
| 内部节点存什么 | 键 + 数据（或指向数据的地址） | **只存指路用的键** |
| 数据存在哪儿 | 每一层节点都可能存 | **全部在叶子上** |
| 叶子之间 | 没有链子 | **用链子串起来** |
| 查一行 | 可能在中途某个节点就命中 | **一定走到叶子** |

先说第一个好处：**内部节点只存键、不存数据**，同样一页 16KB，能塞下的键就更多，扇出更大，树更矮。这是「瘦身换身高」喵。

再说第二个好处，也是 B+ 树最漂亮的地方：**叶子之间有链子**。所有叶子按顺序排在最后一层，再用一根链子从左到右串起来。

这根链子是干嘛的？专门伺候**范围查询**。

假设大肥鱼说：「把订单号在 500000 到 500100 之间的订单都叼出来。」这就是 SQL 里的 `BETWEEN`；或者他说「按日期排好给我」，那就是 `ORDER BY`。这类查询要的不是一行，是**一连串挨着的行**。

- 用 **B 树**：数据散在各层节点里，你找到 500000 之后，下一个 500001 可能在另一个分支，得爬上去、再下来，来回折腾。
- 用 **B+ 树**：先在树里找到 500000 所在的那片叶子，然后**顺着叶子的链子往右扫**——500001、500002……一片叶子读完接下一片，一路扫过去，根本不用回到上层。

所以范围查询在 B+ 树上特别顺：**定位一次，剩下全靠链子。**

> **本喵提醒**：别把「B 树」和「B+ 树」当成同一个东西喵。考试卷子上要写清楚：**B+ 树的数据只在叶子上、叶子之间有链子；B 树的节点自己也能存数据。** 这两句话是送分点，也是送命点。

### 一个节点里的二分

顺便把「节点内二分」走一遍，免得它只是个名词喵。假设一个节点里排着这些键：

```text
[ 10 | 25 | 47 | 63 | 88 | 102 | 150 ]
```

要找 70。先看中间那个 63：70 比 63 大，往右半边找；右半边中间是 102：70 比 102 小，往左；剩下 88：70 比 88 小——落到 63 和 88 之间，走那一格对应的孩子。七个键，**三次比较**就定了方向。

要是节点里有 300 个键呢？二分也就 **9 次**（2⁹ = 512 > 300）。9 次内存比较，换掉一次读盘——这买卖太划算了喵。

## 天下没有白拿的索引

讲到这里，你可能已经想给自己的每张表都加十个索引了。先别急，本喵把账本翻到支出那一页。

索引是一棵**额外的树**，它不会自己长出来，也不会自己保持正确。每次你插入一行、更新一行、删除一行，数据库都得**把这棵树一起改**：找到位置、插进去、键满了还要分裂节点、删多了还要合并。**查询快出来的时间，是从写入那里借的。**

还有磁盘：索引本身要占地方。一张表三个索引，可能就是三棵额外的树，写三份键。

所以本喵把话说全：

- **索引让读变快，让写变慢，还占磁盘。**
- **不是越多越好。** 只给真正要拿来查的列建索引；查询里根本不出现的列，建了就是白养一棵树。
- 还有一种情况：如果一次查询要取回表里**大部分行**，走索引反而绕远——顺着整张表扫一遍可能更便宜。索引不是万能钥匙喵。

> **小心喵**：索引不是「加了就赚」。每条写操作都要伺候它，每份空间都要花钱。建索引之前先问自己：**这条查询真的常用吗？它真的需要吗？** 两个都答「是」，再动手。

### 复合索引：最左前缀

还有一种索引叫**复合索引**——把好几列捆在一起建一棵树。比如订单表上建一个 `(customer_id, order_date, amount)` 的索引。

它的规矩叫**最左前缀**：这棵树先按第一列排，第一列相同再按第二列排，再相同按第三列排。所以它能帮上忙的查询是：

| 查询条件 | 用得上这个索引吗 |
|---|---|
| 只按 `customer_id` 查 | 用得上（最左那一列） |
| `customer_id` + `order_date` | 用得上 |
| `customer_id` + `order_date` + `amount` | 用得上 |
| 只按 `order_date` 查 | **用不上** |
| 只按 `amount` 查 | **用不上** |

为什么喵？因为树是**先按 customer_id 排好的**。同一个日期的订单，散落在不同客户的分支里，根本不挨着——你没法在树上顺着一条线把它们扫出来。想让第二列单独能用，就得**另建一个以它打头的索引**。

这就是「最左前缀」四个字的分量：**索引的列顺序，就是它的使用顺序。** 建 `(a,b,c)` 能顶 `a`、`a+b`、`a+b+c` 三种用法，但单查 `b` 用不上——顺序反了，树就帮不了你。

## 三种语言，同一笔账

最后把这两笔账翻成三种方言。三段程序算的是同一件事：每翻一倍记一次探测，直到盖住 100 万行；每乘一次扇出记一次读盘，直到盖住 100 万行。

```compare
cpp::
#include <iostream>

int main() {
    int rows = 1000000;
    int probes = 0;
    long long reach = 1;
    while (reach < rows) {
        reach *= 2;
        probes++;
    }
    int reads = 1;
    long long covered = 1;
    while (covered < rows) {
        covered *= 100;
        reads++;
    }
    std::cout << "binary probes: " << probes << std::endl;
    std::cout << "btree reads: " << reads << std::endl;
    return 0;
}

reads = 1
covered = 1
while covered < rows:
    covered *= 100
    reads += 1

print(f"binary probes: {probes}")
print(f"btree reads: {reads}")
```

```text
binary probes: 20
btree reads: 4
```

三段输出一模一样喵。底数从 2 换成 100，次数就从 20 掉到 4——**这就是「矮胖」两个字的全部数学**。至于数据库为什么偏爱 B+ 树而不是 B 树：内部节点只存指路的键，扇出更大、树更矮；叶子又有链子，范围查询顺着扫就行。两条加起来，读盘次数被压到了最少。
